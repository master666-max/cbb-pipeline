# 图谱派生层（GraphRAG / LightRAG）接入手册

写于 2026-09-25。判据来源：本机实跑（GraphRAG 3.2.0 冒烟索引一条完整管线 + LightRAG 1.5.7 直灌实验），
不是文档转述。凡"未测"集中列在末节，不许当已知用。

## 0. 一层话定位：这层能干什么、不能干什么

GraphRAG / LightRAG 的产物是 **L4 派生视图**：可坏、可重建、可以不准，**不许反过来成为事实源**。
理由是产出形态，不是实现质量——它们的记录是"块级来源 + 模型改写的描述"，
没有 `(卷,单元,行,引文)` 四元组，描述也不是原文逐字子串。要进正典必须过回填与人工抽检两道。

三条推论：

1. 派生层的抽取结果**永不写入 confirmed 面**；它只当先验、当主题候选、当巡检的图载体。
2. 派生层坏了不阻断干活，但**记导出债务**（终审必须见到这块债的处置）。
3. 派生层的"干净"（零孤悬、零矛盾、社区数 0）一律先当可疑，直到判定面被证明非空。

## 1. 三种接入拓扑与选型

| 拓扑 | 做法 | 实测成本 | 判定 |
|---|---|---|---|
| A 各跑一遍 | GraphRAG 抽一遍 + LightRAG 再抽一遍 | 卷1 ≈ 3.1h + 再 1.5~2h，两倍 LLM 账 | **不推荐**：同一弱模型两次幻觉互相"印证"；别名分裂只会变成两套各分裂一次 |
| B 一次抽取、两份产物 | GraphRAG 从原文抽（唯一一次 LLM 抽取）；LightRAG **不抽取**，只灌已核验的正典记录 | 灌库 **LLM 0 次 / 嵌入 5 次**（3 实体＋2 关系，实测） | **默认** |
| C 只用一个 | GraphRAG 的 `graph.graphml` 直接导进本项目专属 Neo4j 当巡检图载体 | 零额外 LLM | 资源紧时走这条，别硬撑两套 |

B 的交叉验证仍然在，而且验的是真正想比的那一对：**人审过的正典记录 vs 模型机抽的图**。

B 的技术前提（LightRAG 1.5.7 源码行号＋本机实跑）：
`acreate_entity`（`lightrag.py:6749`）、`acreate_relation`（`:6785`，注释明确接受 `source_id`，
且规定 `weight` ≥ 去重后的 `source_id` 数）、`ainsert_custom_chunks`（`:1878`，允许调用方自己定切块边界
⇒ 可以把块边界对齐到章/行而不是让它的 token 切法乱切）。

实测回读（灌进去再查出来）：

```
get_entity_info("梅芙") →
 {"entity_name":"梅芙","source_id":"卷1·第1话·行1237",
  "graph_data":{"entity_type":"PERSON","description":"保护大家的持枪少女，手枪名为沙姆希尔",
                "source_id":"卷1·第1话·行1237","file_path":"卷1/卷1·第1话·行1237","created_at":…}}
```

⇒ **坐标字段能自定义并原样回读**，这是 B 能成立的关键。注意 `entity_type`/`description`
藏在 `graph_data` 一层里，第一遍读会误判成"字段丢了"。

## 2. 自造词与归纳标签的处置（本项目最容易做错的一处）

派生层给出的实体名，有一部分在原文里字面找不到。**整句"抽得不准"没法处置**，
必须按四类分开，责任方与修法都不同（实测：102 个实体 → 命中 86 / A 2 / B 1 / C 0 / D1 4 / D2 9）：

| 类 | 判据 | 责任方 | 处置 |
|---|---|---|---|
| 命中 | 原文逐字可定位（忽略大小写） | — | 可作 `canon_name`；仍须过引文逐字门 |
| A 写法变体 | 去间隔号/空白/全半角后可定位 | 模型少写或多写标点 | 归一后作 `canon_name`，原写法进 `aliases` |
| B 括注修饰 | 剥掉「（代称）」后可定位 | 模型 | 名字本体可用，括注内容转别名 |
| C 转换吃字符 | **模型原始回执里有正确写法且能精确命中，终值不能** | 上游流水线清洗 | 开上游缺陷单，数据不改、等修好重跑 |
| D1 可合成 | 拆得出 ≥1 个原文成词片段（`梅芙莉莎的手枪`←梅芙莉莎＋手枪；`天空都市·…的苍之学园`＝层级路径被压成专名） | 模型归纳 | `proposed` 标签：记 `grounded_to`（成素＋支撑块），**禁入受控词表与去重键**；路径型应拆成 `part_of` 边 |
| D2 纯命名 | 拆不出任何原文成素（`终末对抗`/`接吻行为`/`轻小说情节`） | 模型命名 | `interpretation`：**永不进 confirmed**；只当检索别名与主题候选，页面上标『非原文逐字』 |

D 类**不是缺陷清单，是候选清单**。"给一段动作起个可调用的名字"正是人读三遍才会做的动作，
事件名词化（`丝线攻击`）与主题标签（`停滞性末日之人`）直接对上伏笔台账与事件轴的缺口。
但它的价值只能在"检索别名 + 主题候选"这一侧兑现，一旦当身份键用就污染地基。

三条纪律（写进 `实体名归因.py`，不靠自觉）：

1. **零支撑不许立词**：D 类若无支撑块计数 ⇒ 判 `reject`（`--strict` 下退出码 1）。
2. **匹配键只认命中类与 A/B 归一后的名字**；D 类一律不得进受控词表与去重键。
3. **C 必须排在 A 前面判**：终值少写间隔号看着像模型的锅，可若原始回执里写的是对的，
   那就是流水线吃掉了字。**没有原始回执时不许默认判模型的锅**，要在依据里写明"不能排除是清洗吃的字"。
   （实测 graphrag 的 `clean_str` 只做 strip＋`html.unescape`＋删控制字符，中文标点不在其列，C 类＝0。）

另须自印**口径上界**：字面命中只证"这词出处有"，不证"这实体含义对"；未命中也不等于幻觉
（可能是译名差异或复合全称）。两端都不许被读成结论——仍需按 `审查与收口.md` 的分层抽样人工对原文。

## 3. 半途写的哨：`派生层对账.py`

实测事故：嵌入端点中途挂掉时，LightRAG 的 `acreate_entity` **已经把节点写进了图**
（graphml 里 `entity_id/entity_type/description/source_id` 全在），**向量库却没写**——
半途写、非事务，且调用侧只表现为一次异常，图与向量库从此不一致。
后果不是报错而是**静默**：图里查得到、向量召回不到，用 local/hybrid 检索会以为"这本书没有这条"，
与真没有完全同形。

四道检查（任一不过退出码 1）：C1 图节点数 == 实体向量记录数（并列两侧差集）、
C2 图边数 == 关系向量记录数、C3 每个节点必须带来源位、C4 正典名单为空 ⇒ 判失败
（判定面为空不许读成"都对得上"）。

**用法约定**：每次灌完派生层立刻跑一次，PASS 才准把该层挂上去给检索用；FAIL 就重建，别修修补补。

## 4. 本机跑法与四道环境门（都是撞出来的）

| 门 | 症状 | 真因 | 处置 |
|---|---|---|---|
| Windows 默认编码 | `Pipeline error: 'gbk' codec can't encode character '\u30fb'`，且在 `create_base_text_units` **之后**才炸、前面产物已落盘 | 中间件按系统默认编码（cp936）写文件，书里有日文中点 | 全程 `PYTHONUTF8=1 PYTHONIOENCODING=utf-8` |
| 端点路径 | 自检报 `litellm.BadRequestError: OpenAIException -`（空消息） | litellm 不给 `api_base` 补 `/v1`，实际打 `POST /chat/completions` 被拒 | `api_base` 一律写全 `…/v1` |
| 端口被系统占走 | `bind` 报 `WinError 10013` | 8391 落在 Hyper-V/WinNAT 保留段（`netsh int ipv4 show excludedportrange protocol=tcp` 可查；本机 8343–8442 整段排除） | 换段外端口；自建件一律把端口做成参数 |
| 思考道吃空正文 | `content` 空串、`finish_reason=length`、答案全在 `reasoning_content` | 本机 35B 两个都是思考型模板，且 LM Studio 不认 `chat_template_kwargs.enable_thinking=false` | 中转层回收，**回收不出就 502 中断**，绝不返回空串；每次调用留一行遥测（秒/token/回收态） |
| `response_format` 不兼容 | LightRAG 查询期 `400: 'response_format.type' must be 'json_schema' or 'text'`；把值置 null 又 `Cannot read properties of null` | 本地兼容层只认两种 type | 中转层**删键**（不是置 null）；实测删后仍按提示词里的格式出 JSON |

选型实测（同一道真章节抽取题）：`tifa-14b-cot` 11.6 tok/s、`content` 非空、`finish=stop` ⇒ 可用；
`hermes-3.6-35b` 15.5 tok/s 但 2400 token 全在思考道 ⇒ 直连必出假干净；
`qwen3.6-35b` 补 `/no_think` 后有正文但 3 tok/s ⇒ 不可用；`gemma-3-1b` 装载失败 500。

## 5. 成本账（用于排期，别拿旧估数）

GraphRAG 3.2.0 standard 方法，2 章 / 19 块：

```
105 次调用（抽取级 58）｜进 181,338 / 出 68,018 token｜LLM 墙钟 28.8 分钟｜回收态 105/105 PASSTHROUGH
产出：实体 102、关系 151、社区 20、社区报告 20、graph.graphml
均摊：5.53 次调用/块（含描述摘要与社区报告，不只抽取）
外推卷1（124 块）：约 685 次调用、1.2M 进 / 0.44M 出、串行 ≈ 3.1 小时
```

LightRAG 1.5.7：灌 3 实体＋2 关系 = **LLM 0 次、嵌入 5 次**；一次 local 查询 = **2 次 LLM**
（关键词抽取＋答案生成）＋查询向量 1 次嵌入。⇒ "每章都要跑"的活给 LightRAG，
"一卷才跑一次"的活给 GraphRAG，这条分工是按频率×成本切的，不是按偏好。

## 6. 未测清单（别当已知）

- LightRAG 实体级 `source_id` 上限（源码级记忆：`DEFAULT_MAX_SOURCE_IDS_PER_ENTITY=200` 会裁）
  **未在本机版本复验**；热表人物（一个名字出现上千块）会不会掉溯源，要装机时实测。
- LightRAG 抽取前剥 cite/refid 锚的行为：未在本机复验（B 拓扑不走抽取，暂不受影响）。
- 社区报告的**事实性**抽检：未做。冒烟只验了"出得来、是中文、字段齐"，没验"报告里的断言能回落原文"。
- 派生层名字与正典名单的**别名级**对齐（不是字面命中，是同指合并）：未测。
- 多语混排（书名里有日文假名与译注）下嵌入召回质量：未测。

## 7. 判定者身份（并入主链时必须写）

本手册所有数字由**本机 GGUF 模型**产出（GraphRAG 抽取与 LightRAG 查询期），
**不是宿主 Agent**。并入 CBB 流程时，`环境自检.py --judge` 必须如实声明判定者身份与端点，
报告里同口径写明"判定者=本地模型 <名>，非宿主 Agent、非付费端点"，并附实测速度表——
否则这份账会被误读成宿主 Agent 的产出质量，两边口径都会错。
