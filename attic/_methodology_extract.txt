第一章　一页导读：双库体系是什么
本工作区要建立的是两套互相链接、互相成就的库。第一套是知识库（knowledge/），它回答「怎么做事」：存放踩过的坑、提炼出的可复用范式、以及固化成技能的操作流程。第二套是工件库（archive/），它回答「做出来的东西在哪、怎么复现、怎么续接」：存放已完成任务的代码、数据、交付物和交接说明。两套库各自解决一半问题，但真正让体系产生复利的是它们之间的双向链接。
互链互证是整个体系的价值倍增器。知识库里的每一条教训和范式，必须挂上至少一个真实存在的工件实例作为证据——没有实例佐证的经验会越来越抽象空洞，最终沦为正确的废话；工件库里的每一个项目 README，必须回链相关的知识库条目——没有经验提炼的档案会越堆越厚，三个月后连自己都找不到东西。这两条链接把「做过的任务」变成了「可检索、可复用、可进化的资产」。
体系的运转靠两个闭环技能驱动。任务开始时执行 task-start：先读索引、检索相关教训与范式、声明本次要规避什么和复用什么，然后才动手。任务结束时执行 wrap-up：清场、归档、复盘、互链、同步索引五步依次执行。一个管「进门」，一个管「出门」，知识就在这一进一出之间持续积累。
配套的执行文件是工作区根目录下的《双库自进化体系·建库提示词.md》，它是一份自包含的可执行提示词，放在工作区根目录后，任何具备文件读写能力的 Agent 工具（ZCode、Claude Code、Cursor、Codex CLI 等）都可以一键执行建库。本文件则是它的人类阅读版，解释每一条设计背后的「为什么」。

第一份文件给出了体系的宪法：五条铁律。其中最要紧的两条，一是永不删除、永不覆盖已有文件，废弃版本一律移入 attic/ 保留；二是写入知识库的每条教训必须有工作区内的真实依据，禁止编造听起来合理的经验。后者是 AI 协作场景特有的污染源——语言模型极擅长生成「貌似合理的教训」，一旦编造内容混入知识库，体系就会用错误经验污染未来的每一次任务。

第三份文件贡献了认知模型：让 AI 越用越强的核心不是「记住」，而是「复盘、提炼、固化、回灌」这个闭环。它把知识按更新频率和读取方式分成五层（详见第四章），并强调没有淘汰机制的库会在三个月内变成垃圾场——这是所有自进化系统踩过的共同坑。
三份文件合流后的设计原则可以压缩成一句话：知识库存方法、工件库存成果、互链作证据、闭环驱动进化、淘汰对抗腐烂。
第三章　业界调研：这套体系有据可依
双库体系并非凭空发明，它的每个部件都能在业界找到经过验证的原型。建库前做了一轮针对性调研，以下是四条最有分量的发现，它们已经分别吸收进提示词文件的对应设计里。
3.1　Anthropic Agent Skills 官方最佳实践
Anthropic 为 Agent 技能文件（SKILL.md）发布了官方编写规范，有三条直接影响了本体系。第一，frontmatter 里的 description 字段是自动路由的关键，要写清楚「什么时候用」的触发条件和「效果如何」的量化数据，Agent 的自动调用准确率直接取决于这个字段的质量。第二，渐进式披露：SKILL.md 本体保持精简，细节放在 references/ 目录，脚本放在 scripts/ 目录，按需加载而不是全量预载。第三，小而聚焦的「微技能」优于大而全的单体技能，多个微技能可以链式组合。本体系的 task-start 和 wrap-up 两个技能的写法即遵循这三条。
3.2　自进化 Agent 的复利模式
业者在实践自进化编码 Agent 时得出一个关键结论：上下文文件（如 AGENTS.md、CLAUDE.md）的价值在于让知识跨会话复利，而实现复利的关键环节是「任务收尾时的复盘写入」——没有 wrap-up 这一步，Agent 每次会话结束就把学到的东西丢掉，永远无法累积。这与本体系把 wrap-up 称为「体系的发动机」是同一个判断。配套的做法是让索引常驻上下文：在会话入口文件里加一行「每次会话开始先读 knowledge/_index.md」，用不到两百行的索引换取全局经验的可及性。
3.3　持久记忆的读写回路
关于 Agent 持久记忆系统的实践总结了一个朴素的回路：任务后复盘提炼，把蒸馏后的教训写入持久文件；任务开始前再把这份文件读回来。写什么、读什么、什么时机触发，三个问题都指向同一个答案——结构化、带触发条件、带验证状态的经验条目。孤立的日记式记录无法被检索命中，这是多数「记了但没用」的失败案例的共同根因。
3.4　结构化 Markdown 优先于向量数据库
在存储选型上，业界有一个反直觉的共识：在库规模达到千条以上之前，结构化 Markdown 加索引在能力传递上通常优于向量数据库 RAG。Markdown 可读可编辑、Agent 可以直接修改、能用 Git 做版本管理、零运维成本。本体系据此从纯 Markdown 起步，并预留了演进路径：超过五百条经验后引入轻量向量索引补充语义检索，超过五千条且多 Agent 共享时再考虑向量库加元数据库。

第四章　五层知识分层模型
知识库不是一个大杂烩文件夹，而是按「更新频率」和「读取方式」分层的五个层次。分层的目的不是分类好看，而是让不同抽象层级的信息以不同的节奏更新、被不同的机制读取。

前三层解决「这次学到了什么」，后两层解决「下次怎么自动用上」。没有第四、五层，前面积累再多也只是日记——这正是多数个人知识管理失败的根因：只有存储，没有检索与回灌。
条目的写入格式也有讲究。教训条目（pitfall）包含四要素：场景（在什么情况下遇到的）、教训（核心结论一句话加根因）、详情（可选）、实例链接（必须指向真实存在的工件）。范式条目（pattern）在此基础上多一层「验证状态」：待验证、已验证 N 次、部分适用。验证状态是后续进化循环的驱动数据——它决定了这条经验什么时候升级成技能、什么时候被淘汰。
第五章　目录结构与归档模板
5.1　整体目录骨架
双库体系在磁盘上的样子如下。workspace 是热区，放进行中的任务，结构随意，反正收尾时会清场；knowledge 和 archive 是两个冷区，一旦写入就按规矩来。
knowledge/                      # 知识库：存「怎么做事」
├── _index.md                   # 总索引（200 行内，每次会话必读）
├── pitfalls.md                 # 教训库，编号 P-001 起
├── patterns.md                 # 范式库，编号 PT-001 起
├── decisions.md                # （可选）架构决策记录
├── tools.md                    # （可选）工具使用心得
├── skills/                     # 固化技能层
│   ├── task-start/SKILL.md
│   └── wrap-up/SKILL.md
└── trajectories/               # 原始轨迹（只追加，不加载）
archive/                        # 工件库：存「做出来的东西」
├── _INDEX.md                   # 项目索引（项目级条目）
├── _cold/                      # 冷区：12 个月未引用的项目压缩存放
└── {YYYY}/{MM}/{task-name}/    # 按完成年月归档
workspace/                      # 热区：进行中任务（结构随意）
5.2　单项目归档模板
工件库的基本单元是一个自包含目录：一个已完成的任务对应一个目录，三个月后不需要翻聊天记录就能接续。目录结构借鉴数据科学界验证过的 Cookiecutter Data Science 标准并做了 AI 协作适配。
{task-name}/
├── README.md        # 核心元数据，写给「三个月后的你或全新 AI 会话」
├── HANDOFF.md       # 交接说明：未完成事项、已知限制
├── src/             # 正式代码（notebook 升级后放这里）
├── data/raw|interim|processed/   # 数据三层，raw 只读不改
├── outputs/         # 交付物（文件名带版本，明确终版）
├── notebooks/       # 探索性分析（3 个封顶，多了就提炼进 src）
├── configs/         # 参数配置，与代码分离
├── env/             # 环境快照（requirements.txt 等）
├── logs/            # 运行日志，可定期清
└── attic/           # 废弃旧版本（不删，移入这里）
其中的 README 是归档的灵魂，六个小节各司其职：一句话（这个项目做了什么）、复现（环境、确切命令、终版产物路径）、数据流（从原始数据到产出的完整链路）、关键决策（为什么这样做，否决过什么备选方案）、踩坑与经验（回链知识库条目）、复用提示（能否当模板、怎么改）。判断标准很简单：一个从没见过这个项目的 AI 会话，只靠 README 能不能在五分钟内恢复全部上下文。
5.3　大文件策略
代码、配置、README 进 Git 版本管理。当任务产出物普遍小于 10MB 时，数据也直接进 Git（或用 Git LFS）就够了；规模上来后再引入 DVC：Git 里只存几 KB 的 .dvc 元文件，实际数据放远程存储，用 push 和 pull 按需同步。这样一来，git clone 加 dvc pull 两个命令就能完整恢复任何一个归档项目。
5.4　面向 AI 读者的四条特殊设计
与传统工程归档最大的差异在于：这套库的读者一半是未来的 AI 会话。因此有四条针对性设计。其一，README 和 _INDEX.md 是 AI 的重入点，这两个文件的质量直接决定 AI 能否断点续传。其二，结构一致性优先于内容完美——AI 对固定结构的解析远优于自由格式，每个项目目录必须严格同构。其三，归档即模板：索引里标注三星可复用的项目就是活的脚手架，新任务直接复制整个目录改配置。其四，在 AGENTS.md 或 CLAUDE.md 会话入口文件里声明「每次会话开始先读 knowledge/_index.md」，让索引自动进入上下文。
第六章　闭环运行机制
6.1　task-start：任务启动三步
任何新任务开始前调用，作用是「带着历史开工」而不是每次从零开始。
读 knowledge/_index.md，列出与当前任务类型相关的 pitfalls 与 patterns；
读 archive/_INDEX.md，找出可复用三星项目作为脚手架候选；
开工前向用户声明：本次规避哪些坑、复用哪个范式或模板，确认后再动手。
6.2　wrap-up：任务收尾五步
任何任务完成后调用，是整个体系的发动机。五步依次执行，缺一不可。
第一步　清场：列出临时文件清单，经确认后删除或移入 attic/；确认唯一最终交付物，其余版本移入 attic/。
第二步　归档：workspace 任务目录移入 archive 对应年月，按模板补写 README；归档后目录视为只读。
第三步　复盘：失败与弯路写入 pitfalls 新条目（必须含根因一句话加实例链接）；成功路径写入 patterns 新条目或给已有条目验证次数加一；写入前先与已有条目对比去重。
第四步　互链：新条目补实例字段；项目 README 补回链。
第五步　索引同步：更新两个索引的新增行、触发次数、最后引用日期；验证达到三次的 pattern 标记为「建议升级为独立技能」，不自动执行。
6.3　进化循环与淘汰规则
归档不是终点。每条经验都要经历「验证、合并、淘汰」的生命周期，由明确的阈值规则驱动，而不是靠主观感觉整理。

第七章　落地路线与验收清单
7.1　建库六阶段
Phase 0 侦察：只读不写，扫描全目录，产出已完成任务、进行中任务、可挖掘素材三份清单；若工作区为空则跳过挖掘阶段。
Phase 1 搭骨架：按第四章目录结构建目录与文件头，已存在的跳过，保持可重复运行。
Phase 2 挖掘历史：对每个已完成任务建归档目录、移动文件归位、写 README、提炼经验写入知识库。
Phase 3 建索引与互链：生成两个索引文件，抽查全部互链，断链当场修复。
Phase 4 建闭环技能：写入 task-start 与 wrap-up 两个 SKILL.md。
Phase 5 验证与总报告：跑自检清单，输出目录树、条目统计、待确认清单与下一步建议。
执行中有一条贯穿始终的纪律：移动任何文件前先输出移动清单；拿不准的判断标记【待确认】集中留给用户裁决，而不是替用户做主。
7.2　人工验收三件事
自动化执行跑完之后，有三件事必须人工验收——它们恰恰是自动化跑不出来的部分。
教训真实性：抽查 pitfalls 条目，去对应文件验证「实例」是否真能支撑那条结论。语言模型编造貌似合理的教训是这套体系最大的污染源，铁律只能降低风险而不能根除。
复现可行性：随便挑一个归档项目，照着 README「复现」一节的命令跑一遍，跑不通就当场改。
移动完整性：对着侦察阶段的文件清单抽查几个原位置文件，确认都归位了而不是凭空消失。
7.3　日常使用与重构信号
体系建成后，日常只有两个触发词：任务开始时说「按 task-start 技能启动」，任务结束时说「执行 wrap-up」。积累一个月左右，会出现一批验证满三次的范式，那时把高验证范式批量升级成独立技能，双库就完成了从「记录」到「能力固化」的第一次进化。
五个信号说明该重构结构了：找一个明知存在的文件超过一分钟；notebooks 目录超过二十个文件还没有子目录；同样的处理逻辑出现在三个地方且各略有不同；说不清哪个文件是当前版本；接手的人或新 AI 会话反复问「这个放哪」。重构时机选在任务里程碑处或新协作者加入前，小步调整，不要等项目烂透了再大动。
第八章　附录：提示词使用说明
8.1　怎么用配套的提示词文件
工作区根目录下的《双库自进化体系·建库提示词.md》是自包含的：它把结构、模板、闭环逻辑全部压缩在一份文件里，不需要附任何对话原文。使用方法是把文件放在工作区根目录，然后对任何有文件系统权限的 Agent 工具说一句「按《双库自进化体系·建库提示词.md》执行建库任务」。纯对话式产品没有文件读写能力，跑不了这个任务。
提示词文件与本阅读文件的分工：提示词文件是给机器执行的，讲究无歧义、可校验、可重复运行；本文件是给人读的，讲究把每个设计的来龙去脉讲清楚。两者内容同源，遇到冲突以提示词文件的铁律部分为准。
8.2　阅读路径建议
如果只有五分钟：读第一章导读，然后直接翻到第六章表 6-1 看进化规则。如果有半小时：按章节顺序通读，重点消化第四章五层模型和第五章目录模板。如果要动手建库：以提示词文件为工作底稿，本文件作为查阅手册放在手边。
