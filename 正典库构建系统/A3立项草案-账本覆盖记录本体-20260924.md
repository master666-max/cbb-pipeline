# 立项草案 · A3：账本覆盖记录本体（libraries/**.json）

> 状态：**草案（未动工）**。来源：审计 R4 A3（P1）——「账本不覆盖 `libraries/**.json` 记录本体——正典内容篡改不可检」。
> 优先级：P1（防御面与系统宣称错配：库名"证据可核验正典库"，但正典正文当前不在防篡改覆盖内）。

## 一、问题（据实）

- 现状：`LedgedStore` 只包裹 `_append`（jsonl 旁车：aliases/appearances/state_changes/transitions/quarantine 两件…）；`ThreeStateStore._write_immutable`（`admit`/`supersede` 落库件的唯一写点）不入账。
- 后果：改写任一正典记录 JSON 的字段后，`ledger_chain verify` 仍返回 `ok:true`——防篡改覆盖不到"事实本体"，只覆盖到索引/旁车。
- 复现（现存行为，即为反例）：改 `libraries/character/provisional/<rid>.json` 任一字段 → `verify` 不报错。

## 二、方案（推荐 A3-1：复用现有机制，零新概念）

三段式，全部走既有的 append-only 账本，不引入新文件格式：

1. **P1a 基线入账**（一次性，对存量 6172 件）：对每个记录件追加 `genesis` 行，`target = libraries/<lib>/<state>/<file>.json`，`sha = 文件 sha256`。幂等：同 target 同 sha 已入账即跳过（`record_genesis` 现成语义）。
2. **P1b 写路径入账**：`LedgedStore` 覆写 `_write_immutable`——`created=True` 时记 `record_append(rel, key=record_id, sha_before=EMPTY_SHA, sha_after=现 sha)`；`created=False`（幂等命中、文件已存在）时**不记行**（无写事件，与"append 行才算占键"一致）。
3. **P1c 校验面自动扩**：`verify()` 现有逻辑已按 `last[target]`（含 `genesis`）与磁盘 sha 比对——基线与写路径入账完成后，**无需改 verify 逻辑**即产生"记录件被改即红"。

被否决的备选：
- 备选 B3-2「verify 时现算全库清单元数据」：不解决"改后仍自洽"（无历史基线可对照），且每次全量重算不落痕；
- 备选 B3-3「单行 Merkle 清单」：省行数但引入新结构 + 需定义清单格式与增量更新协议，收益（约 2.8 MB）不抵复杂度。

## 三、成本实测（本机 2026-09-24）

| 项 | 实测 | 影响 |
|---|---|---|
| 全库记录件 sha256 重算 | 6172 件 **1.45 s**（0.23 ms/件） | `verify` 每次 +1.5 s；`run_chapter` 前置/后置两门 = 每章 +3 s（相对每章 3–4.5 万 token 的抽取成本可忽略） |
| 账本新增行 | 约 6172 行 × 468 B ≈ **2.8 MB** | append-only；与现有 2.0 MB 同量级 |
| 规模外推 | 5 万件 → verify ≈ 12 s | 到量级再评估按需开关（`verify(deep=)`），现阶段不加开关 |

## 四、验收判据（每条都必须是可失败的反例）

1. **篡改必红**：改任一记录件一个字节 → `verify.ok == False` 且 errors 含 `当前 sha 与账本不符`；恢复字节 → 复绿。（对现状=必失败，故为真反例）
2. **新写入账**：`admit` 一件 → 账本出现该件 `append` 行；同件重放（幂等命中）→ **零新行**。
3. **基线幂等**：基线入账脚本连跑两次 → 第二次零新行；期间 `verify` 全绿。
4. **不可读件披露**：`iter_skipped` 中件不得进基线（sha 不可得）——记 `skip` 行并在报告披露（B6 不静默）。
5. **回放等价**：入账后重放账本（`verify`）在干净库上 `ok:true`，且 `rows` 增量 == 实际入账件数。

## 五、迁移与纪律

- **授权**：基线入账 = 向 `迷深实战-本体库/`（冻结线）追加账本行。需用户裁定引用（同 P0 原区补账先例）；`决策账.jsonl` 记 `ruling` + 写入时记 `hook-bypass` 同形条目。
- **append-only**：不重写、不删除既有 4466 行；基线行批量追加前/后各跑一次 `verify`（前置门精神）。
- **依赖**：写路径入账把账本写入频次从"每批 jsonl 追加"抬到"每记录件写入"——审计 B1（共享账本并发写纪律，已在 R-015 立条）的优先级随之上升；并发写场景需先落 B1 的"先读后写/重撞重读合入"纪律。
- **回滚**：不删行（append-only）；如需弃用基线，追加一条 `rebaseline` 覆盖该 target 的现行 sha，并在台账登记原因。

## 七、开放问题（待裁）

1. 基线粒度：逐件 `genesis`（6172 行）vs 分库合并行（每库一行、内容为名→sha 映射）——后者行数少但"每数带口径"变弱，且单行体积大。倾向逐件（推荐）。
2. 是否同时覆盖 `迷深实战-工作区/**`（manifest/candidates/gate1 等产物件）——审计未列；若覆盖，行数再翻倍（工作区件数与记录件同量级）。倾向**不覆盖**（工作区是过程物，本体库才是正典）。
3. `verify` 是否拆两级：`verify()` 常跑（含记录件，1.5 s）与 `verify(fast=True)`（仅 jsonl 旁车）——现倾向不拆，到 5 万件再说。
