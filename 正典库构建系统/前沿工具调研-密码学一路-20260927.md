# 前沿工具调研 · 密码学一路（2026-09-27）

> 深度档：Merkle 透明日志/OpenTimestamps/供应链证明/C2PA/轻量签名/哈希链形式化。全部活跃度/license 于 2026-09-27 实抓核验（GitHub API+PyPI+官方站点）；【待确认】处已标注。

## A. 逐题深度发现

**1. Merkle 透明日志（CT 谱系）**
- Trillian（Apache-2.0，v1.8.0 2026-09-21 仍活）=多写者服务器系统，单机不适用，**只抄数据结构语义**；社区主轴已移 transparency-dev（Tessera v1.0.4 活跃）。
- **Sunlight**（Filippo Valsorda，ISC，2026-09 活跃）：关键洞察=**日志不需要服务器 API——Merkle 树切静态 tile 文件放任何静态托管即可**；C2SP tlog-tiles 规范：tile 布局+`/checkpoint` 签名树头（Ed25519）。
- Python 侧：pymerkle（GPL-3.0 注意传染，RFC 9162 严格对齐）；**务实方案=proof 验证自写 ~80-100 行纯 Python**（照 RFC 9162 §2.1.3-2.1.4，用 transparency-dev/merkle 的 Go 测试向量对照）——贴合零依赖约束。

**2. OpenTimestamps**
- 创建免费（公共日历聚合锚进 Bitcoin，无需注册/key/本地节点）；延迟数小时非即时；.ots 证明仅几字节~几百字节；完全自验需 pruned Bitcoin Core（否则日历辅助验证，信任弱一档可离线复验）。
- client v0.7.2（LGPL-3.0，2026-02 仍有 push）；core 库刻意分离共识关键部分，极稳。
- 结论：**适用但只适合低频锚定**（按 release/按日锚 HASHES 或 checkpoint，而非逐行）——"记录 t′created 不可抵赖"的达标件。

**3. 供应链证明（in-toto/SLSA/sigstore）**
- in-toto：**CNCF graduated**，PyPI v3.1.0（2026-04，活跃）；Attestation Framework v1.2=通用 statement 格式（subject+predicateType+predicate，纯 JSON 可手写）。
- SLSA v1.2 Provenance predicate 字段已核验：buildDefinition（buildType/externalParameters/resolvedDependencies）+runDetails（builder.id/startedOn/finishedOn）——**正是"谁在何时用什么源构建了什么"的标准词汇表**。
- sigstore/cosign（极活跃）：keyless 签名依赖 OIDC+Fulcio+Rekor 外部基础设施（验证可离线 via bundle）——**与零服务单机冲突，排除**。

**4. C2PA 内容凭证**
- 规范 2.4（含 AI/ML 专章，trainedAlgorithmicMedia 断言）；c2pa-python（MIT OR Apache-2.0，极活跃）。
- **可借鉴核心=清单式断言结构**：claim（谁/何时/签名）+assertions（来源哈希 c2pa.hashData/操作历史 c2pa.actions/ingredient 嵌套引用）——**借结构不借容器**（JUMBF+证书链对内部库是重依赖）。

**5. 轻量签名与密钥管理**
- minisign（Rust 版 0.12，ISC，Windows 可用，Ed25519 单文件签名）；**SSH 签名（SSHSIG）：Windows 10/11 自带 OpenSSH，零安装**——`ssh-keygen -Y sign/verify` 且 **allowed_signers 原生支持 valid-after/valid-before + verify-time=按任意历史时点验证**（密钥轮换时间窗内建）。
- git 集成：`git commit -S` + `gpg.format=ssh`（Git ≥2.34）。
- 密钥轮换与信任锚：仓库内**版本化 TRUSTED_KEYS.md**（公钥+key id+生效区间+namespace），轮换期新旧双签过渡链=TUF 思想的单机极简版，不需引入 TUF 本身。

**6. 哈希链形式化与检查点纪律**
- RFC 9162（已抓取核验）：MTH §2.1.1（域分离）/inclusion §2.1.3/**consistency §2.1.4（证明"新树是旧树的追加扩展"）**/STH §4.9-10；**§1.6 明示：防日志方作弊（split-view）的 gossip 机制超出范围**——即"检查点必须发布到日志存储之外"是有出处的纪律。
- hash chain vs Merkle：线性链篡改可见但需全量重放、无高效存在性证明；Merkle 追加日志=O(log n) inclusion/consistency（Crosby & Wallach history trees，USENIX Sec 2009）。
- 生产检查点纪律谱系（Key Transparency）：WhatsApp KT（每 epoch 原子提交+审计记录发第三方公开存储，facebook/akd Apache-2.0 活跃）、Apple iMessage CKV（CONIKS 型+48h MMD+客户端互传 log hash 抓 split-view）、Sigsum（强制 witness 共签）。⚠️ google/key-transparency 旧仓库 2021 已归档，勿再引为现役。

**一句话形式化结论**：防篡改证明成立条件=①追加日志＋②**周期性把签名树头/链头检查点发布到日志存储之外的外部追加通道**。缺②，任何链都可被持有者整体重写——这是纯机内账本的唯一真正弱点。

## B. 对账本与构建/发布链的升级建议（性价比排序）

1. **检查点发布纪律（最高优先，零新依赖）**：每次 build/release 算账本头（行数+链头哈希），写成 C2SP checkpoint 风格文本（origin/size/hash/时间/签名），推到**独立外部追加通道**（公开只读 git 仓/静态站/邮件存档均可）→ 防持有者事后整体重写（split-view）——现有 sha256 链唯一真漏洞。
2. **OTS 低频锚定**：每次 release 对 HASHES.json/checkpoint 跑一次 `ots stamp`，.ots 随产物发布 → 防 t′created 倒签；成本 0 延迟数小时。
3. **账本并行 Merkle 索引**：每 N 行算 RFC 9162 树根入 checkpoint → 篡改定位从全量重放降为 O(log n)，第三方可验"某行在某版本存在"；自写 ~100 行（避免 GPL pymerkle）。
4. **HASHES.json → in-toto attestation**：statement JSON（subject=内容寻址 id+sha256；predicate=canon-build/v1：源快照哈希/构建命令/起止时间/builder 指纹）+ minisign/SSH 签名 → 获得与 in-toto/SLSA 生态互认的标准词汇。
5. **签名件与导出凭证**：Windows 自带 `ssh-keygen -Y`（namespace 区分 canon-checkpoint/canon-release）；`git commit -S`；导出图谱/百科页借鉴 C2PA 断言清单结构（HTML meta/JSON 旁车嵌来源 manifest）。
6. **信任锚文档**：TRUSTED_KEYS.md 版本化（公钥+key id+生效区间+namespace），轮换期双签过渡，历史验证按时点匹配。

## C. 排除项

直接上链/代币（OTS 属"用链不发币"，相容）；google/key-transparency（2021 归档）、merkletools（2018 停更）、in-toto-attestation PyPI 绑定（落后 spec v1.2，statement 手写即可）、ct-woodpecker（仓库查不到【待确认】）；Trillian/Tessera/Sunlight 服务器部署（单机取数据格式即可）、SLSA L2/L3+hosted builder（需 CI）、sigstore keyless 全家桶（外部服务冲突）、完整 C2PA SDK 容器（借结构不借容器）、TUF 完整框架（取轮换思想）；pymerkle（GPL-3.0——内部无碍，对外分发注意，替代=自写 RFC 9162 验证器）。
