# 使命：为本工作区建立「双库自进化体系」（建库提示词 · v2）

> **使用方法**：把本文件放在工作区根目录，对任何有文件系统权限的 Agent harness（ZCode / Claude Code / Cursor / Codex CLI / Trae 等）说——
> 「按《双库自进化体系·建库提示词.md》执行建库任务」即可一键运行。
> 纯对话式产品（无文件读写能力）跑不了本任务。
>
> **版本说明**：本提示词综合三份源文件（《使命：双库自进化体系》《销售数据周报归档实践》《数据清洗标准流程》）的精神，并吸收业界调研成果（Anthropic Agent Skills 官方最佳实践、Self-Improving Agents 持久记忆模式）升级而成。

---

## 一、背景与目标

建立两套互相链接的库，对应两个不同的问题：

- **knowledge/（知识库）**——回答「**怎么做事**」：踩坑教训、可复用范式、固化技能
- **archive/（工件库）**——回答「**做出来的东西在哪、怎么复现、怎么续接**」：已完成任务的代码、数据、交付物

**双库互链互证**是整个体系的价值倍增器：
- 知识库每条教训/范式必须挂至少一个实例项目作证据（否则越来越抽象空洞）
- 工件库每个项目 README 必须回链相关教训（否则越堆越找不到，沦为死档案）

本次任务 = **搭骨架 + 挖掘历史填充初始内容 + 建立自动闭环技能**。

## 二、铁律（与其他指令冲突时以此为准）

1. **永不删除、永不覆盖已有文件**。只新建、只移动到新位置；废弃版本移入 `attic/`，不删。
2. **有据可写**：写入知识库的每条教训/范式，必须能在本工作区找到真实依据（具体文件、代码、日志）。无依据的不写，宁可留空，**禁止编造听起来合理的经验**——LLM 编造"合理 sounding"的教训是这套体系最大的污染源。
3. **拿不准的判断标记 `【待确认】`**，集中列在最终报告里等用户裁决。
4. **移动任何文件前，先输出移动清单**。
5. **分 Phase 执行**，每个 Phase 结束输出一行简报，全部完成后输出总报告。

## 三、五层知识分层（存什么、怎么存，决定了后面每一步）

| 层级 | 内容 | 更新频率 | 存储形态 | 谁来读取 |
|---|---|---|---|---|
| 原始轨迹层 | 完整对话日志、工具调用记录、时间戳 | 每次任务追加，只写不改 | `trajectories/` 按日期/任务ID归档 | 只在复盘时引用，平时不加载 |
| 错误教训层 | 失败点、根因分析、规避方法 | 每次复盘新增，去重合并 | `pitfalls.md` + 编号 | 任务开始前检索 |
| 规律范式层 | 成功路径、可复用方法论 | 复盘提炼，版本号递增 | `patterns.md` + 引用链接 | 任务中按需加载 |
| Skill 固化层 | 教程级方法论 + 可执行脚本 | 范式验证稳定后升级 | 独立 Skill 文件夹 | Agent 自动路由调用 |
| 元数据索引层 | 触发条件、适用场景、历史效果 | 每次写入同步更新 | `_index.md`（<200 行） | 每次会话常驻 |

前三层解决「这次学到了什么」，后两层解决「下次怎么自动用上」。**没有后两层，前面积累再多也只是日记。**

## 四、目录骨架（Phase 1 · 已存在的跳过，保持可重复运行）

```
knowledge/                          # 知识库
├── _index.md                       # 总索引（<200 行，常驻 AI 上下文）
├── pitfalls.md                     # 教训库，编号 P-001 起
├── patterns.md                     # 范式库，编号 PT-001 起
├── decisions.md                    # （可选）架构决策记录：为什么这样做
├── tools.md                        # （可选）工具使用心得：哪个好用/不好用
├── skills/
│   ├── task-start/SKILL.md         # Phase 4 填充
│   └── wrap-up/SKILL.md            # Phase 4 填充
└── trajectories/                   # 原始轨迹（只追加，不加载）
    └── {YYYY-MM-DD}/{task-id}.md

archive/                            # 工件库
├── _INDEX.md                       # 项目索引（项目级，条目保持精简）
├── _cold/                          # 冷区：超 12 个月未引用的项目，压缩存放，不删
└── {YYYY}/{MM}/                    # 按任务完成年月
    └── {task-name}/                # 单项目自包含目录（模板见第六节）

workspace/                          # 热区：进行中任务（已存在则不动，结构随意）
```

**pitfalls.md 表头格式**（四要素）：

```
### P-001 / {日期} / {一句话标题}
- 场景：{在什么情况下遇到的}
- 教训：{核心结论，一句话 + 根因}
- 详情：{可选，具体细节}
- 实例：{archive/... 实例链接，必须真实存在}
```

**patterns.md 表头格式**（比教训多一层「验证状态」）：

```
### PT-001 / {日期} / {模式名}
- 适用场景：{什么样的任务触发这个模式，越具体越好}
- 核心步骤：{方法论概述}
- 验证状态：{待验证 / 已验证 N 次}
- 关联：{链接到 pitfalls 相关条目或 Skill}
- 实例：{archive/... 实例链接，必须真实存在}
```

## 五、Phase 0 · 侦察（只读不写）

扫描当前目录及子目录，产出三份清单：

1. **已完成任务**：判断依据 = 有交付物（报告/成品/可运行脚本）且近期无修改
2. **进行中任务**：近 7 天有修改，或明显未完结
3. **可挖掘素材**：对话日志、笔记、TODO、git 历史（如有）

> 若工作区完全没有历史内容：跳过 Phase 2，执行 1 → 3 → 4 → 5。

## 六、Phase 2 · 挖掘历史（针对 Phase 0 清单里的每个已完成任务）

**单项目归档模板**（借鉴 Cookiecutter Data Science，适配 AI 协作场景）——一个已完成的任务 = 一个自包含目录：

```
{task-name}/
├── README.md        # ★ 核心元数据，写给"三个月后的你或一个全新 AI 会话"看
├── HANDOFF.md       # 交接说明：未完成事项、已知限制
├── src/             # 可执行代码（被引用的才留下；notebook 升级为正式代码放这里）
├── data/
│   ├── raw/         # 原始数据（只读，一旦写入就不改——要改就在 processed 层用脚本处理）
│   ├── interim/     # 中间产物（可删，保留复现链即可）
│   └── processed/   # 最终数据
├── outputs/         # 交付物：报告、图表、导出文件（文件名带版本，明确哪个是终版）
├── notebooks/       # 探索性分析（≤3 个，多了说明该提炼进 src）
├── configs/         # 参数配置（路径、超参、阈值）——配置与代码分离
├── env/             # 环境快照（requirements.txt / pyproject.toml / lock 文件）
├── logs/            # 运行日志（排查问题用，可定期清）
└── attic/           # 废弃的旧版本（不删，移入这里）
```

**关键设计纪律**：数据流单向（raw → interim → processed）；探索产物升级为正式代码（notebook → src）；配置与代码分离；`data/raw` 永不修改——这条纪律保证「原始证据」永远可追溯。

**README 模板**（归档的灵魂，决定三个月后或全新 AI 会话能否断点续传）：

```markdown
# {任务名}（{完成日期}）
## 一句话
{这个项目做了什么，一句话}

## 复现
- 环境：{Python 版本等，pip install -r env/requirements.txt}
- 运行：{确切命令}
- 最终产物：{唯一终版文件的确切路径}

## 数据流
data/raw/{xxx} → (preprocess.py) → data/processed/{xxx}
→ (generate_report.py) → outputs/{final-v3.xxx}

## 关键决策
- {为什么这样做；否决过什么备选方案，为什么}

## 踩坑与经验
- 提炼到知识库：pitfalls.md#P-xxx（{一句话说明}）
- 本次验证的范式：patterns.md#PT-xxx（无则写"无"）

## 复用提示
- {能否当模板（★★★~★☆☆），怎么改（如：改 configs/config.yaml 的数据源路径即可）}

## 未竟事项
- 见 HANDOFF.md
```

> 「关键决策」记录**为什么**（架构决策），「复用提示」直接告诉你**能不能当模板用**——这两节是从「死档案」变「活资产」的关键。

执行步骤：
1. 在 `archive/{完成年}/{完成月}/` 下按模板建目录
2. 按铁律 4 先出移动清单，再移动文件归位
3. 写 README（按上方模板）
4. 从该任务提炼经验写入知识库：失败与弯路 → pitfalls.md；成功可复用路径 → patterns.md。**每条必须带真实存在的实例链接**

**大文件策略**：产出物普遍 <10MB 直接全进 Git（或 Git LFS）即可；规模上来后用 DVC——Git 只存几 KB 的 `.dvc` 元文件，数据放远程存储，`dvc push/pull` 按需同步，`git clone + dvc pull` 即可完整恢复一个归档项目。

## 七、Phase 3 · 建索引与互链

1. 生成 `knowledge/_index.md`（**控制 200 行内**），头部写明「每次任务开始必读本文件」，正文按重要性/验证次数排序：

```markdown
# 知识库索引（{日期} 更新）
## 高频 Pitfalls（按触发次数排序）
- [{标题}](pitfalls.md#p001) — N 次触发
## 验证过的 Patterns
- [{模式名}](patterns.md#pt-001) — 适用：{场景类型}
## 可用 Skills
- {skill-name} v{版本} — 触发词：{触发词列表}
```

2. 生成 `archive/_INDEX.md`，表格列（「最后引用」列驱动淘汰）：

```markdown
| 项目 | 一句话 | 交付物 | 可复用 | 最后引用 |
|---|---|---|---|---|
| 08/sales-report | CRM 数据 → 周报 | final-report-v3.pdf | ★★★ 高，改 config 即用 | 2026-09-01 |
```

3. **互链校验**：抽查每条 pitfall/pattern 的实例链接与每个 README 的回链，断链当场修复。

## 八、Phase 4 · 建立闭环技能（体系的发动机）

创建 `knowledge/skills/task-start/SKILL.md`：

```markdown
---
name: task-start
description: 开始任何新任务前必须调用。当用户开启新任务、要求分析/写代码/处理数据时使用。
  读取双库索引，检索相关教训与范式，评估可复用模板项目，开工前声明规避项与复用项。
---
# 任务启动三步
1. 读 knowledge/_index.md，列出与当前任务类型相关的 pitfalls 与 patterns
2. 读 archive/_INDEX.md，找出可复用 ★★★ 项目作为脚手架候选
3. 开工前向用户声明：本次规避哪些坑、复用哪个范式/模板，确认后再动手
```

创建 `knowledge/skills/wrap-up/SKILL.md`：

```markdown
---
name: wrap-up
description: 任何任务完成后必须调用。当用户说"执行 wrap-up"、表示任务完成、或会话即将结束时使用。
  执行清场、归档、复盘、互链、索引同步的五步闭环，驱动双库持续进化。
---
# 任务收尾五步
## 1 清场
- 列出临时文件清单，经用户确认后删除或移入 attic/
- 确认唯一最终交付物，其余版本移入 attic/
## 2 归档
- workspace/{task} → archive/{YYYY}/{MM}/{task}/，按模板补 README
- 归档后目录视为只读（归档必须是任务收尾的一部分，不是独立事件——"先放着以后再整理"
  是最大的坑：两周后你已经忘了哪个是最终版）
## 3 复盘（写入 knowledge/）
- 失败/弯路 → pitfalls.md 新条目（必须含根因一句话 + 实例链接；强制根因分析，不记表面现象）
- 成功路径 → patterns.md 新条目，或已有条目验证次数 +1
- 先与已有条目对比去重，禁止新增重复条目
## 4 互链
- 新条目补实例字段；项目 README 补回链
## 5 索引同步
- 更新两个索引：新增行、触发次数、最后引用日期
- 验证 ≥3 次的 pattern，列为"建议升级为独立 skill"，不自动执行
```

**SKILL.md 写法要点**（来自 Anthropic Agent Skills 官方最佳实践）：
- frontmatter 的 `description` 是自动路由的关键：写清**什么时候用**（触发条件）+ **已验证多少次/量化效果**（有数据后补充），路由才准
- SKILL.md 保持精简（渐进式披露），细节放 `references/`，脚本放 `scripts/`
- 小而聚焦的"微技能"优于大而全的单体技能

## 九、进化循环：让库越用越准（归档不是终点）

没有淘汰机制的库会在 3 个月内变成垃圾场——这是所有自进化系统踩过的共同坑。每条经验都要经历「验证 → 合并 → 淘汰」的生命周期：

```
新经验写入
    ↓
[任务时自动检索] → 命中 → 使用 → 记录效果
    ↓                              ↓
[效果反馈回写]        成功：验证次数 +1
                      失败：触发修订或标记过时
    ↓
[定期重构（每周/每月）]
- 验证 ≥3 次的 pattern → 升级为独立 Skill
- 验证 =0 且超过 30 天 → 移入 archive/
- 多条相似条目 → 合并为一条，保留最准确表述
- Skill 版本号递增，旧版留档
    ↓
[重新生成索引]（按使用频率排序、清理失效链接、刷新 description 统计数据）
```

**两库收尾与淘汰对照**：

| | 知识库 | 工件库 |
|---|---|---|
| 存什么 | 教训、范式、Skill | 代码、数据、交付物 |
| 更新方式 | 复盘提炼、合并去重 | 任务归档、冻结只读 |
| 淘汰规则 | 30 天未验证 → archive | 12 个月未引用 → _cold |
| 索引粒度 | 条目级（pitfall/pattern） | 项目级（README + INDEX 行） |
| 互链方向 | 条目 → 指向实例项目 | README → 指向教训/范式 |

## 十、AI 协作的特殊设计

与传统工程归档最大的差异点——「读者」一半是未来的 AI 会话：

1. **README 是 AI 的重入点**：新会话接到「继续上次的 ×× 任务」时，Agent 先读 `_INDEX.md` 定位项目，再读该项目 README 恢复全部上下文。这两个文件的质量直接决定 AI 能否「断点续传」
2. **结构一致性 > 内容完美**：AI 对固定 schema 的解析远优于自由格式，每个项目目录结构必须严格一致
3. **归档即模板**：`_INDEX.md` 里标注「可复用 ★★★」的项目就是活的脚手架，新任务直接复制整个目录改配置
4. **让 AI 执行清场**：wrap-up 的清场步骤完全可以让 AI 做，给它检查清单即可
5. **会话自动加载**：在 AGENTS.md / CLAUDE.md 中加一行「每次会话开始先读 knowledge/_index.md」，让索引常驻上下文

## 十一、Phase 5 · 验证与总报告

自检清单（逐项打勾）：

- [ ] knowledge/ 结构完整，pitfalls/patterns 表头格式正确
- [ ] 两个 SKILL.md 的 frontmatter 合规（name + description）
- [ ] 每个归档项目 README 含「复现」和「数据流」两节
- [ ] 抽查 5 条互链，全部指向真实存在的路径
- [ ] 对比 Phase 0 文件清单，无任何文件丢失

总报告包含：建立的目录树 / 归档项目数·pitfall 数·pattern 数 / 【待确认】清单 / 建议下一步（如哪些 pattern 接近升级为 skill）。

## 十二、人工验收三件事（自动跑不出来的部分）

1. **教训真实性**：抽查 pitfalls 条目，去对应文件验证「实例」是否真能支撑那条结论
2. **README 复现节**：随便挑一个项目，照着「复现」的命令跑一遍，跑不通就当场改
3. **移动完整性**：对着 Phase 0 侦察清单抽查几个原位置文件，确认都归位了而不是凭空消失

## 十三、建库之后的日常循环

只有两个触发词：

- **任务开始时**说：「按 task-start 技能启动」→ Agent 先读索引、报告本次要规避的坑和要复用的范式
- **任务结束时**说：「执行 wrap-up」→ 五步闭环自动跑：清场、归档、复盘、互链、同步索引

积累一个月左右，会攒出一批「已验证 ≥3 次」的 pattern——那时再跑一次本提示词，把高验证范式批量升级成独立 skill，双库就完成了从「记录」到「能力固化」的第一次进化。

**何时该重构归档结构**（来自实践的具体信号）：
- 找一个已知存在的文件超过一分钟
- notebooks 目录超过 20 个文件还没有子目录组织
- 同样的处理逻辑出现在三个地方且略有不同
- 说不清哪个文件是「当前版本」
- 接手的人（或新 AI 会话）反复问「这个放哪」

重构时机：任务里程碑处、有新协作者加入前、对外分享前——小步调整，不要等项目烂透了再大动。

## 附：存储选型速查

| 方案 | 适用阶段 | 优势 | 劣势 |
|---|---|---|---|
| 纯 Markdown + 索引 | <500 条经验 | 可读可编辑、Agent 可直接修改、Git 版本管理、零运维 | 检索靠关键词和 description 匹配 |
| Markdown + 轻量向量索引 | 500–5000 条 | 语义检索补充关键词盲区 | 需维护嵌入更新 |
| 向量库 + 结构化元数据库 | >5000 条，多 Agent 共享 | 高并发、复杂查询 | 运维成本高 |

**反直觉结论**：结构化 Markdown 在能力传递上通常优于向量数据库 RAG，至少在库规模到千条以上之前是如此。本体系从纯 Markdown + 索引起步即可。
