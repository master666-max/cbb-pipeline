# v3.3-2 工单 —— 建库全程质量监测发现（方法论与运行态）

> 来源：任务 2 的全称质量监测——对「库调试v3.2」建库/迁移/冒烟全程的运行态监测（区别于 v3.3-1 的逐条缺陷，本单记录**监测框架本身的表现与运行态风险**）。

---

### M-01 监测框架有效性自证：三层断言全部命中过真问题
- 守恒断言（条目数=源数）→ 抓出 PT-006 空洞疑点（后判明为源库空洞，监测无罪）；
- 逐条 schema 校验（走真实 engine append）→ 抓出 W1 Path 崩溃；
- 冒烟矩阵（wrapup/retire/重装校验/guard/根对账）→ 抓出 W2/W4/W5 三个语义 bug。
- 结论：**「迁移必须真实走 schema 校验 + 冒烟必须跑全命令面」是有效的监测配方**，v3.3 起固化为 install 后置检查清单（随包渲染）。

### M-02 运行态风险：反思触发阈值在迁移场景即达到（228 ≥ 50）
- 现场：42 条迁入条目 importance 总和 228，首次 wrapup 即触发反思提示。
- 分析：阈值 50 对「批量导入」场景过低——trigger 是为「日常增量」设计的，迁移/批量 append 一次性越线属预期但提示无差别。
- 修复方向：importance_accum 记录来源（批量/日常），批量导入后建议阈值临时上浮或触发提示标注「批量导入累积」；属调优项非缺陷。

### M-03 运行态观察：wrapup 与根快照的时序耦合
- retire 在 wrapup 之后追加审计行导致根漂移（W5 的运行态表现）。建议的修复（写操作后刷新根）会让 changes.jsonl 的每次 append 都伴随根更新——须评估高频 append 的性能（Merkle 全树重算 O(n)）；条目数百规模内可接受，登记规模触发器。

### M-04 会话入口切换的滞后效应（C-000 教训的活例）
- 本会话自始至终运行在旧工作区语境（根 AGENTS.md v4 版）；新库 AGENTS.md（v3 渲染版）对 harness 的实际影响要到**下一个会话**才显形。监测结论：**「库建成」与「库被采用」是两个事件**——下一个会话开始时应显式走新入口三级加载，并把偏离记录进 v3.3-2 续篇。

### M-05 审计面与账本面的分工验证通过
- audit（lifelog 哈希链）46 行 = 事件真相源；ledger/changes.jsonl 46 动作 = 变更账本；两者条数一致、动作齐全（install/charter-confirmed/42×append/wrapup/retire）。双平面（公理 D）首次在真实建库中运行，无分叉。

### M-06 质量监测的负空间（本轮没测到的）
- 未测：并发写（单用户假设，登记边界）；大条目（>1MB content）append；中断恢复（append 半途崩溃的链状态）；citations.md 与 REGISTRY 的漂移（渲染产物手改检测）。→ 全部进 v3.3 统合工单的测试扩展清单。
