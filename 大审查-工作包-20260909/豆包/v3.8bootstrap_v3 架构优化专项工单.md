### 1.2 核心架构问题

| # | 问题 | 表现 | 影响 |
|---|------|------|------|
| A1 | **无存储抽象** | 所有函数直接操作 `Path`、`read_text`、`write_bytes` | 无法替换存储后端、无法 mock 测试、无法支持 SQLite/远程存储 |
| A2 | **无事务保证** | append 涉及 4 个文件写入（memory+audit+ledger+state），中途崩溃则不一致 | 崩溃后数据不一致，doctor 只能检测无法自动修复 |
| A3 | **写操作紧耦合** | append/wrapup/retire 各自复制粘贴 audit+ledger+root 刷新逻辑 | 新增写操作容易遗漏刷根，逻辑重复，修改需改 N 处 |
| A4 | **无扩展点** | 引擎操作硬编码在 if-elif 中，渲染器硬编码 8 个，守卫规则硬编码 | 新增功能必须修改核心文件，无法通过插件扩展 |
| A5 | **错误处理混乱** | 混用 sys.exit / assert / raise SystemExit / 裸 except / 静默 pass | 错误不可捕获、不可恢复、测试难以模拟错误场景 |
| A6 | **配置硬编码** | TUNABLES 是代码中的 dict，无法外部覆盖、无法校验、无版本 | 调参需改代码发版，不同环境无法使用不同配置 |
| A7 | **无依赖注入** | 函数直接引用全局 DATA_DIR、时间函数、urllib | 测试需 monkey-patch 全局状态，已发生 test pollution |
| A8 | **读写共享模型** | retrieve 和 append 操作同一组 JSON 文件，无读优化、无缓存 | 检索性能差，无法为读路径建专门索引 |
| A9 | **无版本化迁移框架** | v2→v3 迁移是一次性硬编码脚本，schema 变更无通用机制 | v3→v4 迁移需重新写一套，无法复用 |
| A10 | **无可观测性** | 只有 print，无结构化日志、无 metrics、无操作耗时统计 | 生产环境无法排查性能问题，无法监控库健康状态 |

### ARCH-01：存储抽象层（Storage Abstraction Layer）

| 字段 | 内容 |
|------|------|
| **优先级** | P0 |
| **预估工时** | 4-6 人天 |
| **依赖** | 无（可独立启动） |

#### 问题诊断

当前所有函数直接操作文件系统：
- `merkle_root()` 直接 `root.rglob("*")` + `p.read_bytes()`
- `_rank_entries()` 直接 `(lib/"memory").rglob("*.json")` + `json.loads(f.read_text())`
- `cmd_engine("append")` 直接 `dest.write_text(...)`
- `chain_append()` 直接 `f.open("a")`

这导致：
1. 无法替换存储后端（如 SQLite、LevelDB、远程对象存储）
2. 测试无法使用内存存储，必须操作真实文件系统（慢且易污染）
3. 无法添加缓存层（所有读都直接读磁盘）
4. 路径逻辑散落在各处，修改目录结构需改 N 处

#### 架构方案

定义 `Storage` 抽象基类，封装所有持久化操作：

```python
from abc import ABC, abstractmethod
from typing import Optional, Iterator

class EntryStorage(ABC):
    """条目存储抽象：支持按 id 读写、按目录遍历、范围查询"""
    @abstractmethod
    def get(self, entry_id: str) -> Optional[dict]: ...
    @abstractmethod
    def put(self, entry_id: str, entry: dict, tier: str = "intermediate") -> None: ...
    @abstractmethod
    def exists(self, entry_id: str) -> bool: ...
    @abstractmethod
    def iter_all(self, include_attic: bool = False) -> Iterator[tuple[str, dict]]: ...
    @abstractmethod
    def move_to_attic(self, entry_id: str) -> None: ...
    @abstractmethod
    def list_ids(self, tier: Optional[str] = None) -> list[str]: ...

class AuditStorage(ABC):
    """审计链存储抽象：追加行、读取尾哈希、遍历验证"""
    @abstractmethod
    def append(self, text: str, prev_override: Optional[str] = None) -> str: ...
    @abstractmethod
    def tail_hash(self) -> Optional[str]: ...
    @abstractmethod
    def iter_lines(self) -> Iterator[tuple[int, str]]: ...

class LedgerStorage(ABC):
    """变更账本存储抽象"""
    @abstractmethod
    def append(self, action: str, detail: str) -> None: ...
    @abstractmethod
    def iter_recent(self, n: int = 30) -> Iterator[dict]: ...

class StateStorage(ABC):
    """库状态存储抽象（state.json）"""
    @abstractmethod
    def load(self) -> dict: ...
    @abstractmethod
    def save(self, state: dict) -> None: ...

class LibraryStorage:
    """聚合根：持有各子存储引用 + 事务上下文"""
    def __init__(self, entries: EntryStorage, audit: AuditStorage,
                 ledger: LedgerStorage, state: StateStorage):
        self.entries = entries
        self.audit = audit
        self.ledger = ledger
        self.state = state
```

**实现类**：
- `FileSystemEntryStorage`：当前的 JSON 文件实现
- `FileSystemAuditStorage`：当前的 lifelog-*.md 实现
- `InMemoryEntryStorage`：测试用，dict 实现
- `SQLiteEntryStorage`（未来）：高性能实现

#### 实施步骤

1. **第 1 天**：定义抽象接口，编写接口契约测试（用 InMemory 实现验证接口语义）
2. **第 2-3 天**：实现 `FileSystem*` 适配器，将现有文件操作迁移到适配器中
3. **第 4 天**：实现 `InMemory*` 适配器，改造 5-10 个核心测试使用内存存储
4. **第 5-6 天**：全量迁移，所有函数通过 `LibraryStorage` 接口操作，消除直接文件操作
5. **验证**：现有 40+ 测试全部通过；新增存储后端切换测试

#### 预期收益

- 测试速度提升 5-10 倍（内存存储 vs 文件系统）
- 为 SQLite/远程存储等高性能后端铺路
- 缓存层可以作为装饰器添加到存储接口上
- 路径逻辑集中，修改目录结构只需改适配器

#### 风险与权衡

- **风险**：迁移过程中可能引入行为差异（如文件权限、编码、换行符）
- **缓解**：保留 FileSystem 实现的行为与现有代码完全一致；用现有测试作为回归基准
- **权衡**：抽象层增加一层间接调用，性能损耗约 1-3%，可接受

### ARCH-02：事务与一致性模型（Write-Ahead Log + 补偿事务）

| 字段 | 内容 |
|------|------|
| **优先级** | P0 |
| **预估工时** | 3-5 人天 |
| **依赖** | ARCH-01（存储抽象层） |

#### 问题诊断

一次 `engine append` 操作涉及 4 个独立文件写入：
1. `memory/intermediate/<id>.json` — 条目文件
2. `audit/lifelog-YYYY-MM.md` — 审计链追加
3. `ledger/changes.jsonl` — 账本追加
4. `state.json` — 更新 importance_accum + merkle_root

如果在第 2 步和第 3 步之间进程崩溃（断电、OOM、Ctrl+C），系统处于不一致状态：
- 条目文件存在，但审计链无记录 → `doctor` 报 "memory有而audit无"
- merkle_root 未更新 → `doctor` 报 "state 根不一致"

当前 `doctor` 只能**检测**不一致，无法**自动修复**。用户需要手动裁决，且没有操作日志指导修复。

更严重的是，`state.json` 的写入不是原子的——`write_text` 会先截断文件再写入，如果中途崩溃，`state.json` 可能是半写的损坏文件，导致整个库无法加载。

#### 架构方案

**1. 预写日志（Write-Ahead Log, WAL）**

```
操作开始 → 写 WAL（记录操作类型+参数+预期状态）→ 执行各步写入 → 标记 WAL 为 committed → 完成
```

启动时检查 WAL：
- 存在未 committed 的 WAL → 执行补偿回滚或前向重做
- 存在 committed 但未清理的 WAL → 清理

**2. 原子文件写入**

所有文件写入采用"写临时文件 + rename"模式：
```python
def atomic_write(path: Path, data: bytes):
    tmp = path.with_suffix(path.suffix + ".tmp")
    tmp.write_bytes(data)
    os.replace(tmp, path)  # 原子操作（POSIX 保证）
```

**3. 补偿事务框架**

每个写操作定义 `execute()` 和 `compensate()`：
```python
@dataclass
class AppendOperation:
    entry_id: str
    entry: dict
    def execute(self, storage: LibraryStorage) -> None:
        storage.entries.put(...)
        storage.audit.append(...)
        storage.ledger.append(...)
        state = storage.state.load()
        state["importance_accum"] += ...
        state["merkle_root"] = compute_root(storage)
        storage.state.save(state)
    def compensate(self, storage: LibraryStorage) -> None:
        # 回滚：删除条目、追加补偿审计记录、回滚 state
        storage.entries.move_to_attic(self.entry_id)
        storage.audit.append(f"COMPENSATE: append {self.entry_id} rolled back")
        ...
```

**4. 一致性检查与自动修复**

`doctor` 增强为：检测 → 分类 → 建议修复 → （授权后）自动执行补偿修复。

#### 实施步骤

1. **第 1 天**：实现 `atomic_write` 工具函数，迁移所有关键文件写入
2. **第 2 天**：实现 WAL 机制（`library/.wal.jsonl`），写操作前后写 WAL
3. **第 3 天**：实现启动时 WAL 恢复逻辑（未 committed → 补偿回滚）
4. **第 4 天**：定义 `Operation` 基类和补偿事务框架，迁移 append 操作
5. **第 5 天**：迁移 wrapup/retire/reflect-done 操作；增强 doctor 自动修复建议
6. **验证**：崩溃测试（在操作各步骤 kill -9 进程，重启后验证一致性）

#### 预期收益

- 崩溃后数据一致性有保证，不再需要人工裁决
- `state.json` 不会半写损坏
- 操作可追溯、可回滚，为"撤销"功能铺路
- `doctor` 从"只报告"升级为"可修复"

#### 风险与权衡

- **风险**：WAL 本身可能损坏；补偿事务可能执行失败
- **缓解**：WAL 采用 append-only + 校验和；补偿失败时升级为人工裁决并保留详细日志
- **权衡**：每次写操作增加一次 WAL 写入（约 1ms），性能损耗可接受
- **注意**：WAL 本身也需要纳入 Merkle 根计算，否则可能被篡改

### ARCH-03：事件驱动架构 + 写操作管道（Event-Driven Write Pipeline）

| 字段 | 内容 |
|------|------|
| **优先级** | P1 |
| **预估工时** | 3-4 人天 |
| **依赖** | ARCH-01（存储抽象层） |

#### 问题诊断

当前写操作（append/wrapup/retire/reflect-done）的模式是复制粘贴：

```python
# append（第 933-941 行）
(dest / f"{e['id']}.json").write_text(...)
h = chain_append(lib / "audit", f"entry:{e['id']} → ...")
_ledger_append(lib, "append", f"entry={e['id']} → ...")
st = json.loads(st_path.read_text(...))
st["importance_accum"] = ...
st["merkle_root"] = merkle_root(...)
st_path.write_text(...)

# wrapup（第 978-981 行）
chain_append(lib / "audit", f"wrap-up emotion={emo}...")
_ledger_append(lib, "wrapup", f"emotion={emo}")
s["merkle_root"] = merkle_root(...)
st.write_text(...)

# retire（第 1087-1093 行）
chain_append(lib / "audit", f"retire: {len(moved)} 条...")
_ledger_append(lib, "retire", f"moved={len(moved)}...")
st["merkle_root"] = merkle_root(...)
st_path.write_text(...)
```

问题：
1. **逻辑重复**：audit + ledger + root 刷新在 4 处复制粘贴
2. **顺序不一致**：append 是"写条目→audit→ledger→root"，wrapup 是"audit→ledger→root"，retire 是"移动文件→audit→ledger→root"——没有统一的管道
3. **新增操作易遗漏**：如果未来新增一种写操作，开发者可能忘记刷 root（事实上 `reflect` 操作就没有刷 root，因为它是"取材"不是"写"，但边界模糊）
4. **无法插入中间件**：无法在写操作前统一加安全检查、性能监控、缓存失效等

#### 架构方案

**事件驱动的写操作管道**：

```python
class WriteEvent:
    """写操作事件：记录操作类型、参数、结果"""
    action: str
    params: dict
    timestamp: str
    entry_id: Optional[str]
    audit_text: str
    ledger_detail: str
    state_updates: dict  # 需要更新的 state 字段

class WritePipeline:
    """写操作管道：按顺序执行各阶段，每阶段可插拔"""
    def __init__(self, storage: LibraryStorage):
        self.storage = storage
        self.before_hooks = []   # 写前钩子：安全检查、校验
        self.after_hooks = []    # 写后钩子：缓存失效、通知
        self.audit_logger = AuditLogger(storage.audit)
        self.ledger_logger = LedgerLogger(storage.ledger)
        self.root_manager = RootManager(storage)

    def execute(self, event: WriteEvent) -> WriteResult:
        # 阶段 1：写前钩子（安全检查、schema 校验、密钥扫描）
        for hook in self.before_hooks:
            hook.before_write(event)

        # 阶段 2：执行核心写操作（由具体操作提供）
        result = event.execute(self.storage)

        # 阶段 3：写审计链（统一）
        self.audit_logger.append(event.audit_text)

        # 阶段 4：写账本（统一）
        self.ledger_logger.append(event.action, event.ledger_detail)

        # 阶段 5：更新 state（统一，含 root 刷新）
        self.root_manager.update_state(event.state_updates)

        # 阶段 6：写后钩子（缓存失效、metrics）
        for hook in self.after_hooks:
            hook.after_write(event, result)

        return result
```

**具体操作只需定义核心逻辑和事件参数**：

```python
class AppendEvent(WriteEvent):
    action = "append"
    def execute(self, storage):
        storage.entries.put(self.entry_id, self.entry, self.tier)
        return WriteResult(entry_id=self.entry_id)
    @property
    def audit_text(self): return f"entry:{self.entry_id} → {self.tier}"
    @property
    def ledger_detail(self): return f"entry={self.entry_id} → {self.tier}"
    @property
    def state_updates(self):
        return {"importance_accum_add": self.entry["importance"]}
```

#### 实施步骤

1. **第 1 天**：定义 `WriteEvent` / `WritePipeline` / `WriteResult` 基类和接口
2. **第 2 天**：实现管道的统一阶段（audit/ledger/state/root），迁移 `append` 操作
3. **第 3 天**：迁移 `wrapup` / `retire` / `reflect-done` 操作
4. **第 4 天**：实现钩子机制（安全检查钩子、metrics 钩子），将密钥扫描/schema 校验迁移为钩子
5. **验证**：现有测试通过；新增管道顺序测试（验证 audit→ledger→root 顺序）；新增钩子测试

#### 预期收益

- 消除 4 处复制粘贴的 audit+ledger+root 逻辑
- 新增写操作只需定义核心逻辑，管道自动处理审计/账本/刷根
- 安全检查（密钥扫描、schema 校验）作为钩子统一执行，不会遗漏
- 可插入性能监控、缓存失效等横切关注点
- 为异步写操作（后台刷根）铺路

#### 风险与权衡

- **风险**：管道抽象可能过度设计，简单操作也需走完整管道
- **缓解**：提供 `SimpleWriteEvent` 便捷基类；管道阶段可跳过（如 shadow 操作不刷 root）
- **权衡**：增加一层间接调用，性能损耗 < 1%

### ARCH-04：插件化扩展点（Plugin System）

| 字段 | 内容 |
|------|------|
| **优先级** | P1 |
| **预估工时** | 4-6 人天 |
| **依赖** | ARCH-03（写操作管道） |

#### 问题诊断

当前所有功能硬编码在核心文件中：
- **引擎操作**：9 种操作硬编码在 `cmd_engine` 的 if-elif 链中，新增操作需修改核心函数

```python
class PluginRegistry:
    def __init__(self):
        self.engine_ops = {}      # name → EnginePlugin
        self.renderers = {}       # name → RendererPlugin
        self.guards = []          # GuardPlugin 列表
        self.retrievers = {}      # name → RetrieverPlugin

    def register_engine_op(self, plugin: EnginePlugin): ...
    def register_renderer(self, plugin: RendererPlugin): ...
    def register_guard(self, plugin: GuardPlugin): ...
    def register_retriever(self, plugin: RetrieverPlugin): ...

    def discover(self):
        """通过 setuptools entry_points 自动发现第三方插件"""
        try:
            from importlib.metadata import entry_points
            for ep in entry_points(group="bootstrap_v3.plugins"):
                plugin_cls = ep.load()
                self.register(plugin_cls())
        except Exception:
            pass  # 无 entry_points 时静默跳过
```

### ARCH-05：命令查询职责分离（CQRS）+ 检索引擎抽象

| 字段 | 内容 |
|------|------|
| **优先级** | P1 |
| **预估工时** | 4-6 人天 |
| **依赖** | ARCH-01（存储抽象层）、ARCH-04（插件系统） |

#### 问题诊断

当前读写共享同一数据模型和存储：
- **写路径**（append/retire/wrapup）：直接写 JSON 文件，更新 state.json
- **读路径**（retrieve/eval/doctor）：全量扫描所有 JSON 文件，`json.loads`，内存中打分排序

问题：
1. **读路径无优化**：每次 retrieve 都全量扫描+全量解析，无索引、无缓存
2. **读写竞争**：写操作修改文件时，读操作可能读到半写文件（虽然 JSON 写入通常原子，但跨文件一致性无保证）
3. **检索算法硬编码**：`_rank_entries` 中的打分公式（keywords×3 + content×1 + importance - 0.1×age + links扩散）无法替换或调优
4. **eval 和 retrieve 重复扫描**：eval 对每个 query 都调用一次 `_rank_entries`，N 个 query 就是 N 次全库扫描
5. **无法支持高级检索**：如布尔查询、短语查询、字段加权查询、语义检索（向量）

#### 架构方案

**CQRS 分离**：

```
                    ┌─────────────────────┐
                    │   写模型 (Write)     │
                    │  - EntryStorage      │
                    │  - AuditStorage      │
                    │  - LedgerStorage     │
                    │  - StateStorage      │
                    └──────────┬──────────┘
                               │ 写操作触发
                               ▼
                    ┌─────────────────────┐
                    │  索引构建器 (Indexer) │
                    │  - 监听写事件         │
                    │  - 增量更新倒排索引    │
                    │  - 维护向量索引(可选)  │
                    └──────────┬──────────┘
                               │
                               ▼
                    ┌─────────────────────┐
                    │   读模型 (Read)      │
                    │  - 倒排索引 (InMemory)│
                    │  - 检索引擎 (可插拔)   │
                    │  - 结果缓存           │
                    └─────────────────────┘
```

**检索引擎抽象**：

**倒排索引实现**：

```python
class InvertedIndex:
    def __init__(self):
        self.index = defaultdict(list)   # token → [(entry_id, field, weight)]
        self.metadata = {}                # entry_id → {length, keywords, ...}

    def add_entry(self, entry: dict):
        tokens = self._tokenize(entry)  # 中文分词 + 英文分词
        for token, field, weight in tokens:
            self.index[token].append((entry["id"], field, weight))
        self.metadata[entry["id"]] = {"length": len(tokens)}

    def search(self, query: str, k: int = 5) -> list[tuple[str, float]]:
        query_tokens = self._tokenize_query(query)
        scores = defaultdict(float)
        for token in query_tokens:
            for entry_id, field, weight in self.index.get(token, []):
                # BM25 打分
                scores[entry_id] += self._bm25(token, entry_id, field, weight)
        return sorted(scores.items(), key=lambda x: -x[1])[:k]
```

**索引持久化与缓存**：
- 索引存储在 `memory/.index/` 目录（倒排索引序列化 + 元数据）
- 写操作时增量更新索引（通过 ARCH-03 的写后钩子）
- 启动时加载索引到内存，mtime 校验有效性
- 索引损坏时自动全量重建

#### 实施步骤

1. **第 1 天**：定义 `Retriever` 抽象接口和 `SearchResult`，实现 `InMemoryRetriever`（当前算法的封装，作为基线）
2. **第 2 天**：实现倒排索引 `InvertedIndex` + 中文分词（字符 bigram，无外部依赖）
3. **第 3 天**：实现 `LexicalRetriever`（BM25 排序），与基线算法对比评测
4. **第 4 天**：实现索引持久化（`memory/.index/`）和增量更新（写后钩子）
5. **第 5 天**：实现结果缓存（相同 query 复用结果，写操作失效缓存）
6. **第 6 天**：通过插件系统注册检索器，配置文件可切换；eval 命令优化为一次扫描多 query
7. **验证**：检索质量评测（golden 集上 recall@5/MRR 不低于基线）；性能评测（1000 条目 < 200ms）；索引重建测试

#### 预期收益

- 检索性能提升 10-50 倍（倒排索引 vs 全量扫描）
- eval 性能提升 N 倍（一次索引构建 vs N 次全量扫描）
- 可插拔检索算法（BM25/向量/混合），为语义检索铺路
- 结果缓存减少重复计算
- 检索可解释性（matched_fields + explanation）
- 为高级查询（布尔/短语/字段加权）铺路

#### 风险与权衡

- **风险**：倒排索引可能与基线算法排序结果不同，用户可能感知变化；索引维护增加写操作开销
- **缓解**：保留基线算法作为可选项；默认使用 BM25 但通过 golden 集验证质量不下降；写操作增量更新索引（O(词条数)，非全量）
- **权衡**：索引占用额外磁盘空间（约为原始数据的 20-30%）；内存占用增加（索引加载到内存）
- **注意**：索引文件必须纳入 Merkle 根计算，否则可能被篡改；索引损坏时必须能自动重建

**轻量级依赖注入容器**（不引入外部 DI 框架，保持简单）：

```python
from dataclasses import dataclass, field
from typing import Optional
from datetime import datetime

@dataclass
class Clock:
    """时间抽象：便于测试中 mock 时间"""
    def now(self) -> datetime: return datetime.now()
    def strftime(self, fmt: str) -> str: return time.strftime(fmt)
    def time(self) -> float: return time.time()

@dataclass
class HttpClient:
    """HTTP 客户端抽象：便于测试中 mock 网络"""
    timeout: int = 15
    def get(self, url: str, retries: int = 2, delay: float = 2.0) -> str: ...

@dataclass
class AppContext:
    """应用上下文：持有所有依赖，通过参数传递而非全局变量"""
    lib_path: Path
    storage: LibraryStorage
    config: Config
    clock: Clock = field(default_factory=Clock)
    http: HttpClient = field(default_factory=HttpClient)
    plugin_registry: Optional[PluginRegistry] = None
    logger: Optional[logging.Logger] = None

    @classmethod
    def create(cls, lib_path: Path, config: Optional[Config] = None) -> "AppContext":
        """工厂方法：根据配置构造所有依赖"""
        config = config or ConfigManager(lib_path).get_config()
        storage = FileSystemStorage(lib_path)  # 或根据 config.storage.backend 选择
        return cls(lib_path=lib_path, storage=storage, config=config)
```

**函数签名改造**：

### ARCH-08：版本化数据模型与通用迁移框架

| 字段 | 内容 |
|------|------|
| **优先级** | P2 |
| **预估工时** | 3-4 人天 |
| **依赖** | ARCH-01（存储抽象层） |

#### 问题诊断

当前数据模型版本化和迁移是一次性硬编码：

1. **schema v2 → v3 迁移**：`entry_normalize()`（第 249-258 行）是硬编码的八字段→十字段兼容回填，只处理了 keywords/links 两个新字段
2. **v2.x 库 → v3 迁移**：`cmd_migrate()`（第 1152-1174 行）是一次性脚本，只处理审计链续接和 state.json 创建，**不处理条目数据迁移**
3. **absorb-md v4 → v3 迁移**：`cmd_absorb_md()`（第 458-538 行）是另一个一次性脚本，硬编码 v4 Markdown 格式解析
4. **无版本号标记**：条目 JSON 中没有 `schema_version` 字段，无法判断条目是哪个版本的 schema
5. **无迁移框架**：每次 schema 变更都需要写一套新的迁移逻辑，无法复用

如果未来有 v3 → v4 schema 变更（如增加 `embedding` 字段、修改 `validity` 结构），需要：
- 写新的 normalize 函数
- 写新的 migrate 命令
- 处理所有存量条目的升级
- 保证向后兼容（旧代码读新条目不崩）

这是不可持续的。

```python
from abc import ABC, abstractmethod

class Migration(ABC):
    """迁移基类：从 from_version 升级到 to_version"""
    from_version: int
    to_version: int

    @abstractmethod
    def migrate_entry(self, entry: dict) -> dict:
        """迁移单条条目"""
        ...

    @abstractmethod
    def migrate_state(self, state: dict) -> dict:
        """迁移 state.json"""
        ...

    def migrate_library(self, storage: LibraryStorage) -> MigrationReport:
        """迁移整个库：遍历所有条目，调用 migrate_entry"""
        report = MigrationReport()
        for entry_id, entry in storage.entries.iter_all():
            try:
                new_entry = self.migrate_entry(entry)
                new_entry["schema_version"] = self.to_version
                storage.entries.put(entry_id, new_entry, tier=...)
                report.migrated += 1
            except Exception as e:
                report.failed.append((entry_id, str(e)))
        state = storage.state.load()
        state = self.migrate_state(state)
        state["data_version"] = self.to_version
        storage.state.save(state)
        return report

# 注册迁移链
MIGRATIONS = {
    2: MigrationV2toV3(),   # v2 → v3
    3: MigrationV3toV4(),   # v3 → v4（未来）
}

def migrate_library(storage: LibraryStorage, target_version: int) -> list[MigrationReport]:
    """按版本链逐步迁移，如 v2 → v3 → v4"""
    current = storage.state.load().get("data_version", 2)  # 默认 v2（无版本号的存量）
    reports = []
    while current < target_version:
        migration = MIGRATIONS[current]
        report = migration.migrate_library(storage)
        reports.append(report)
        current = migration.to_version
    return reports
```

```python
import time
from functools import wraps

def timed(action: str):
    """操作耗时统计装饰器：记录到日志和 metrics"""
    def decorator(fn):
        @wraps(fn)
        def wrapper(ctx, *args, **kwargs):
            start = time.perf_counter()
            try:
                result = fn(ctx, *args, **kwargs)
                duration = (time.perf_counter() - start) * 1000
                ctx.logger.info(f"{action} completed",
                                extra={"action": action, "duration_ms": round(duration, 2)})
                ctx.metrics.observe(f"{action}.duration_ms", duration)
                return result
            except Exception as e:
                duration = (time.perf_counter() - start) * 1000
                ctx.logger.error(f"{action} failed: {e}",
                                  extra={"action": action, "duration_ms": round(duration, 2)})
                ctx.metrics.increment(f"{action}.errors")
                raise
        return wrapper
    return decorator
```

### ARCH-10：领域驱动设计重构（DDD）

**用例示例**：

```python
# application/use_cases/append_entry.py
class AppendEntryUseCase:
    def __init__(self, entry_repo: EntryRepository, audit_repo: AuditRepository,
                 ledger_repo: LedgerRepository, state_repo: StateRepository,
                 clock: Clock, config: Config):
        self.entry_repo = entry_repo
        self.audit_repo = audit_repo
        self.ledger_repo = ledger_repo
        self.state_repo = state_repo
        self.clock = clock
        self.config = config

    def execute(self, entry_data: dict) -> AppendResult:
        # 1. 构造领域对象
        entry = Entry.from_dict(entry_data)

        # 2. 领域校验（铁律 2/5）
        errors = entry.validate()
        if errors:
            raise ValidationError(errors)

        # 3. 业务规则：永不覆盖（铁律 1）
        if self.entry_repo.exists(entry.id):
            raise DuplicateEntryError(entry.id)

        # 4. 业务规则：大小限制
        if entry.size_bytes > self.config.storage.max_entry_bytes:
            raise EntryTooLargeError(entry.id, entry.size_bytes)

        # 5. 持久化（通过仓库接口，不直接操作文件）
        tier = "longterm" if entry.is_longterm(self.config.governance.longterm_importance_threshold) else "intermediate"
        self.entry_repo.save(entry, tier)

        # 6. 审计链（领域逻辑：哈希链追加）
        audit_event = AuditEvent.entry_appended(entry.id, tier, self.clock)
        self.audit_repo.append(audit_event)

        # 7. 账本
        self.ledger_repo.append("append", f"entry={entry.id} → {tier}")

        # 8. 更新 state（importance_accum + merkle_root）
        state = self.state_repo.load()
        state.importance_accum += entry.importance.value
        state.merkle_root = compute_merkle_root(self.entry_repo, self.audit_repo, ...)
        self.state_repo.save(state)
```

### ARCH-12：多库同步与协作（Multi-Library Sync）

| 字段 | 内容 |
|------|------|
| **优先级** | P3 |
| **预估工时** | 5-8 人天 |
| **依赖** | ARCH-01（存储抽象层）、ARCH-02（事务）、ARCH-09（可观测性） |

#### 问题诊断

当前每个库是完全独立的：
- 无法在多设备间同步（如台式机和笔记本之间同步知识库）
- 无法库间共享条目（如个人库和工作库之间引用）
- 无法协作（多人共享一个知识库）
- 无冲突解决机制（如果两个设备同时修改同一库）

这限制了系统的实际使用场景——个人知识库通常需要多设备同步。

#### 架构方案

**增量同步协议**：

```
库 A（主）                    库 B（从）
  │                             │
  │  1. 发送本地状态（最后同步点+Merkle根） │
  │────────────────────────────>│
  │                             │  2. 计算差异（自上次同步以来的变更）
  │                             │     - 新增条目列表
  │                             │     - 修改条目列表（版本号比较）
  │                             │     - 删除/归档条目列表
  │  3. 发送变更集（增量）       │
  │<────────────────────────────│
  │                             │
  │  4. 应用变更（事务性）       │
  │     - 冲突检测（同一条目双方都修改）│
  │     - 冲突解决（保留双方/人工裁决）  │
  │     - 写入审计链和账本       │
  │                             │
  │  5. 确认同步完成，更新同步点 │
  │────────────────────────────>│
```

**冲突解决**：

```python
class ConflictResolver:
    def resolve(self, local: Entry, remote: Entry, policy: str) -> Entry:
        if policy == "keep_local":
            return local
        if policy == "keep_remote":
            return remote
        if policy == "keep_both":
            # 保留双方，远程条目加后缀
            remote.id = f"{remote.id}-remote"
            return [local, remote]  # 返回两条
        if policy == "manual":
            raise ManualConflictRequired(local, remote)
        # 默认：基于 updated_at 时间戳，较新的优先
        return local if local.updated_at > remote.updated_at else remote
```

- 远程同步（通过 HTTP API + 同步端点，ARCH-11）
- 端到端加密（可选，敏感知识库）

2. **第 3-4 天**：实现增量变更计算（基于审计链的变更集生成）

- 库间协作（多人共享知识库）

### ARCH-13：状态机框架（State Machine Framework）

| 字段 | 内容 |
|------|------|
| **优先级** | P3 |
| **预估工时** | 2-3 人天 |
| **依赖** | ARCH-10（DDD 重构） |

#### 问题诊断

当前有多个隐式状态机，但都是硬编码的：

1. **特色包账本状态机**（PACKAGES 定义中）：
   - x-roleplay: `剧情钩子(pending/paid-off)`
   - x-writing: `伏笔账本(planted/recovered)`
   - x-life: `承诺账(made/kept/broken)`
   - x-game: `任务(open/done/abandoned)`
   - 这些状态机只在文档中描述，无代码实现，无状态转换校验

2. **条目生命周期**（隐式）：
   - active → superseded → invalid → archived（attic）
   - 无显式状态机，retire 直接移 attic，无状态转换校验

3. **反思流程**（隐式）：
   - accum < threshold → accum ≥ threshold → reflect 取材 → 合成 → append R-xxx → reflect-done（accum 重置）
   - 无状态机，各步骤独立，可能跳过步骤

这导致：
- 状态转换无校验（如可以从 pending 直接跳到 done，跳过 paid-off）
- 状态转换无审计（谁在什么时候把状态从 A 改成 B）
- 无法查询"当前有多少 pending 状态的条目"
- 新增状态机需重复造轮子

#### 架构方案

**通用状态机框架**：

```python
from dataclasses import dataclass, field
from typing import Callable, Optional
from enum import Enum

class StateMachine:
    """通用状态机：定义状态、转换、守卫条件、副作用"""
    def __init__(self, name: str, states: list[str], initial: str,
                 transitions: dict[str, list[str]],
                 guards: Optional[dict[str, Callable]] = None,
                 on_transition: Optional[Callable] = None):
        self.name = name
        self.states = set(states)
        self.initial = initial
        self.transitions = transitions  # {from_state: [to_states]}
        self.guards = guards or {}      # {transition_name: guard_function}
        self.on_transition = on_transition  # 副作用钩子（写审计链/账本）

    def can_transition(self, from_state: str, to_state: str) -> bool:
        return to_state in self.transitions.get(from_state, [])

    def transition(self, obj, to_state: str, reason: str = "",
                   actor: str = "system") -> tuple[bool, Optional[str]]:
        from_state = getattr(obj, "state", self.initial)
        if not self.can_transition(from_state, to_state):
            return False, f"非法转换: {from_state} → {to_state}（允许: {self.transitions.get(from_state, [])}）"
        guard = self.guards.get(f"{from_state}->{to_state}")
        if guard and not guard(obj):
            return False, f"守卫条件不满足: {from_state} → {to_state}"
        obj.state = to_state
        if self.on_transition:
            self.on_transition(obj, from_state, to_state, reason, actor)
        return True, None

# 预定义状态机
ENTRY_LIFECYCLE = StateMachine(
    name="entry_lifecycle",
    states=["active", "superseded", "invalid", "archived"],
    initial="active",
    transitions={
        "active": ["superseded", "invalid", "archived"],
        "superseded": ["invalid", "archived"],
        "invalid": ["archived"],
        "archived": [],  # 终态
    },
)

PROMISE_TRACKER = StateMachine(
    name="promise",
    states=["made", "kept", "broken", "cancelled"],
    initial="made",
    transitions={
        "made": ["kept", "broken", "cancelled"],
        "kept": [],
        "broken": [],
        "cancelled": [],
    },
)

STORY_HOOK = StateMachine(
    name="story_hook",
    states=["pending", "paid_off", "abandoned"],
    initial="pending",
    transitions={
        "pending": ["paid_off", "abandoned"],
        "paid_off": [],
        "abandoned": [],
    },
)
```

1. **第 1 天**：定义 `StateMachine` 基类和 `StateMachineRegistry`
2. **第 2 天**：实现预定义状态机（条目生命周期、承诺追踪、剧情钩子、任务等）
3. **第 3 天**：实现 `engine state` 命令（查询状态、转换状态、列出状态机）
4. **验证**：状态转换校验测试（非法转换拒绝）；守卫条件测试；副作用钩子测试（转换写审计链）

#### 预期收益

- 状态转换有校验，非法转换被拒绝
- 状态转换有审计（谁在什么时候因为什么原因转换）

- **风险**：状态机框架可能过度设计（简单状态不需要完整框架）；状态机定义增加配置复杂度

## 四、补充建议：错误处理与异常体系

（此建议在 14 项之外，作为基础架构的补充）

### 问题

当前错误处理混乱：
- `sys.exit(f"...")`：在函数中直接退出，无法被调用方捕获
- `assert`：优化模式下失效（P0-02）
- `raise SystemExit(...)`：与 sys.exit 混用
- 裸 `except Exception: pass`：静默吞掉异常（如第 552 行 `_urllib_read`、第 993 行 wrapup 批量导入检测）
- `except Exception as ex: last = ex`：捕获所有异常后重试，可能掩盖严重错误
- 无自定义异常层次，调用方无法区分"条目已存在"和"schema 校验失败"

### 方案

```python
# domain/exceptions.py
class BootstrapV3Error(Exception):
    """基类异常"""
    exit_code: int = 1

class ValidationError(BootstrapV3Error):
    """schema 校验失败"""
    exit_code = 2
    def __init__(self, errors: list[str]):
        self.errors = errors
        super().__init__(f"校验失败: {'; '.join(errors)}")

class DuplicateEntryError(BootstrapV3Error):
    """条目已存在（铁律1：永不覆盖）"""
    exit_code = 3
    def __init__(self, entry_id: str, created_at: str = ""):
        self.entry_id = entry_id
        super().__init__(f"条目 {entry_id} 已存在" + (f"（created_at={created_at}）" if created_at else ""))

class EntryNotFoundError(BootstrapV3Error):
    exit_code = 4

class EntryTooLargeError(BootstrapV3Error):
    exit_code = 5

class SecretDetectedError(BootstrapV3Error):
    """铁律5：检测到密钥"""
    exit_code = 6

class SlowLaneConfirmationRequired(BootstrapV3Error):
    """慢车道：需要人类确认"""
    exit_code = 10
    def __init__(self, level: str, gate_text: str):
        self.level = level
        self.gate_text = gate_text
        super().__init__(f"[慢车道] {level} 需人类令牌")

class MigrationError(BootstrapV3Error):
    exit_code = 20

class StorageError(BootstrapV3Error):
    exit_code = 30

class NetworkError(BootstrapV3Error):
    exit_code = 40
```

**CLI 层统一异常处理**：

```python
def main():
    try:
        args = parse_args()
        execute_command(args)
    except BootstrapV3Error as e:
        print(f"错误: {e}", file=sys.stderr)
        if isinstance(e, ValidationError):
            for err in e.errors:
                print(f"  - {err}", file=sys.stderr)
        if isinstance(e, SlowLaneConfirmationRequired):
            print(e.gate_text, file=sys.stderr)
            print("确认后加 --yes", file=sys.stderr)
        sys.exit(e.exit_code)
    except KeyboardInterrupt:
        print("\n操作中断", file=sys.stderr)
        sys.exit(130)
    except Exception as e:
        print(f"未预期的错误: {type(e).__name__}: {e}", file=sys.stderr)
        if debug_mode:
            import traceback; traceback.print_exc()
        sys.exit(99)
```

## 五、架构决策记录（ADR）模板

建议为每个重大架构决策建立 ADR（Architecture Decision Record），存储在 `docs/adr/` 目录：

```markdown
# ADR-001: 引入存储抽象层

## 状态
已接受（2026-09-08）

## 背景
当前所有函数直接操作文件系统（Path/read_text/write_bytes），导致：
- 无法替换存储后端（SQLite/内存/远程）
- 测试需操作真实文件系统，慢且易污染
- 无法添加缓存层

## 决策
定义 EntryStorage/AuditStorage/LedgerStorage/StateStorage 抽象接口，
所有持久化操作通过接口进行。提供 FileSystemStorage（默认）和
InMemoryStorage（测试用）实现。

## 后果
### 正面
- 测试可使用内存存储，速度提升 5-10 倍
- 为 SQLite/远程存储铺路
- 缓存层可作为装饰器添加

### 负面
- 增加一层间接调用，性能损耗约 1-3%
- 迁移工作量约 5 人天

## 替代方案
- 维持现状（直接文件操作）：否决，可测试性差
- 使用 ORM（SQLAlchemy）：否决，过度设计，文件系统是主要存储
```
