### P0-01：Merkle 树缺乏域分离，存在第二原像攻击漏洞

| 字段 | 内容 |
|------|------|
| **问题 ID** | P0-01 |
| **标题** | Merkle 树叶子节点与内部节点使用相同哈希函数无前缀区分，存在第二原像攻击 |
| **严重程度** | 严重（安全漏洞） |
| **优先级** | P0 |
| **文件位置** | `merkle_root()` 函数，第 260-268 行 |
| **模块** | 加密/审计基础设施 |
| **预估工时** | 0.5 人天 |

#### 问题描述

`merkle_root()` 函数构建 Merkle 树时：

```python
# 第 265 行：叶子节点哈希
layer = [sha((p + h).encode()) for p, h in leaves]

# 第 267 行：内部节点哈希
layer = [sha((layer[i] + (layer[i+1] if i+1 < len(layer) else layer[i])).encode())
         for i in range(0, len(layer), 2)]
```

叶子节点和内部节点都使用 `sha(data.encode())`，**没有任何域分离前缀**。这意味着攻击者可以构造一个内部节点的拼接字符串（`left_hash + right_hash`），使其恰好等于某个叶子节点的 `path + file_hash`，从而用一个内部节点冒充叶子节点，或反之。

#### 根因分析

Merkle 树的标准安全实现要求对不同层级的节点使用不同的哈希前缀（如叶子节点用 `0x00`，内部节点用 `0x01`），这是 Bitcoin、Certificate Transparency 等系统的标准做法。当前实现省略了这一关键步骤。

#### 影响范围

- 直接动摇"公理 E：根锚定"的安全承诺——库根（Merkle root）是系统完整性的核心锚点
- 攻击者理论上可以构造伪造的文件集合，使其 Merkle 根与合法库相同
- 影响所有依赖根对账的功能：`install` 校验模式、`engine doctor` 第五态、`guard --anchor`

#### 复现步骤（概念验证）

1. 构造合法库，计算 Merkle 根 `R`
2. 找到一个叶子节点 `L = sha(path + hash)`
3. 构造两个伪哈希 `a, b` 使得 `sha(a + b) = L`（通过寻找碰撞或利用长度扩展）
4. 用包含 `a, b` 的伪树替换原叶子节点，根仍为 `R`

> 注：实际利用需要找到 SHA-256 碰撞，计算上不可行，但域分离是标准安全实践，缺失意味着安全边界不完整。对于以"可证伪"和"根锚定"为核心设计哲学的系统，这是不可接受的安全缺口。

#### 修复建议

```python
def merkle_root(root: Path, exclude: set = frozenset()) -> str:
    leaves = sorted(...)
    if not leaves: return sha(b"empty")
    # 叶子节点加 0x00 前缀
    layer = [sha(b"\x00" + (p + h).encode()) for p, h in leaves]
    while len(layer) > 1:
        # 内部节点加 0x01 前缀
        layer = [sha(b"\x01" + layer[i].encode() +
                     (layer[i+1] if i+1 < len(layer) else layer[i]).encode())
                 for i in range(0, len(layer), 2)]
    return layer[0]
```

- [ ] 叶子节点和内部节点使用不同的哈希前缀

- [ ] 新增测试：验证修改文件内容后根变化、修改路径后根变化

### P0-02：`assert` 用于安全关键校验，`python -O` 下全部失效

| 字段 | 内容 |
|------|------|
| **问题 ID** | P0-02 |
| **标题** | `cmd_verify` 中使用 `assert` 进行不变式校验，优化模式下被编译器移除 |
| **严重程度** | 严重（安全/正确性） |
| **优先级** | P0 |
| **文件位置** | `cmd_verify()` 函数，第 618-622 行 |
| **模块** | 验证/对账 |
| **预估工时** | 0.5 人天 |

#### 问题描述

```python
# 第 618-622 行
assert len(LAWS) == 6 and len(LEVELS) == 10 and len(PACKAGES) == 12
a14 = json.dumps(REGISTRY["A14"], ensure_ascii=False)
assert "Kang" in a14 and "Wang" not in REGISTRY["A14"]["note"]
assert "objective hacking" in CHARTER_L8 and "reward hacking" not in CHARTER_L8
assert "删除" not in ESCAPE_POD and "attic" in ESCAPE_POD
```

这 4 条 `assert` 校验的是**系统不变式**：铁律数量、档位数量、特色包数量、关键题录正确性、宪章术语正确性、回退措辞正确性。这些是 `verify` 命令的核心校验逻辑，不是调试断言。

Python 的 `assert` 语句在使用 `-O`（优化）标志运行时会被编译器完全移除，不生成任何字节码。这意味着如果用户或 CI 环境使用 `python -O bootstrap_v3.py verify`，这些不变式校验**全部静默跳过**，`verify` 会 falsely report success。

#### 根因分析

开发者混淆了"调试断言"和"生产校验"。`assert` 适用于开发阶段的内部状态检查，不适用于面向用户的命令校验逻辑。

#### 影响范围

- `verify` 命令在 `-O` 模式下不变式校验全部失效
- 可能导致被篡改的 `REGISTRY`、`LAWS`、`CHARTER_L8` 等关键数据未被检测
- CI/CD 环境如果配置了 `PYTHONOPTIMIZE=1` 或使用 `-O`，会受影响

#### 修复建议

将所有 `assert` 替换为显式条件检查 + `sys.exit` 或 `raise ValueError`：

```python
errors = []
if len(LAWS) != 6: errors.append(f"铁律数量异常: {len(LAWS)} != 6")
if len(LEVELS) != 10: errors.append(f"档位数量异常: {len(LEVELS)} != 10")
if len(PACKAGES) != 12: errors.append(f"特色包数量异常: {len(PACKAGES)} != 12")
a14 = json.dumps(REGISTRY["A14"], ensure_ascii=False)
if "Kang" not in a14: errors.append("A14 题录作者错误（缺 Kang）")
if "Wang" in REGISTRY["A14"]["note"]: errors.append("A14 note 含错误作者名 Wang")
if "objective hacking" not in CHARTER_L8: errors.append("宪章缺 objective hacking 术语")
if "reward hacking" in CHARTER_L8: errors.append("宪章误用 reward hacking（应为 objective hacking）")
if "删除" in ESCAPE_POD: errors.append("回退措辞含「删除」（违反铁律1措辞约束）")
if "attic" not in ESCAPE_POD: errors.append("回退措辞缺 attic")
if errors:
    print("verify: 静态不变式校验失败：")
    for e in errors: print(f"  [不变式] {e}")
    sys.exit(1)
```

- [ ] `cmd_verify` 中不再使用 `assert`
- [ ] 使用 `python -O bootstrap_v3.py verify` 运行时，不变式校验仍然生效
- [ ] 故意篡改 `LAWS` 数量后，`verify` 能检测到并 exit 1
- [ ] 全文件搜索确认无其他生产路径使用 `assert`（测试代码中的 `assert` 可保留）

### P0-04：`cmd_build()` 中死分支逻辑错误

| 字段 | 内容 |
|------|------|
| **问题 ID** | P0-04 |
| **标题** | `cmd_build` 中 `if lib and out == Path("./dist")` 永远为 False，`--out` 与 `--lib` 优先级逻辑混乱 |
| **严重程度** | 严重（正确性） |
| **优先级** | P0 |
| **文件位置** | `cmd_build()` 函数，第 634-656 行，具体第 642-643 行 |
| **模块** | 安装器/渲染 |
| **预估工时** | 0.5 人天 |

#### 问题描述

```python
# 第 636 行
if out is None: out = Path(lib) if lib else Path("./dist")

# ... 渲染 spec.md / 提示词速查.md / citations.md 到 out ...

# 第 642-643 行
if lib and out == Path("./dist"):   # ← 永远为 False
    out = Path(lib)                  # ← 死代码
```

逻辑分析：
- 当 `lib` 存在且 `out is None` 时，第 636 行将 `out` 设为 `Path(lib)`
- 当 `lib` 存在且 `out is not None` 时，`out` 是用户指定的值
- 因此，当 `lib` 为真时，`out` 要么是 `Path(lib)`，要么是用户指定值，**不可能等于 `Path("./dist")`**
- 第 642 行的条件 `lib and out == Path("./dist")` 永远为 False
- 第 643 行 `out = Path(lib)` 是**永远不会执行的死代码**

这说明 `--out` 和 `--lib` 的优先级逻辑存在设计混乱。开发者可能意图是：当同时指定 `--lib` 和 `--out` 时，渲染件先写到 `./dist` 再复制到 lib，但实际实现并非如此。

#### 根因分析

`cmd_build` 的 `--out` 和 `--lib` 参数语义不清晰：
- `--out`：渲染产物输出目录
- `--lib`：已安装库目录（用于刷新库内渲染件和 state）

当两者同时指定时，行为不明确。第 642-643 行的死代码表明开发者曾尝试处理某种组合，但逻辑有误。

#### 影响范围

- `build-docs --lib <lib>` 时，`spec.md`/`提示词速查.md`/`citations.md` 会写到 `Path(lib)`（第 636 行），然后第 645-655 行又写 `AGENTS.md`/`README.md` 到 lib，并更新 state。这部分功能正常。
- 但如果用户同时指定 `--out ./dist --lib <lib>`，渲染件会写到 `./dist`，而 `AGENTS.md`/`README.md` 和 state 更新会作用于 lib——**渲染件分裂到两个目录**，这可能不是用户预期。
- 死代码的存在表明逻辑未经充分测试。

#### 修复建议

明确 `--out` 和 `--lib` 的语义：

```python
def cmd_build(out, lib=None):
    """渲染文档产物。
    - 仅 --out: 渲染 spec/速查/citations 到 out 目录
    - 仅 --lib: 渲染全部产物（含 AGENTS/README）到库目录并更新 state
    - 同时指定: 渲染到 out，不触碰 lib（--lib 被忽略，或报错）
    """
    if lib:
        if out is not None and out != Path(lib):
            sys.exit("build-docs: --out 与 --lib 同时指定且路径不同时行为不明确，请只指定其一")
        out = Path(lib)
    elif out is None:
        out = Path("./dist")
    out = Path(out)
    out.mkdir(parents=True, exist_ok=True)
    # ... 统一渲染逻辑 ...
```

移除死代码，添加参数互斥校验。

### P1-01：每次写操作全量重算 Merkle 根，O(n) 全文件扫描，性能不可扩展

| 字段 | 内容 |
|------|------|
| **问题 ID** | P1-01 |
| **标题** | append/wrapup/retire/reflect-done 每次写操作都全量重算 Merkle 根，遍历所有文件并读取全部字节 |
| **严重程度** | 重要（性能） |
| **优先级** | P1 |
| **文件位置** | `merkle_root()` 第 260-268 行；调用点：第 940、980、1029、1092、870 行 |
| **模块** | 加密/审计基础设施 |
| **预估工时** | 3-5 人天 |

#### 问题描述

每次写操作都会调用 `merkle_root(lib, exclude={"state.json"})`，该函数执行：

```python
leaves = sorted((str(p.relative_to(root)), sha(p.read_bytes()))
                for p in root.rglob("*")
                if p.is_file() and p.name not in exclude)
```

这会：
1. `root.rglob("*")` 递归遍历目录下所有文件
2. 对每个文件调用 `p.read_bytes()` 读取**全部字节**
3. 对每个文件计算 SHA-256
4. 构建 Merkle 树（O(n) 哈希计算）

对于一个包含 1000 个条目（平均 5KB）的库，每次 `append` 都要读取约 5MB 数据；如果包含大条目（最大 16MB），单次 append 可能读取数百 MB。

代码中已经意识到这个问题：

```python
# 第 91 行 TUNABLES
"merkle_refresh_trigger": {"value": 500, "source": "工程判断",
    "note": "Y-010：条目超此值时评估增量哈希树（Merkle 全树重算 O(n)），登记不动手"},
```

"登记不动手"意味着这个优化**只登记了需求，从未实现**。当条目数超过 500 时，系统会变得极慢，但没有任何降级策略或警告。

#### 根因分析

Merkle 树的全量重算是最简单的实现，但没有考虑可扩展性。缺少：
- 文件级哈希缓存（避免重复读取未变化的文件）
- 增量 Merkle 树更新（只更新受影响的路径）
- 写操作合并（批量写入后只算一次根）
- 懒计算（根哈希按需计算，而非每次写操作都算）

#### 影响范围

- `engine append`：每次写入都全量重算，写入延迟随库大小线性增长
- `engine wrapup`：同上
- `engine retire`：同上
- `engine reflect-done`：同上
- `install`：安装时算一次（可接受）
- `doctor`：体检时算一次（可接受）
- 当库包含大文件（如 16MB 条目）时，单次写操作可能需要数秒甚至数十秒

#### 修复建议

**短期方案（1-2天）**：引入文件级哈希缓存

```python
# 在 state.json 或独立的 .merkle_cache.json 中维护
# {relative_path: {"sha256": ..., "mtime": ..., "size": ...}}
def _file_hash_cached(root, rel_path, cache):
    p = root / rel_path
    stat = p.stat()
    cached = cache.get(rel_path)
    if cached and cached["mtime"] == stat.st_mtime and cached["size"] == stat.st_size:
        return cached["sha256"]
    h = sha(p.read_bytes())
    cache[rel_path] = {"sha256": h, "mtime": stat.st_mtime, "size": stat.st_size}
    return h
```

**中期方案（3-5天）**：实现增量 Merkle 树

1. 维护一个扁平的文件哈希映射（path → hash）
2. 写操作时只更新受影响文件的哈希
3. 使用排序后的路径列表构建 Merkle 树，只重算受影响路径到根的 O(log n) 个节点

**替代方案**：将根哈希改为懒计算——写操作时只更新文件哈希缓存，标记 `merkle_dirty=True`；`doctor`/`guard --anchor`/用户显式请求时才重算根。但这会削弱"写后根立即一致"的保证，需要权衡。

#### 验收标准

- [ ] 1000 条目库的单次 `append` 耗时 < 100ms（当前可能 > 1s）
- [ ] 文件哈希缓存持久化，进程重启后有效
- [ ] 缓存失效机制正确（mtime + size 双重校验）
- [ ] 现有测试 `t_merkle_root_consistency`、`t_root_refresh_on_write` 通过
- [ ] 新增性能测试：100/500/1000 条目下的 append 耗时基准
- [ ] 当条目数超过 `merkle_refresh_trigger`(500) 时，输出性能警告

### P1-02：检索引擎全量扫描，无索引无缓存，中文分词缺失

| 字段 | 内容 |
|------|------|
| **问题 ID** | P1-02 |
| **标题** | `_rank_entries` 每次检索全量扫描所有 JSON 文件，无倒排索引无缓存；中文查询按空白分割导致整短语作为单 token |
| **严重程度** | 重要（性能/功能） |
| **优先级** | P1 |
| **文件位置** | `_rank_entries()` 第 885-915 行；`cmd_engine` retrieve 分支第 943-948 行 |
| **模块** | 引擎 |
| **预估工时** | 3-5 人天 |

#### 问题描述

**性能问题**：
```python
# 第 888-896 行
for f in (lib / "memory").rglob("*.json"):
    e = json.loads(f.read_text(encoding="utf-8"))
    ...
    entries.append((f, e, age_days))
```

每次 `retrieve` 都遍历所有 `.json` 文件，读取并 `json.loads`。`eval` 中对每个 query 都调用一次 `_rank_entries`——N 个 query 就是 N 次全库扫描。没有内存缓存，没有倒排索引。

**中文分词问题**：
```python

kw_hit = sum(1 for w in q.split() if w in " ".join(e["keywords"]))
c_hit = sum(1 for w in q.split() if w in c)
```

`q.split()` 按空白分割查询词。对于中文查询"哈希链审计"，由于没有空白，整个短语作为一个 token。只有当条目的 content 或 keywords 中恰好包含完整的"哈希链审计"子串时才命中，而包含"哈希链"和"审计"两个独立关键词的条目不会命中。

**子串匹配问题**：
`w in c` 是子串匹配，不是词匹配。例如查询 "hash" 会匹配 "hashchain"、"hashtable" 等不相关内容。

#### 根因分析

检索引擎是最简单的实现（全表扫描 + 子串匹配），没有考虑：
- 中文分词（jieba 或字符 n-gram）
- 倒排索引（token → 条目列表）
- 结果缓存（相同查询复用结果）
- BM25/TF-IDF 等标准检索排序算法

#### 影响范围

- 检索性能随库大小线性下降，1000 条目库检索可能 > 500ms
- `eval` 命令的性能为 O(Q × N)，Q=query 数，N=条目数
- 中文检索效果差——多关键词查询无法拆分匹配
- 子串匹配导致误报（短查询词匹配到不相关的长词）

#### 修复建议

**短期（1-2天）**：
1. 引入中文分词：使用 `jieba`（外部依赖）或简单的字符 bigram/trigram（无依赖）
2. 添加内存缓存：`functools.lru_cache` 或手动缓存，缓存条目列表（按库 mtime 失效）
3. 词匹配替代子串匹配：分词后用集合交集计算命中

**中期（3-5天）**：
1. 实现倒排索引：`{token: {entry_id: {tf, positions}}}`
2. 写入时增量更新索引（append 时添加，retire 时移除）
3. 实现 BM25 排序算法替代当前的简单加权
4. 索引持久化到 `memory/.index.json` 或类似文件

```python
# 简单的无依赖中文分词（字符 bigram）
def _tokenize(text):
    # 英文按空白和标点分割，中文按 bigram
    tokens = []
    for seg in re.findall(r'[a-zA-Z0-9]+|[\u4e00-\u9fff]+', text.lower()):
        if re.match(r'[a-zA-Z0-9]+', seg):
            tokens.append(seg)
        else:
            # 中文 bigram
            for i in range(len(seg) - 1):
                tokens.append(seg[i:i+2])
            if len(seg) == 1:
                tokens.append(seg)
    return tokens
```

### P1-04：`chain_append()` 非原子，并发场景下审计链分叉

| 字段 | 内容 |
|------|------|
| **问题 ID** | P1-04 |
| **标题** | `chain_append` 读取最后一行哈希与追加新行之间无文件锁，并发调用导致链分叉 |
| **严重程度** | 重要（数据完整性） |
| **优先级** | P1 |
| **文件位置** | `chain_append()` 第 220-238 行 |
| **模块** | 审计基础设施 |
| **预估工时** | 1 人天 |

#### 问题描述

```python
# 第 229-233 行：读取最后一行哈希
if files:
    last = files[-1].read_text(encoding="utf-8").strip().splitlines()
    if last:
        m = re.search(r"h:([0-9a-f]{64})", last[-1])
        prev = m.group(1) if m else ""

# 第 233 行：计算新行哈希
h = line_hash(prev, text)

# 第 236-237 行：追加新行
with f.open("a", encoding="utf-8") as fh:
    fh.write(f"- {time.strftime(...)} | prev:{prev or 'genesis'} | h:{h} | {text}\n")
```

"读取最后一行哈希"（第 230 行）和"追加新行"（第 237 行）之间没有任何同步机制。如果两个进程/线程同时执行 `chain_append`：

1. 进程 A 读取最后一行哈希 = H_A
2. 进程 B 读取最后一行哈希 = H_A（同一行）
3. 进程 A 追加行，prev=H_A，h=H_A1
4. 进程 B 追加行，prev=H_A，h=H_B1

结果：文件中有两行的 prev 都指向 H_A，但 H_A1 和 H_B1 是兄弟关系，不是链式关系。审计链**分叉**了——后一行的 prev 不指向文件中的前一行，`doctor` 的链校验会检测到断链。

#### 根因分析

缺少文件锁。`chain_append` 假设串行调用，但没有强制这一假设。

#### 影响范围

- `absorb-md` 批量导入：虽然是单进程串行，但如果未来改为并发会受影响
- 脚本并发调用 `engine append`：用户可能在多个终端同时写入
- CI/CD 并发任务：如果多个 job 操作同一库
- 链分叉后 `doctor` 会报断链，但修复困难（需要人工合并分叉）

#### 修复建议

使用文件锁确保原子性：

```python
import fcntl  # Linux/macOS；Windows 可用 portalocker 或 msvcrt

def chain_append(audit_dir: Path, text: str, prev_override: str = None) -> str:
    audit_dir.mkdir(parents=True, exist_ok=True)
    stamp = time.strftime("%Y-%m")
    f = audit_dir / f"lifelog-{stamp}.md"

    # 使用锁文件确保读-算-写的原子性
    lock_file = audit_dir / ".chain.lock"
    with open(lock_file, "w") as lock_fh:
        fcntl.flock(lock_fh.fileno(), fcntl.LOCK_EX)
        try:
            # 读取最后一行哈希（在锁内）
            files = sorted(audit_dir.glob("lifelog-*.md"))
            if prev_override is not None and not files:
                prev = prev_override
            else:
                prev = ""
                if files:
                    last = files[-1].read_text(encoding="utf-8").strip().splitlines()
                    if last:
                        m = re.search(r"h:([0-9a-f]{64})", last[-1])
                        prev = m.group(1) if m else ""
            h = line_hash(prev, text)
            with f.open("a", encoding="utf-8") as fh:
                fh.write(f"- {time.strftime('%Y-%m-%d %H:%M')} | prev:{prev or 'genesis'} | h:{h} | {text}\n")
        finally:
            fcntl.flock(lock_fh.fileno(), fcntl.LOCK_UN)
    return h
```

跨平台方案：使用 `portalocker` 库（支持 Linux/macOS/Windows），或检测平台选择 `fcntl`/`msvcrt`。

- [ ] 现有测试 `t_chain_and_cross_month`、`t_chain_tamper_detected`、`t_doctor_chain_check` 通过

### P1-06：`cmd_migrate()` generator truthy 误导 + 空文件崩溃

| 字段 | 内容 |
|------|------|
| **问题 ID** | P1-06 |
| **标题** | `cmd_migrate` 中 `glob()` 返回 generator 永远 truthy 导致条件误导；legacy 链文件为空时 `splitlines()[-1]` 崩溃 |
| **严重程度** | 重要（正确性/健壮性） |
| **优先级** | P1 |
| **文件位置** | `cmd_migrate()` 第 1152-1174 行；具体第 1155、1162 行 |
| **模块** | 迁移 |
| **预估工时** | 0.5 人天 |

#### 问题描述

**问题 1：generator truthy 误导（第 1155 行）**

```python
if (lib / "audit").glob("lifelog-*.md") and any((lib / "audit").glob("lifelog-*.md")):
    sys.exit("已存在 v3 审计链...")
```

`Path.glob()` 返回一个 generator 对象。在 Python 中，generator 对象的布尔值**永远为 True**（因为它是一个有 `__iter__` 方法的对象，不是空容器）。因此第一个条件 `(lib/"audit").glob(...)` 永远为 True，实际判断只靠 `any(...)`。

虽然功能上等价于 `if any(...)`，但：
- 第一次 `glob()` 调用被完全浪费（创建了 generator 但从未迭代）
- 代码具有严重误导性，读者会以为两个条件都在检查
- 如果未来有人修改为 `if (lib/"audit").glob(...):`（去掉 `any`），条件会永远为 True，导致 bug

**问题 2：空文件崩溃（第 1162 行）**

```python
cands.sort(key=lambda p: p.name)
tail = cands[-1].read_text(encoding="utf-8").strip().splitlines()[-1]
```

如果 legacy 链文件存在但为空（0 字节），`read_text().strip().splitlines()` 返回 `[]`，`[-1]` 直接抛出 `IndexError: list index out of range`，没有友好错误提示。

#### 根因分析

1. 开发者不了解 `Path.glob()` 返回 generator 而非 list，误用了 truthy 检查
2. 缺少对空文件的防御性检查

#### 影响范围

- 代码可读性差，误导维护者
- 空 legacy 链文件导致 `migrate` 命令崩溃，只有 Python traceback
- 浪费一次 `glob()` 调用（性能影响可忽略）

#### 修复建议

```python
# 问题 1 修复：使用 any() 或先转 list
v3_chain_exists = any((lib / "audit").glob("lifelog-*.md"))
if v3_chain_exists:
    sys.exit("已存在 v3 审计链（audit/lifelog-*.md）——勿重复 migrate ...")

# 问题 2 修复：空文件检查
cands.sort(key=lambda p: p.name)
last_file = cands[-1]
lines = last_file.read_text(encoding="utf-8").strip().splitlines()
if not lines:
    sys.exit(f"migrate: legacy 链文件为空（{last_file}），无法提取尾哈希")
tail = lines[-1]
```

### P1-07：同 id 拒绝时读取整个旧条目仅为获取 created_at

| 字段 | 内容 |
|------|------|
| **问题 ID** | P1-07 |
| **标题** | `engine append` 同 id 拒绝路径读取并解析整个 JSON 文件仅为错误消息中的 created_at，大条目场景下产生不必要的 I/O |
| **严重程度** | 重要（性能） |
| **优先级** | P1 |
| **文件位置** | `cmd_engine()` append 分支，第 930-932 行 |
| **模块** | 引擎 |
| **预估工时** | 0.2 人天 |

#### 问题描述

```python
# 第 929-932 行
epath = dest / f"{e['id']}.json"
if epath.exists():
    old = json.loads(epath.read_text(encoding="utf-8"))  # 读取整个文件
    sys.exit(f"schema v3 拒绝写入：条目 {e['id']} 已存在（created_at={old.get('created_at')}）。更新请人工裁决或换 id——写入路径不覆盖。")
```

当条目 id 已存在时，代码读取整个 JSON 文件并 `json.loads`，只为了获取 `created_at` 字段用于错误消息。

如果已存在的条目是一个大条目（`max_entry_bytes = 16MB`），这个拒绝路径会：
1. 读取 16MB 文件到内存
2. `json.loads` 解析 16MB JSON（CPU 密集）
3. 提取一个字段
4. 退出

这在拒绝路径上产生了完全不必要的 16MB 读取和 JSON 解析。

#### 根因分析

开发者为了在错误消息中显示 `created_at`，选择了最简单的实现（读取整个文件），没有考虑大条目场景。

#### 影响范围

- 大条目（接近 16MB）的重复写入拒绝时，延迟可能 > 100ms
- 内存峰值增加 16MB（虽然很快释放）
- 如果攻击者知道某个大条目的 id，反复尝试写入可以造成 DoS（每次都触发 16MB 读取）

#### 修复建议

方案 1：不显示 created_at，只报告条目已存在

```python
if epath.exists():
    sys.exit(f"schema v3 拒绝写入：条目 {e['id']} 已存在。更新请人工裁决或换 id——写入路径不覆盖。")
```

方案 2：使用文件 mtime 作为近似时间

```python
if epath.exists():
    mtime = time.strftime("%Y-%m-%d %H:%M:%S", time.localtime(epath.stat().st_mtime))
    sys.exit(f"schema v3 拒绝写入：条目 {e['id']} 已存在（文件 mtime={mtime}）。更新请人工裁决或换 id——写入路径不覆盖。")
```

方案 3：流式读取 JSON 的前几个字段（复杂，不推荐）

推荐方案 2，既保留了时间信息，又避免了大文件读取。

#### 验收标准

- [ ] 同 id 拒绝时不读取整个条目文件
- [ ] 错误消息仍包含有用的时间信息（mtime 或不包含）
- [ ] 现有测试 `t_append_rejects_dup_id` 通过

    """统一的写操作后处理：写 audit + 写 ledger + 刷 merkle_root"""
    chain_append(lib / "audit", f"{action}: {detail}")
    _ledger_append(lib, action, detail)

    if st_path.exists():
        st = json.loads(st_path.read_text(encoding="utf-8"))
        st["merkle_root"] = merkle_root(lib, exclude={"state.json"})
        st_path.write_text(json.dumps(st, ensure_ascii=False, indent=1), encoding="utf-8")

    "retrieve": _engine_retrieve,
    "eval": _engine_eval,

    "reflect": _engine_reflect,
    "reflect-done": _engine_reflect_done,
    "doctor": _engine_doctor,
    "retire": _engine_retire,
    "shadow": _engine_shadow,
}

    ENGINE_COMMANDS[op](lib, text, k)

但这只是一个字符串列表，不是类型定义。条目在代码中以裸 `dict` 传递，字段通过字符串键访问：

- 第 1079 行：`(e.get("validity") or {}).get("t_invalid")`

         "level": ..., "packages": ..., "modules": ..., "delivered": ...,

但这也是一个裸 dict，`emotion` 的四维结构（valence/arousal/certainty/stakes）没有类型定义，在 `wrapup` 中通过 `for k4 in emo: emo[k4] = ...` 遍历。

#### 影响范围

#### 问题描述

8 个渲染函数：

以 `render_entrypoint` 为例（第 325-352 行，28 行）：
- 铁律列表用 `"\n".join(f"{i}. {t}" ...)` 生成
- 档位信息直接嵌入 f-string
- 命令清单纯文本硬编码在 f-string 中

- 修改文档格式需要修改 Python 代码，增加回归风险
- 非开发者（如技术写作人员）无法直接修改模板
- 模板无法独立测试（需要运行 Python 代码）
- f-string 中的 Markdown 格式容易出错（缩进、换行、转义）

#### 修复建议

引入 Jinja2 模板引擎：

```
templates/
├── AGENTS.md.j2
├── README.md.j2
├── spec.md.j2
├── quickref.md.j2
├── citations.md.j2
├── skills/
│   ├── wrap-up.md.j2
│   └── task-start.md.j2
└── pkg_template.md.j2
```

```python
# render.py
from jinja2 import Environment, FileSystemLoader

_template_env = Environment(
    loader=FileSystemLoader("templates"),
    trim_blocks=True,
    lstrip_blocks=True,
)

def render_entrypoint(level: str) -> str:
    template = _template_env.get_template("AGENTS.md.j2")
    return template.render(
        version=VERSION,
        level=level,
        level_info=LEVELS[level],
        laws=LAWS,
        tunables=TUNABLES,
    )
```

### P2-08："慢车道"人类令牌机制薄弱

| 字段 | 内容 |
|------|------|
| **问题 ID** | P2-08 |
| **标题** | L8/L9 安装只需 `--yes` 命令行参数，任何脚本都可自动添加，无法区分人工确认和脚本自动确认 |
| **严重程度** | 架构/安全 |
| **优先级** | P2 |
| **文件位置** | `cmd_install()` 第 764-767 行 |
| **模块** | 守卫/安全 |
| **预估工时** | 1 人天 |

#### 问题描述

```python
# 第 764-767 行
if level in ("L8", "L9") and not yes and (is_first or redeliver):
    gate = CHARTER_L8 if level == "L8" else "BCA 公理+验收三件..."
    sys.exit(f"[慢车道] {level} 需人类令牌。先展示并确认：\n{gate}\n确认后加 --yes")
```

"慢车道"机制只检查 `--yes` 标志。这意味着：
- 任何脚本都可以加 `--yes` 自动确认，无需人工干预
- 无法区分"用户在终端手动输入 --yes"和"CI/CD 脚本自动加 --yes"
- 无法记录确认人（谁确认的？）
- 无法防止自动化绕过（一个简单的 shell 函数 `install_l8() { bootstrap_v3.py install L8 --yes "$@"; }` 就完全绕过了慢车道）

这与"公理 F：慢车道——L8/L9 安装、变异、回退需人类令牌"的承诺存在差距。`--yes` 不是"人类令牌"，只是一个命令行标志。

#### 影响范围

- L8/L9 的"慢车道"安全承诺形同虚设
- 自动化脚本可以无提示地安装 L8/L9
- 审计链中记录的"人类令牌：命令行 --yes 确认"（第 857 行）无法证明是人类确认
- 如果 L8/L9 包含危险操作（自指演化、BCA 情绪系统），自动化安装可能带来风险

#### 修复建议

**方案 1：交互式确认**

```python
import sys

def _human_confirm(prompt: str, level: str) -> bool:
    """交互式人类确认：要求用户输入完整的确认短语"""
    print(prompt)
    print(f"\n要安装 {level}，请输入「确认安装{level}」（输入其他任何内容将中止）：")
    try:
        answer = input().strip()
    except EOFError:
        return False
    expected = f"确认安装{level}"
    if answer != expected:
        print(f"未输入正确的确认短语（期望：{expected}），安装中止")
        return False
    return True
```

**方案 2：外部签名文件（人侧保管）**

用户预先在人侧（如密码管理器、加密 USB）保管一个授权令牌文件，安装时通过 `--token-file` 指定：

```python
def _verify_human_token(token_file: Path, level: str) -> bool:
    """验证人类令牌文件：包含授权级别和时间戳，人侧保管"""
    if not token_file.exists():
        return False
    token = json.loads(token_file.read_text())
    return token.get("level") == level and token.get("authorized", False)
```

**方案 3：至少记录确认方式**

在审计链中区分"交互式确认"和"--yes 自动确认"：

```python
confirm_method = "interactive" if human_confirmed else "cli-flag---yes"
chain_append(lib / "audit", f"M-003 charter-confirmed level={level}（确认方式：{confirm_method}）")
```

推荐方案 1（交互式确认）+ 方案 3（记录确认方式），`--yes` 可以保留为 CI/CD 场景的显式绕过，但必须在审计链中明确标注"非交互式确认"。

#### 验收标准

- [ ] L8/L9 首次安装需要交互式确认（输入确认短语），`--yes` 标注为非交互式
- [ ] 审计链中记录确认方式（interactive / cli-flag）
- [ ] `--yes` 仍可用于 CI/CD，但输出明确警告
