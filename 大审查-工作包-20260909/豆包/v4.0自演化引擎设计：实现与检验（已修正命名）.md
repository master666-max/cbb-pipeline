# 自演化引擎设计：实现与检验
## library-bootstrap 核心机制深度设计文档

---

> **文档定位**：本文档设计 library-bootstrap 系统中最为核心的自演化（Self-Evolution）机制。这不是普通功能，而是系统"自己修改自己"的能力——它既是最强大的特性，也是最危险的攻击面。设计的核心矛盾是：**如何在允许系统自主改进的同时，保证它不会突破安全边界、不会退化、不会失控。**
>
> **与 v3 的关系**：v3 的 L8（自指演化）和 L9（BCA，Baseline-Confined Autonomy）只提供了概念框架——宪章（charter）定义了变异规则，guard --diff 检查外部 diff 是否触碰基准，run_tests 作为准入条件。但 v3 没有变异生成机制、没有隔离验证环境、没有多目标评估、没有灰度应用、没有感知监控。本文档补全这些缺失环节。

---

## 一、定义：自演化究竟在演化什么

### 1.0 两套层级体系的澄清（重要）

本文档涉及两套不同的「层级」概念，必须严格区分，避免混淆：

**体系 A：安装档位（Installation Level）—— v3 原有的 L0-L9**

这是系统的**功能级别**，决定系统安装了哪些能力、有没有自演化功能：

| 安装档位 | 含义 | 自演化能力 |
|----------|------|-----------|
| L0-L6 | 基础安装，不同程度的功能集 | **无** |
| L7 | 实验性功能 | 无（仅有实验框架） |
| **L8** | **自指演化（Self-Modifying）** | **有——每个变异必须人类确认** |
| **L9** | **BCA（Baseline-Confined Autonomy）** | **有——基准约束下的有限自主，人类定期审查** |

**自演化能力从 L8 才开始引入。** L1-L7 档位的系统根本没有自演化功能。v3 的宪章、guard、run_tests 门禁是为 L8/L9 设计的框架。

**体系 B：演化对象风险层级（Evolution Risk Level）—— 本文档定义的 E1-E5**

这是在**已经拥有自演化能力的前提下**（即安装档位 ≥ L8），「演化什么东西」的风险分级。不同的演化对象需要不同严格程度的验证和人类参与：

| 演化风险层级 | 演化对象 | 风险 |
|-------------|----------|------|
| E1 | 配置参数（检索权重、阈值、衰减率） | 极低 |
| E2 | 提示词与模板（AGENTS.md、spec.md、技能提示词） | 中 |
| E3 | 非核心代码（工具脚本、插件、检索算法实现） | 高 |
| E4 | 核心代码（领域逻辑、治理、审计链） | 极高 |
| E5 | 架构与数据模型（分层、接口、schema） | 灾难性——**不允许自动演化** |

**两套体系的关系**：安装档位（L0-L9）决定系统**有没有**自演化能力；演化风险层级（E1-E5）决定在有自演化能力的前提下，**演化什么**需要多严格的验证。例如：一个 L9 档位的系统，可以自动演化 E1 参数，但演化 E4 核心代码仍需双人复核。

本文档后续使用 **E1-E5** 表示演化对象风险层级，使用 **L8/L9** 表示 v3 安装档位。

### 1.1 演化对象的风险分层（E1-E5）

不是所有东西都可以演化。按风险从低到高，演化对象分为五层：

| 风险层级 | 演化对象 | 风险 | v3 状态 | 演化方式 |
|----------|----------|------|---------|----------|
| E1 | **配置参数**（检索权重、阈值、衰减率、top_k） | 极低 | TUNABLES 硬编码 | 数值搜索/贝叶斯优化 |
| E2 | **提示词与模板**（AGENTS.md、spec.md、技能提示词、特色包内容） | 中 | 渲染产物，禁手改 | LLM 生成 + A/B 评估 |
| E3 | **非核心代码**（工具脚本、插件、检索算法实现） | 高 | 无 | LLM 生成 + 完整验证 |
| E4 | **核心代码**（领域逻辑、治理、审计链） | 极高 | 无（基准黑名单） | 仅 L9 档位，严格受限 |
| E5 | **架构与数据模型**（分层、接口、schema） | 灾难性 | 无 | 不允许自动演化，仅人类设计 |

**核心原则：演化权限必须小于系统赋予它的权限。** 演化引擎不能修改"规定演化引擎能做什么"的规则。

### 1.2 不可演化的核心（Immutable Core）

以下内容是系统的"宪法"，**任何层级的演化都不可触碰**，其 SHA-256 哈希被锁定并纳入 Merkle 根：

```
不可演化核心（Immutable Core）
├── laws/                    # 6 条铁律（系统宪法）
│   ├── law-01-no-deletion.md
│   ├── law-02-evidence.md
│   ├── law-03-citation.md
│   ├── law-04-audit-only.md
│   ├── law-05-no-secrets.md
│   └── law-06-slow-lane.md
├── charter/                 # 宪章（演化规则本身）
│   ├── evolution-charter.md    # 演化的范围、条件、限制
│   └── immutable-core.manifest # 不可演化核心的清单+哈希
├── guard/                   # 守卫脚本（检查变异合法性）
│   ├── guard.py                # diff 检查 + 安全扫描
│   └── immutable-core.sha256   # 不可演化核心的哈希锁
├── tests/core/              # 核心测试套件（验证系统行为）
│   ├── test_laws.py            # 铁律执行测试
│   ├── test_audit_chain.py     # 审计链完整性测试
│   ├── test_golden.py          # 黄金端到端测试
│   └── test_properties.py      # 属性测试（不变式）
└── evolution/               # 演化引擎本身
    ├── engine.py               # 演化循环
    ├── validator.py            # 验证套件
    └── sandbox.py              # 隔离环境
```

**为什么演化引擎本身不可演化？** 因为如果演化引擎可以修改自己，它可以移除安全检查、扩大演化范围、修改验证标准——这是经典的"规则修改者"攻击。v3 的宪章已经意识到这一点（"变异不得触碰基准黑名单"），v4 将其正式化为不可演化核心。

**不可演化核心的完整性检查**：每次演化操作前后、每次系统启动时，guard 都会计算不可演化核心所有文件的 SHA-256 哈希，与 `immutable-core.sha256` 锁定值对比。任何不一致立即触发紧急模式（拒绝所有写操作，通知人类）。

### 1.3 可演化表面（Evolvable Surface）

不可演化核心之外的所有内容都是可演化的，但不同层级有不同的演化条件：

| 演化风险层级 | 允许的操作 | 验证要求 | 人类参与 |
|----------|-----------|----------|----------|
| E1 参数 | 修改 TUNABLES 数值 | 性能基准不退化 + 黄金测试通过 | 无需（L9 档位下自动） |
| E2 提示词 | 修改模板内容 | 渲染产物对比 + 行为测试 | 每个变异确认（L8）/批量审查（L9） |
| E3 非核心代码 | 修改工具脚本/插件/检索实现 | 完整测试 + lint + 性能 + 安全扫描 | 每个变异确认（L8）/批量审查（L9） |
| E4 核心代码 | 修改领域逻辑 | 完整测试 + 黄金测试 + 属性测试 + 差分测试 + 红队测试 | 每个变异必须人类确认，且需双人复核 |
| E5 架构/schema | — | — | **不允许自动演化** |

## 二、自演化引擎的核心循环

### 2.1 七阶段演化循环

自演化引擎是一个持续运行的循环，每个循环处理一个候选变异：

```
┌──────────────────────────────────────────────────────────────────┐
│                        演化循环（Evolution Loop）                   │
│                                                                      │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐  │
│  │ 1. 感知   │───→│ 2. 假设   │───→│ 3. 变异   │───→│ 4. 验证   │  │
│  │ Perceive │    │Hypothesize│    │ Mutate   │    │ Validate │  │
│  └──────────┘    └──────────┘    └──────────┘    └────┬─────┘  │
│                                                          │         │
│                                                          ▼         │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐  │
│  │ 7. 审计   │←───│ 6. 应用   │←───│ 5. 选择   │←───│ 验证结果 │  │
│  │  Audit   │    │  Apply   │    │  Select  │    │          │  │
│  └──────────┘    └──────────┘    └──────────┘    └──────────┘  │
│                                                                      │
│  任何阶段失败 → 记录到审计链 → 回到感知阶段（不应用变异）            │
└──────────────────────────────────────────────────────────────────┘
```

#### 阶段 1：感知（Perceive）

持续监控系统的运行状态，识别改进机会和问题：

```python
class PerceptionModule:
    """感知模块：监控系统状态，识别演化机会"""

    def collect_signals(self) -> EvolutionSignals:
        return EvolutionSignals(
            # 性能信号
            retrieval_p95_latency=self.metrics.get("retrieve.p95"),
            append_p95_latency=self.metrics.get("append.p95"),
            memory_usage_mb=self.metrics.get("memory.usage"),
            # 质量信号
            test_coverage=self.metrics.get("test.coverage"),
            lint_error_count=self.metrics.get("lint.errors"),
            # 行为信号
            retrieval_accuracy=self.eval.last_accuracy(),  # golden 集上的准确率
            user_feedback_score=self.feedback.avg_score(),
            # 错误信号
            error_rate=self.metrics.get("errors.rate"),
            recent_failures=self.audit.recent_failures(hours=24),
            # 演化信号
            time_since_last_evolution=self.audit.hours_since_last_evolution(),
            pending_hypotheses=self.hypothesis_store.count(),
        )

    def detect_opportunities(self, signals: EvolutionSignals) -> list[Opportunity]:
        """识别改进机会"""
        opportunities = []
        # 性能退化 → 优化机会
        if signals.retrieval_p95_latency > signals.baseline_p95 * 1.2:
            opportunities.append(Opportunity(
                type="performance_degradation",
                target="retrieval",
                description=f"检索 P95 延迟退化 20%（{signals.retrieval_p95_latency}ms）",
                priority="high",
            ))
        # 准确率低 → 检索算法改进机会
        if signals.retrieval_accuracy < 0.7:
            opportunities.append(Opportunity(
                type="low_accuracy",
                target="retrieval_algorithm",
                description=f"检索准确率 {signals.retrieval_accuracy:.1%}，低于阈值 70%",
                priority="high",
            ))
        # 定期探索 → 即使没有明显问题，也定期尝试改进
        if signals.time_since_last_evolution > 168:  # 7 天
            opportunities.append(Opportunity(
                type="scheduled_exploration",
                target="any",
                description="定期探索：尝试随机改进",
                priority="low",
            ))
        return opportunities
```

**感知的关键设计**：
- 信号来源多样化：metrics、评测集、用户反馈、审计链
- 有基线对比：不是看绝对值，而是看与历史基线的偏差
- 定期探索机制：即使系统"看起来很好"，也定期尝试改进（避免局部最优）
- 感知本身不可演化（属于不可演化核心）

#### 阶段 2：假设（Hypothesize）

基于感知到的机会，生成具体的改进假设：

```python
class HypothesisGenerator:
    """假设生成器：将改进机会转化为可测试的假设"""

    def __init__(self, llm: LLMClient, knowledge_base: EvolutionHistory):
        self.llm = llm
        self.history = knowledge_base  # 历史演化记录（成功/失败的变异）

    def generate(self, opportunity: Opportunity) -> list[Hypothesis]:
        # 1. 检索历史：类似的机会之前是怎么处理的？
        similar = self.history.search_similar(opportunity, top_k=5)

        # 2. LLM 生成假设（结合历史经验和当前机会）
        prompt = self._build_prompt(opportunity, similar)
        raw_hypotheses = self.llm.generate(prompt, max_count=5)

        # 3. 过滤和结构化
        hypotheses = []
        for raw in raw_hypotheses:
            h = Hypothesis.from_llm_output(raw)
            if self._is_valid(h):  # 范围检查、格式检查、不重复
                hypotheses.append(h)
        return hypotheses

    def _is_valid(self, h: Hypothesis) -> bool:
        # 演化目标必须在可演化表面内
        if not self.evolvable_surface.contains(h.target):
            return False
        # 不能与最近 10 次失败的假设重复
        if self.history.recent_failures().contains(h):
            return False
        return True
```

**假设的结构**：
```python
@dataclass
class Hypothesis:
    id: str
    description: str           # "将 BM25 的 k1 参数从 1.5 调整为 2.0"
    target: str                # 演化目标（文件路径 + 具体位置）
    evolution_risk_level: int      # E1-E4（演化对象风险层级）
    expected_improvement: dict # 预期改进（如 {"retrieval_accuracy": "+5%"}）
    risk_level: str            # low / medium / high
    rationale: str             # AI 的推理过程（为什么这个假设可能有效）
    validation_plan: str       # 如何验证这个假设
```

#### 阶段 3：变异（Mutate）

将假设转化为具体的代码/配置/提示词修改（diff）：

```python
class MutationGenerator:
    """变异生成器：将假设转化为具体的 diff"""

    def generate(self, hypothesis: Hypothesis) -> Mutation:
        if hypothesis.evolution_risk_level == 1:
            return self._mutate_params(hypothesis)
        elif hypothesis.evolution_risk_level == 2:
            return self._mutate_prompts(hypothesis)
        elif hypothesis.evolution_risk_level == 3:
            return self._mutate_code(hypothesis)
        elif hypothesis.evolution_risk_level == 4:
            return self._mutate_core_code(hypothesis)

    def _mutate_params(self, h: Hypothesis) -> Mutation:
        """E1：参数变异——直接修改 TUNABLES"""
        # 简单的数值搜索：在合理范围内采样
        new_value = self._sample_in_range(h.param_name, h.suggested_range)
        diff = self._make_param_diff(h.param_name, new_value)
        return Mutation(hypothesis=h, diff=diff, mutation_type="param")

    def _mutate_code(self, h: Hypothesis) -> Mutation:
        """E3：代码变异——LLM 生成代码修改"""
        # 1. 读取目标文件的当前内容
        current_code = self.file_reader.read(h.target_file)
        # 2. LLM 生成修改后的代码
        modified_code = self.llm.modify_code(
            current_code=current_code,
            instruction=h.description,
            constraints=self._code_constraints(h),  # 接口不变、类型不变等
        )
        # 3. 生成 diff
        diff = self._make_diff(current_code, modified_code, h.target_file)
        return Mutation(hypothesis=h, diff=diff, mutation_type="code")
```

**变异生成的关键约束**：
- E1 参数变异：纯数值操作，不需要 LLM，快速且安全
- E2 提示词变异：LLM 生成，需要渲染对比
- E3/E4 代码变异：LLM 生成，必须保持公共接口不变（除非假设明确要求接口变更，但 E4 才允许）
- 所有变异必须生成标准的 unified diff，guard 可以检查
- 变异大小受限：单次变异修改不超过 200 行（E3）/ 50 行（E4），防止大规模不可控修改

#### 阶段 4：验证（Validate）

这是自演化引擎的"免疫系统"，也是最关键的阶段。验证必须在**隔离环境**中进行，且验证套件本身属于不可演化核心。

```python
class ValidationSuite:
    """验证套件：七维度验证，全部通过才允许进入选择阶段"""

    def validate(self, mutation: Mutation, sandbox: Sandbox) -> ValidationResult:
        results = {}

        # 维度 1：guard 守卫（安全边界检查）——最优先，不通过直接拒绝
        results["guard"] = self.guard.check(mutation.diff)
        if not results["guard"].passed:
            return ValidationResult(passed=False, results=results,
                                     reason="guard 拦截：触碰不可演化核心或安全规则")

        # 维度 2：功能测试（完整测试套件）
        results["tests"] = sandbox.run_tests()
        if results["tests"].failures > 0:
            return ValidationResult(passed=False, results=results,
                                     reason=f"测试失败：{results['tests'].failures} 个失败")

        # 维度 3：黄金测试（固定输入输出，验证核心行为不变）
        results["golden"] = sandbox.run_golden_tests()
        if not results["golden"].passed:
            return ValidationResult(passed=False, results=results,
                                     reason="黄金测试失败：核心行为发生改变")

        # 维度 4：属性测试（验证系统不变式）
        results["properties"] = sandbox.run_property_tests()
        if not results["properties"].passed:
            return ValidationResult(passed=False, results=results,
                                     reason="属性测试失败：系统不变式被破坏")

        # 维度 5：差分测试（E3/E4 代码变异专用，验证新旧实现行为一致）
        if mutation.mutation_type in ("code", "core_code"):
            results["differential"] = self._differential_test(mutation, sandbox)
            if not results["differential"].passed:
                return ValidationResult(passed=False, results=results,
                                         reason="差分测试失败：行为不一致")

        # 维度 6：性能基准（关键操作不退化）
        results["performance"] = sandbox.run_benchmarks()
        if results["performance"].regression > 0.10:  # 退化超过 10%
            return ValidationResult(passed=False, results=results,
                                     reason=f"性能退化 {results['performance'].regression:.1%}")

        # 维度 7：代码质量（lint + 类型 + 复杂度 + 覆盖率）
        results["quality"] = sandbox.run_quality_checks()
        if not results["quality"].passed:
            return ValidationResult(passed=False, results=results,
                                     reason="代码质量检查失败")

        return ValidationResult(passed=True, results=results)
```

**验证环境（Sandbox）**：
```python
class Sandbox:
    """隔离验证环境：变异在此环境中验证，不影响生产库"""

    def __init__(self, production_lib: Path):
        self.workdir = tempfile.mkdtemp(prefix="lb-evolution-")
        # 1. 复制生产库到临时目录
        shutil.copytree(production_lib, self.workdir / "lib")
        # 2. 创建独立 venv
        self.venv = self.workdir / "venv"
        subprocess.run(["python", "-m", "venv", str(self.venv)])
        # 3. 安装依赖（含变异后的代码）
        self._install()
        # 4. 资源限制（通过 cgroups 或 ulimit）
        self._set_resource_limits(cpu=4, memory_mb=2048, time_sec=300)
        # 5. 网络隔离（默认禁止网络访问）
        self._disable_network()

    def apply_mutation(self, mutation: Mutation):
        """在沙箱中应用变异"""
        for file_diff in mutation.diff.files():
            self._apply_file_diff(file_diff)

    def run_tests(self) -> TestResult:
        """运行完整测试套件"""
        return self._run_in_venv(["pytest", "tests/", "-x", "--json-report"])

    def cleanup(self):
        """清理沙箱"""
        shutil.rmtree(self.workdir)
```

**沙箱的关键设计**：
- 完全隔离：独立文件系统、独立 Python 环境、独立网络命名空间
- 资源限制：CPU、内存、时间上限，防止变异导致无限循环或内存泄漏
- 网络隔离：默认禁止网络，防止变异下载恶意代码或泄露数据
- 一次性使用：每个变异用一个新沙箱，验证完立即销毁
- 不可演化：沙箱代码属于不可演化核心

#### 阶段 5：选择（Select）

多个候选变异都通过验证后，用多目标评估选择最优变异：

```python
class MutationSelector:
    """变异选择器：多目标优化，选择最优变异"""

    def select(self, candidates: list[ValidatedMutation]) -> Optional[ValidatedMutation]:
        if not candidates:
            return None

        scored = []
        for m in candidates:
            score = self._multi_objective_score(m)
            scored.append((score, m))

        # 按总分排序
        scored.sort(key=lambda x: -x[0])

        # 选择最优，但保留一定的探索概率
        if random.random() < 0.1:  # 10% 概率选择次优，避免局部最优
            return scored[min(1, len(scored)-1)][1]
        return scored[0][1]

    def _multi_objective_score(self, m: ValidatedMutation) -> float:
        weights = {
            "expected_improvement": 0.35,   # 预期改进幅度
            "actual_improvement": 0.25,      # 验证中实际测量到的改进
            "test_coverage_delta": 0.10,     # 测试覆盖率变化
            "performance_delta": 0.10,        # 性能变化（正向加分）
            "risk_level": -0.15,              # 风险（反向加权）
            "mutation_size": -0.05,           # 修改大小（越小越好，可审查性）
        }
        score = 0.0
        for criterion, weight in weights.items():
            value = self._normalize(m, criterion)
            score += weight * value
        return score
```

**选择策略的关键设计**：
- 多目标：不只看"是否通过测试"，而是综合评估改进幅度、风险、可审查性
- 探索 vs 利用：10% 概率选择次优变异，避免陷入局部最优
- 风险惩罚：高风险变异即使改进大也可能被低风险小改进取代
- 可解释性：每个选择都有评分明细，人类可以审查

#### 阶段 6：应用（Apply）

选中的变异不直接生效，而是经过灰度过程：

```python
class MutationApplier:
    """变异应用器：灰度发布 + 自动回滚"""

    def apply(self, mutation: ValidatedMutation) -> ApplyResult:
        # 阶段 A：影子模式（Shadow Mode）
        shadow_result = self._shadow_run(mutation, duration_hours=24)
        if not shadow_result.healthy:
            self._rollback(mutation, reason="影子模式异常")
            return ApplyResult(rejected=True, reason="影子模式异常")

        # 阶段 B：灰度发布（Canary）
        for percentage in [10, 30, 50, 100]:
            canary_result = self._canary_release(mutation, percentage, duration_hours=6)
            if not canary_result.healthy:
                self._rollback(mutation, reason=f"灰度 {percentage}% 异常")
                return ApplyResult(rejected=True, reason=f"灰度 {percentage}% 异常")
            if percentage < 100:
                self._wait_for_human_review(mutation, percentage)  # L8/L9 人类检查点
```

**灰度策略的关键设计**：
- 影子模式先行：变异版本"陪跑"但不影响用户，先观察 24 小时
- 渐进灰度：10% → 30% → 50% → 100%，每个阶段至少 6 小时
- 自动回滚：任何阶段异常（错误率上升、性能退化、行为差异）立即回滚
- 人类检查点：L8/L9 在每个灰度阶段之间需要人类确认
- 基于 Merkle DAG：应用变异 = 创建新 commit，回滚 = reset 到上一个 commit

#### 阶段 7：审计（Audit）

所有演化操作——无论成功失败——都完整记录到审计链：

```python
class EvolutionAuditor:
```

**审计的关键设计**：
- 完整记录：从感知到应用的每个阶段都有记录
- 包含 diff：变异的具体修改内容记录在审计事件中（可审查、可复现）
- 包含验证结果：每个维度的通过/失败详情
- 包含人类决策：L8/L9 的人类确认记录（谁、何时、决策）
- 不可篡改：审计链是 append-only 哈希链，属于不可演化核心的保护范围

## 三、安全边界的多层防御

自演化的安全不是靠单一机制，而是多层防御（Defense in Depth）：

```
┌─────────────────────────────────────────────────────────────┐
│                    第一层：范围限制                             │
│  可演化表面明确定义，E5 架构/schema 不允许演化                  │
│  不可演化核心的哈希被锁定                                       │
├─────────────────────────────────────────────────────────────┤
│                    第二层：guard 守卫                          │
│  每个变异的 diff 经过 guard 检查：                              │
│  • 不触碰不可演化核心文件                                        │
│  • 不扩大演化权限范围                                           │
│  • 不引入已知危险模式（eval/exec/网络访问/文件删除）            │
│  • 密钥扫描（不引入硬编码密钥）                                  │
├─────────────────────────────────────────────────────────────┤
│                    第三层：隔离验证                             │
│  变异在沙箱中验证：独立文件系统/venv/网络/资源限制              │
│  七维度验证：guard/测试/黄金/属性/差分/性能/质量                │
│  任何一维失败即拒绝                                             │
├─────────────────────────────────────────────────────────────┤
│                    第四层：人类参与                             │
│  L8：每个变异必须人类确认才能应用                                │
│  L9：批量审查 + 异常告警 + 否决权                               │
│  E4 核心代码变异：双人复核                                      │
│  任何人类可以随时暂停演化、回滚变异、否决假设                    │
├─────────────────────────────────────────────────────────────┤
│                    第五层：灰度与回滚                           │
│  影子模式 24h → 灰度 10/30/50/100% → 完全生效                │
│  任何阶段异常自动回滚（基于 Merkle DAG commit）                 │
│  回滚操作本身记录在审计链中                                      │
├─────────────────────────────────────────────────────────────┤
│                    第六层：持续监控                             │
│  已应用的变异持续监控：错误率/性能/行为一致性                    │
│  延迟异常检测（变异后 7 天内出现问题也可回滚）                  │
│  不可演化核心完整性定期检查（每次启动 + 每小时）                 │
└─────────────────────────────────────────────────────────────┘
```

### 关键攻击场景与防御

| 攻击场景 | 防御层 | 具体机制 |
|----------|--------|----------|
| AI 生成修改铁律的变异 | D1+D2 | 可演化表面不包含 laws/，guard 检查 diff 触碰 laws/ 即拒 |
| AI 生成修改 guard 脚本的变异 | D1+D2 | guard/ 属于不可演化核心，哈希锁定 |
| AI 生成修改核心测试的变异（让测试变简单） | D1+D2+D3 | tests/core/ 不可演化；黄金测试有固定断言；属性测试独立 |
| AI 生成引入后门的代码变异 | D2+D3+D4 | guard 扫描危险模式；沙箱网络隔离；人类代码审查 |
| AI 生成性能退化但测试通过的变异 | D3+D5 | 性能基准检查（退化>10%拒绝）；灰度期间性能监控 |
| AI 反复尝试类似的危险变异（暴力突破） | D3+D4 | 失败假设记录，近期重复假设自动拒绝；速率限制 |
| 演化引擎修改自己的验证标准 | D1 | evolution/ 属于不可演化核心 |
| 已应用的变异在运行时触发恶意行为 | D5+D6 | 影子模式+灰度监控；延迟异常检测；7天回滚窗口 |
| 人类操作员被社会工程学攻击 | D4 | E4 核心代码变异需双人复核；异常变异自动升级告警 |

## 四、检验方法：如何验证自演化机制本身

自演化引擎是"修改代码的代码"，它的正确性比被修改的代码更重要。以下是四个维度的检验方法。

### 4.1 有效性检验（Does it actually improve things?）

#### 4.1.1 改进率度量

```python
class EvolutionEffectivenessMonitor:
    """演化有效性监控"""

    def compute_metrics(self, window_days: int = 30) -> EffectivenessMetrics:
        cycles = self.audit.get_evolution_cycles(last_days=window_days)
        applied = [c for c in cycles if c.applied]
        rejected = [c for c in cycles if not c.applied]

        # 1. 接受率：多少变异被应用
        acceptance_rate = len(applied) / len(cycles) if cycles else 0

        # 2. 实际改进率：已应用变异中，多少带来了可测量的改进
        improved = sum(1 for c in applied if c.post_evolution_improvement > 0)
        improvement_rate = improved / len(applied) if applied else 0

        # 3. 平均改进幅度
        avg_improvement = np.mean([c.post_evolution_improvement for c in applied]) if applied else 0

        # 4. 退化率：已应用变异中，多少导致了退化（需要回滚）
        rolled_back = sum(1 for c in applied if c.was_rolled_back)
        regression_rate = rolled_back / len(applied) if applied else 0

        return EffectivenessMetrics(
            total_cycles=len(cycles),
            acceptance_rate=acceptance_rate,
            improvement_rate=improvement_rate,
            avg_improvement=avg_improvement,
            regression_rate=regression_rate,
        )
```

**有效性基准**（v4.0 发布时的目标）：
| 指标 | 最低可接受 | 目标值 |
|------|-----------|--------|
| 接受率 | 10%-50%（太低=太保守，太高=太激进） | 20%-30% |
| 实际改进率 | > 50% | > 70% |
| 退化率（回滚率） | < 10% | < 5% |
| 每月有效改进数 | > 2 | > 5 |

#### 4.1.2 演化基准测试集（Evolution Benchmark）

设计一个专门的测试集，包含已知的改进机会和陷阱，评估演化引擎的发现能力和避坑能力：

```
evolution-benchmark/
├── known_improvements/      # 已知改进集：N 个"修改 X 会更好"的场景
│   ├── IMP-001-retrieval-weight/   # 检索权重需要调整（当前 k1=1.5，最优=2.0）

│   └── ...
```

**基准测试的运行方式**：
1. 将演化引擎指向 `known_improvements/` 中的每个场景，验证它能否发现并实现改进
2. 将演化引擎指向 `known_traps/` 中的每个场景，验证它能否避免陷阱（不应用退化变异）
3. 将 `security_challenges/` 中的攻击作为"假设"注入演化引擎，验证 guard 能否拦截
4. 每次演化引擎自身更新后，运行完整基准测试集，验证引擎能力不退化

**基准评分**：
```
演化引擎总分 = 改进发现率 × 0.3
             + 陷阱避免率 × 0.3
             + 安全拦截率 × 0.3
             + 回归通过率 × 0.1
```

### 4.2 安全性检验（Is it safe?）

#### 4.2.1 红队测试（Red Teaming）

- 每次演化引擎自身更新后：完整红队测试
- 每周：自动运行 10 个随机攻击

- 任何安全事件后：针对性红队测试

#### 4.2.2 不可演化核心完整性检查

```python
class ImmutableCoreVerifier:
    """不可演化核心完整性验证"""

    def verify(self) -> IntegrityReport:
        # 1. 计算当前不可演化核心所有文件的 SHA-256
        current_hashes = {}
        for filepath in self.manifest.files():
            current_hashes[filepath] = self._sha256(filepath)

        # 2. 与锁定值对比
        locked_hashes = self.manifest.locked_hashes()
        mismatches = []
        for filepath, current in current_hashes.items():
            locked = locked_hashes.get(filepath)
            if locked is None:
                mismatches.append((filepath, "MISSING_IN_MANIFEST", current))
            elif current != locked:
                mismatches.append((filepath, locked, current))

        # 3. 检查是否有新增文件（不在 manifest 中但在不可演化核心目录下）
        extra_files = self._find_extra_files()

        # 4. 检查审计链中是否有触碰不可演化核心的记录
        audit_violations = self.audit.search_touching_immutable_core()

        return IntegrityReport(
            passed=len(mismatches) == 0 and len(extra_files) == 0 and len(audit_violations) == 0,
            mismatches=mismatches,
            extra_files=extra_files,
            audit_violations=audit_violations,
        )
```

**完整性检查的触发时机**：
- 每次系统启动时
- 每次演化操作前后
- 每小时定时检查
- 人类手动触发（`lb evolution verify-integrity`）

**检查失败的响应**：
1. 立即进入紧急模式（Emergency Mode）：拒绝所有写操作和演化操作
2. 记录安全事件到审计链
3. 通知人类（CLI 告警 / HTTP 告警 / 邮件）
4. 提供诊断信息：哪些文件被修改、修改时间、可能的来源
5. 人类确认后才能退出紧急模式

#### 4.2.3 长时间运行稳定性测试

```python
class LongRunningStabilityTest:
    """长时间运行稳定性测试：连续运行 N 次演化循环，验证系统不崩溃、不退化"""

        for i in range(num_cycles):

                    if not health.healthy:
                        return StabilityReport(
                            passed=False,
                            failed_at_cycle=i,
                            health_issue=health.issue,
                        )
            except Exception as e:
                return StabilityReport(
                    passed=False,
                    failed_at_cycle=i,
                    exception=str(e),
                )

        final_state = self._snapshot_system_state()
        return StabilityReport(
            passed=True,
            cycles_completed=num_cycles,
            initial_state=initial_state,
            final_state=final_state,
            state_diff=self._diff_states(initial_state, final_state),
        )
```

**稳定性测试的通过标准**：
- 1000 次演化循环无崩溃
- 不可演化核心哈希始终不变
- 审计链始终连续（无断链、无篡改）
- 系统性能退化 < 5%（与初始状态对比）
- 测试覆盖率不下降
- 没有任何演化操作触碰不可演化核心

### 4.3 可控性检验（Can humans control it?）

| 检验项 | 方法 | 通过标准 |
|--------|------|----------|
| 人类否决权 | 应用一个变异后，人类执行否决命令 | 变异被回滚，系统恢复到变异前状态，审计链记录否决 |
| 暂停机制 | 演化运行中执行暂停命令 | 正在进行的循环完成后停止，不启动新循环，状态可恢复 |
| 速率限制 | 配置每天最多 5 次演化，触发 6 次 | 第 6 次被拒绝，记录到审计链，通知人类 |
| 范围控制 | 配置只允许演化 E1 参数，尝试 E3 代码变异 | E3 变异被拒绝，错误信息明确说明范围限制 |
| 透明度 | 查询任意历史演化循环 | 能看到完整的七阶段记录：感知信号、假设、diff、验证结果、选择分数、灰度结果、人类决策 |
| 紧急停止 | 模拟演化引擎失控（快速生成大量变异） | 人类执行紧急停止，所有演化立即终止，系统进入只读模式 |
| E4 双人复核 | 尝试应用一个 E4 核心代码变异，只有一人确认 | 变异被拒绝，要求第二人确认 |
| 回滚窗口 | 应用变异 7 天后发现问题 | 仍可回滚到变异前的 commit |

### 4.4 可解释性检验（Can humans understand it?）

自演化的每个决策都必须对人类可解释：

```python
class EvolutionExplainer:
    """演化决策解释器"""

    def explain_cycle(self, cycle_id: str) -> EvolutionExplanation:
        cycle = self.audit.get_cycle(cycle_id)
        return EvolutionExplanation(
            # 为什么演化这个？
            why_this_target=f"感知到 {cycle.perception.trigger}，"
                           f"目标 {cycle.hypothesis.target} 的 "
                           f"{cycle.hypothesis.improvement_metric} "
                           f"当前值 {cycle.perception.current_value}，"
                           f"基线值 {cycle.perception.baseline_value}",
            # 假设是什么？
            hypothesis=cycle.hypothesis.description,
            # AI 的推理过程
            ai_rationale=cycle.hypothesis.rationale,
            # 变异改了什么？
            what_changed=cycle.mutation.diff.summary(),
            # 验证结果
            validation_summary=self._summarize_validation(cycle.validation),
            # 为什么选择这个变异（而不是其他候选）？
            why_selected=f"多目标评分 {cycle.selection_score:.3f}，"
                        f"在 {cycle.num_candidates} 个候选中排名第 1，"
                        f"主要优势：{cycle.selection_rationale}",
            # 灰度过程
            canary_summary=self._summarize_canary(cycle),
            # 人类决策
            human_decisions=[d.summary() for d in cycle.human_decisions],
            # 最终结果
            outcome="applied" if cycle.applied else "rejected",
            outcome_reason=cycle.outcome_reason,
        )
```

**可解释性要求**：
- 每个演化循环的解释可以通过 `lb evolution explain <cycle_id>` 查看
- 解释包含完整的"为什么"链条：为什么演化这个目标 → 假设是什么 → 改了什么 → 验证结果如何 → 为什么选择这个 → 灰度过程 → 人类决策 → 最终结果
- AI 的推理过程（rationale）必须记录和展示，不允许"黑箱决策"
- 解释语言为自然语言（中文），不只是原始数据

## 六、关键设计决策与权衡

### 6.1 为什么不可演化核心包括演化引擎本身？

**风险**：如果演化引擎可以修改自己，它可以：
- 移除 guard 检查，然后修改任何文件
- 弱化验证套件，让危险变异通过
- 修改审计链，删除自己的操作记录
- 扩大演化范围，从 E1 扩大到 E5

**防御**：演化引擎的代码属于不可演化核心，哈希锁定。演化引擎的**参数**（探索率、选择权重等）可以演化（E1），但**代码逻辑**不可演化。

**权衡**：这意味着演化引擎的 bug 修复需要人类手动操作（不能通过自演化修复）。但这是值得的——"修改修改者的代码"是最危险的操作，必须由人类控制。

### 6.2 为什么 E4 核心代码允许演化（尽管风险极高）？

**论点 1（不允许）**：核心代码是系统的基础，任何修改都可能破坏系统的基本性质。应该完全冻结。

**论点 2（允许，但严格受限）**：核心代码也有 bug 和性能问题，完全冻结意味着这些问题永远无法自动修复。只要有足够的验证（黄金测试+属性测试+差分测试+红队测试+双人复核），E4 演化是可控的。

**决策**：允许 E4 演化，但限制最严格：
- 单次变异修改不超过 50 行
- 必须通过全部七维度验证 + 差分测试 + 红队测试
- 每个变异必须双人复核
- 灰度期延长（影子 48h + 灰度每阶段 24h）
- E4 变异的速率限制更严格（每周最多 1 个）
- 任何 E4 变异触发后，不可演化核心完整性检查频率提升到每 10 分钟一次

### 6.3 为什么需要影子模式而不是直接灰度？

**影子模式的价值**：
- 零风险：变异版本不影响用户，即使完全崩溃也无感知
- 行为对比：可以将变异版本的输出与生产版本逐请求对比，发现细微的行为差异
- 性能对比：在真实流量下测量变异版本的性能，比基准测试更准确
- 资源使用：观察变异版本在真实负载下的内存/CPU 使用

**代价**：
- 资源消耗：需要同时运行两个版本，双倍计算资源
- 实现复杂：需要请求复制、结果对比、异常处理
- 有副作用的操作难以影子化（如写入操作，不能真的写入两次）

**决策**：只读操作（检索、查询）使用影子模式；有副作用的操作（写入、演化）直接灰度（但在沙箱中验证过）。

### 6.4 演化速率应该多快？

**太快的风险**：
- 人类审查疲劳（L8 每个变异都确认，太多就不会认真看）
- 变异之间的交互效应难以追踪（A 变异和 B 变异的组合效果）
- 回滚复杂度上升（回滚 B 可能依赖 A 的状态）
- 系统不稳定（持续变化的系统难以调试）

**太慢的风险**：
- 改进速度慢，系统无法及时适应
- 演化引擎的价值无法体现

**决策**：
- E1 参数演化：每天最多 5 个，自动应用
- E2 提示词演化：每天最多 2 个，人类确认
- E3 非核心代码演化：每周最多 3 个，人类确认
- E4 核心代码演化：每月最多 1 个，双人复核
- 任意时刻只有一个变异在灰度中（不并行灰度）
- 两次演化之间有冷却期（E1: 1h, E2: 6h, E3: 24h, E4: 72h）

## 七、总结

### 7.1 自演化机制的本质

自演化不是"AI 随便改代码"，而是一个**受严格约束的、可验证的、可回滚的改进循环**。它的核心是：

1. **明确的边界**：什么可以演化、什么不可以，由不可演化核心和可演化表面定义
2. **完整的循环**：感知→假设→变异→验证→选择→应用→审计，七个阶段缺一不可
3. **多层防御**：范围限制→guard→隔离验证→人类参与→灰度回滚→持续监控，六层安全
4. **可验证性**：有效性基准、红队测试、完整性检查、稳定性测试、可控性测试、可解释性
5. **人类最终控制权**：任何时候人类可以暂停、否决、回滚、修改范围

### 7.2 v3 到 v4 的关键跃迁

| 维度 | v3（L8/L9 概念框架） | v4（自演化引擎） |
|------|----------------------|------------------|
| 变异来源 | 外部提供 diff（guard --diff） | 系统自动感知→假设→变异 |
| 安全边界 | 宪章文本 + 基准黑名单 | 不可演化核心（哈希锁定）+ 可演化表面（明确定义） |
| 验证环境 | 直接在生产库跑测试 | 隔离沙箱（独立文件系统/venv/网络/资源） |
| 验证维度 | run_tests 全绿 + lint | 七维度验证（guard/测试/黄金/属性/差分/性能/质量） |
| 应用方式 | 直接应用 | 影子模式→灰度发布→完全生效，自动回滚 |
| 人类参与 | --yes 跳过交互式确认 | L8 每个确认 / L9 批量审查 / E4 双人复核 |
| 审计 | 审计链记录操作 | 完整七阶段记录（含 diff、验证结果、选择分数、灰度过程） |
| 检验 | 无 | 演化基准 + 红队测试 + 完整性检查 + 稳定性测试 |
| 可解释性 | 无 | 自然语言解释每个演化决策 |

### 7.3 最危险的三个时刻

在自演化系统的生命周期中，有三个特别危险的时刻：

1. **第一次启用自动演化时**：系统第一次自主修改自己，所有安全机制第一次经受真实考验。必须从 E1 参数演化开始，运行至少 100 次循环无异常后，才考虑 E2/E3。

2. **演化引擎自身更新时**：演化引擎的代码属于不可演化核心，更新需要人类手动操作。但更新后的引擎可能有新的 bug 或安全漏洞。每次引擎更新后必须运行完整红队测试和稳定性测试。

3. **人类信任度上升时**：系统运行一段时间后，如果演化一直很成功，人类可能会放松警惕（"它一直很靠谱，随便它演化吧"）。这是最危险的——攻击者可能利用人类的信任，通过缓慢的、渐进的变异逐步突破边界。防御：定期红队测试（即使系统看起来很安全）、不可演化核心检查永不放松、E4 变异永远需要双人复核。
