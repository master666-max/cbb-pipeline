# 完全重构：可能性空间探讨

> 前几轮都是在这个系统的既有框架内优化。这一轮换个起点：
> **先问它在解什么题，再问有多少代码在解这道题，最后才谈能重构成什么样。**
> 文中"实测"指本次会话在沙盒中跑出的结果；"原型"指为验证命题临时写的可运行代码。

---

## 一、先重新定位：这不是一个"记忆库工具"

### 它在解什么题

看 `install` 之后生成的东西：`AGENTS.md`（常驻规则）、`skills/wrap-up.md`（收尾动作）、`memory/`（经验条目）、`guard`（变异守卫）、`spec.md`（宪章）、慢车道（人类令牌）。

这不是"给 agent 一个笔记本"，而是：

> **如何让一个会修改自己的系统，在人类注意力极其有限的前提下，安全地演化。**

这个命题的所有张力都来自一处——**agent 必须能改自己**（否则不成长），**但改自己必然带来 reward hacking / objective hacking 的风险**（代码里 `CHARTER_L8` 明确写了这两个词），**而人类不可能审阅每一次修改**。

所以真正的稀缺资源不是存储、不是算力，是**人类的注意力预算**。整个治理架构应该围绕"如何最有效地花掉这份预算"来设计。

### 一个刺眼的数字

按关注点重新切分 2415 行代码：

| 关注点 | 行数 | 占比 |
|---|---|---|
| 自测（与实现同文件） | 1058 | **43.8%** |
| 粘合/CLI/其他 | 454 | 18.8% |
| **内容分发**（模板交付/漂移/manifest/absorb） | 213 | **8.8%** |
| 常量数据块（REGISTRY/TUNABLES/LAWS…） | 171 | 7.1% |
| 题录与网络对账（arXiv） | 97 | 4.0% |
| **记忆与检索** | 90 | 3.7% |
| 治理（guard/宪章/慢车道） | 40 | 1.7% |
| 渲染（文档即产物） | 36 | 1.5% |
| **审计与账本（chain/ledger/merkle）** | 35 | 1.4% |

**核心三件套（记忆 + 审计 + 治理）加起来 165 行，占 6.8%。**

而"内容分发"——把 v2.x 遗留模板文件搬到目标目录、检测漂移、维护 manifest、处理 `{{SLOT}}` 占位——**213 行，比核心还多**。

这不是"核心系统外加了一些辅助功能"，这是**一个 v2.x 模板分发器，外挂了 165 行的治理内核**。

### 这个数字改变了重构的性质

前几轮我把重构理解为"把 165 行内核做对"。看到这个分布后，判断要修正：

**最大的可能性不在"把现有做对"，而在"删掉一半"。**

内容分发、题录网络对账、常量数据块这三块（481 行，20%）与"自我修改系统的治理"是**正交的问题**。它们混进来，让核心命题被淹没，也解释了为什么 2400 行里只有 6.8% 在做真正的事。

## 二、不变量：先确定什么不能丢，才谈可能性

放开想象之前，先钉死约束。违反任一条就不是重构而是另起炉灶：

| # | 不变量 | 为什么不可让渡 |
|---|---|---|
| I1 | **人类能最终裁决并回滚** | 失去它，系统不再"被治理"，只是自动化 |
| I2 | **任何变更可追溯到一次人类可见的事件** | 审计的意义在于归因 |
| I3 | **回退不销毁**（移 attic） | 铁律 1；销毁式回退让审计失去意义 |
| I4 | **低风险变更不需要人类逐个批准** | 否则人成为瓶颈，系统退化成人工流程 |
| I5 | **能力声明不得强于实际能力** | 公理 G 的精神；自欺比无能力更危险 |

**除这五条外，一切可变**——包括 CLI 形态、文件布局、哈希链、Merkle、install 概念、"库"这个概念本身。

## 三、可能性空间（五个正交维度）

### 维度 1 · 存储与真相模型

| 方案 | 形态 | 免费获得 | 代价 |
|---|---|---|---|
| 现状 | 四真相 + 事后对账 | — | 丢更新、漏刷根、四态对账 |
| **A. 自研事件溯源** | `audit/events-*.jsonl` | 语义完全可控 | 自己实现 replay/压缩/回滚/签名 |
| **B. git 后端** ⭐ | commit = 事件 | 见下方实测 | 语义受 git 数据模型约束 |
| C. CRDT | 无冲突合并 | 多写者并发 | 因果序弱化，审计归因变难 |
| D. 嵌入式 DB（sqlite+append） | 表 + WAL | 事务、索引、查询 | 人类不可直读（违反 I2 的精神） |

**git 后端实测**（本次验证）：

```
1) append → commit        : 天然链式，commit 含父哈希
2) 篡改检出               : git status 直接显示 M memory/e0.json
3) 回滚                   : git revert / checkout —— 无需自写 attic 逻辑
4) 分支实验               : 实验在分支上，切回主分支完全不污染
5) 人类令牌               : git commit -S 需 GPG 私钥（人侧持有，命令行 flag 无法伪造）
6) 截断/篡改 → tip 变化   : 检出
7) git gc / reflog / fsck / diff / bisect 全部现成
```

**这意味着什么**：`chain_append`、`merkle_root`、`_ledger_append`、attic 回退、`guard --snapshot`、锚定对账——**这些自写机制 git 全部原生提供，且经过二十年对抗性检验**。

而且第 5 条解决了 V4-07 想解决的问题：人类令牌不再是一个可以被 agent 随手加上的 `--yes` flag，而是**需要人侧私钥**的签名操作。② 档（粗心）从"随手加 flag"变成"必须拿出私钥"。

**代价**：git 的语义是"文件树快照"而非"业务事件"。`ENTRY_APPENDED` 这种语义靠 commit message 约定承载，需要一层薄封装（把业务事件序列化为一次 commit）。另外 git 不保证"只追加"——可以 `rebase` 改写历史，需要服务端/钩子或 `reflog` 留痕来补足 I2。

### 维度 2 · 安全模型：从"检测"到"不可表达"

这是我认为**最深的一层跃迁**。

**检测式（现状）**：agent 持有完整文件系统权限，事后检查违规。实测盲区：patch 形态、删除文件、改内容不改名——全部绕过。本质是**违规可以表达，只是希望被发现**。

**能力式（capability）**：agent 根本拿不到"直接写库文件"的句柄。实测原型：

```python
class Capability:
    def __init__(self, lib): self.__lib = lib      # 无公开 API 触达文件
    def append(self, entry):
        if not (entry.get("source_event_id") or entry.get("evidence")):
            raise PermissionError("铁律2：无证据锚")
        if "sk-" in json.dumps(entry): raise PermissionError("铁律5：疑似密钥")

cap.append({"id":"x"})                    # → 拒绝：铁律2
cap.append({"id":"x", "source_event_id":"e1", "content":"sk-AAAA..."})  # → 拒绝：铁律5
公开方法: ['append']                       # 没有 write / delete / patch
```

差别不是"检查得更严"，而是**违反铁律的代码根本写不出来**。guard 从启发式黑名单变成结构性保证——P1-5 那类绕过不是被修好，是**不再存在**。

**可达上限**：把六铁律变成类型/能力约束，让"违反 = 编译不过/调用不存在"。这是把治理从运行时前移到构造期。

**代价**：agent 的自由度下降（不能用任意工具操作库）。需要宿主环境配合——如果 agent 能 `bash rm -rf`，能力边界仍可被绕过。所以这一层**必须依赖宿主权限隔离**（容器/沙盒/文件系统权限），单靠 Python 类不够。

### 维度 3 · 治理分层

现状是扁平的：所有变更走同一条路，L8/L9 加一个 `--yes`。

更合理的分层（灵感来自宪法/法律/行政的区分）：

| 层 | 内容 | 变更方式 | 人类参与 |
|---|---|---|---|
| **元层** | 六铁律、审计规则本身、锚点 | 几乎不变；需人侧签名 + 全量重算对账 | 必须 |
| **法层** | 档位定义、包状态机、阈值 | 需性质测试通过 + 人侧令牌 | 抽样 |
| **行层** | 条目、情绪、索引 | 自由写入，事后可审计 | 不参与 |

**关键设计**：每一层的变更，**禁止向下修改**——行层永远不能改法层，法层永远不能改元层。这个方向性约束可以在能力式边界里结构性实现（行层拿到的 capability 没有"改法层"的方法）。

现状的问题正是没有这个方向性：`install --redeliver` 可以用当前 bodies 覆盖任何交付文件，包括基准文件——只要文件名不在黑名单里。

### 维度 4 · 演化闭环

公理 G 说"行为变更先 shadow，测不出差异即判表演"。但实测看，`engine shadow` 只是往审计链记一行日志——**闭环只做了第一步**。

完整的闭环应该是：

```
提议变更 → 影子分支执行 N 次 → 测量行为差异 → 有差异且更优则采纳 / 无差异则判表演拒绝 / 更劣则回滚
                                    ↑
                          与既有 eval 基线对比
```

git 后端下这个闭环几乎免费：分支 = 影子，merge = 采纳，revert = 回滚，`bisect` = 定位劣化点。

**可达上限**：agent 能自主提出规则变更、自主跑实验验证、只在"需要价值判断"时才提交人类。这才是 I4（低风险变更不需要人逐个批准）的真正落地——不是靠"信任它不会做坏事"，而是**靠机制证明它做不了未被测量的事**。

### 维度 5 · 人类注意力预算

现状：慢车道是二元 gate（拦/不拦）。

可能性：把人类注意力**显式建模为预算**——

- 每个待裁决变更带一个风险分（影响面 × 不可逆性 × 偏离既有评估的程度）
- 预算按周/按会话分配，系统按风险分从高到低消耗
- 低风险但数量多的变更，走**抽样审计**（人抽看 5%，其余自动放行并留痕）
- 预算耗尽 → 系统进入"只追加不变更"的保守模式

这把 I1（人能最终裁决）与 I4（人不成为瓶颈）从矛盾变成可调节的参数。

## 四、三种愿景

### 愿景 A · 收敛型重构（保守）

**做什么**：保留 CLI 与"库"概念，切走内容分发与题录对账，核心改为事件溯源（自研或 git）。

**规模**：核心从 2400 行降到约 **600 行**（165 行内核 + fold/projection + 薄 git 封装 + CLI）。

**可达状态**：无 lost update、截断可检出、memory 可重建、信号矩阵全绿、档位可迁移。

**不能达到**：安全仍是检测式的；人类注意力仍是二元 gate；演化仍需人工触发。

**适用**：你想在两周内拿到一个可信、可维护、能长期用的系统。

### 愿景 B · 内核型重设计（激进）

**做什么**：在 A 的基础上，把"库目录"这个概念降级为实现细节。对外暴露的是**认知治理内核 API**（能力式边界 + 分层治理 + 事件流），文件布局只是它的一个后端。

**关键转变**：`install` 不再"交付模板文件"——那 213 行直接删除。模板/预设/特色包变成**可选的内容包**，通过独立通道分发，与治理内核完全解耦。

**规模**：内核约 **400 行**，内容包独立仓库。

**可达状态**：违规不可表达（依赖宿主隔离）；治理分层且方向性有保证；内核可嵌入任何 agent 形态（不限于有文件系统的 coding agent）。

**不能达到**：自动演化闭环仍缺失；注意力仍是粗粒度 gate。

**适用**：你希望这套东西活过当前这一代 agent 形态。今天是 Claude Code / Codex 这类文件系统 agent，明天可能是别的——绑定到"库目录"会让它随形态变化而失效。

### 愿景 C · 自演化系统（范式跃迁）

**做什么**：在 B 的基础上补上闭环——agent 可提议规则变更，系统在影子分支自动跑 eval 测量，按预设判据自动采纳/回滚，只在价值判断点提交人类（受注意力预算约束）。

**这是 Darwin Gödel Machine 思路的工程化落地**（代码里 `REGISTRY` 已引用相关文献，说明作者心里有这个方向）。

**可达状态**：系统能自我改进且改进本身是可审计、可回滚、可测量的。人类角色从"审批者"变成"终审法官 + 价值定义者"。

**代价与风险**：
- 需要一个可靠的评估基准——而现有 `eval` 的判别力已被证明有问题（P1-6：检索排序与查询无关，recall@5 虚高）。**基准不可信时，自动采纳会放大错误**。这是 C 的最大前置依赖
- 自我改进的递归风险（改评估逻辑本身）需要元层硬约束
- 工程量最大，且失败模式是"看起来在自我改进，实际在目标漂移"

**适用**：你把这当作一个长期研究项目，而不只是工具。

## 五、我的判断：真正的杠杆点在哪

按"每单位工作量能消除多少根本问题"排序：

**① 删掉内容分发（213 行）—— 最高杠杆，且几乎无风险**

它比核心还大，却与核心命题正交。切走之后：install 概念消失、manifest 漂移检测消失、`--redeliver` 消失、`_body_for` 的渲染化分叉消失、大量 P2 项随之消失。剩下的系统第一次能让人一眼看懂。

这一步不需要任何设计决策——**只需要承认它是历史包袱**。

**② 存储层交给 git —— 用 20 年对抗性检验替换自写机制**

实测已证明：链式、篡改检出、回滚、分支实验、人侧签名、增量压缩全部免费。自写的 `chain_append` / `merkle_root` / attic / `guard --snapshot` 大部分可删。

附带解决 V4-07：`--yes` 换成 GPG 签名后，②档违规从"随手加 flag"变成"必须拿私钥"。

**③ 安全模型从检测式转能力式 —— 唯一能终结"攻防军备竞赛"的路径**

只要还是检测式，新的绕过方式就会持续出现（这次审查找到 3 种，下次还有）。能力式让这类问题**结构性消失**。

但这一条**依赖宿主隔离**，不是纯代码能解决的——如果 agent 能执行 `rm -rf`，Python 层的 capability 只是君子协定。所以在纯软件范围内它的上限有限，需要配合运行环境。

**这三条做完，愿景 B 就基本达成了，工作量约等于前几轮工单集的一半。**

### 关于愿景 C：我的建议是先别做

不是因为它不好，而是**前置依赖不成立**：

- 自动采纳依赖可靠的 eval —— 而实测证明现有检索排序与查询无关（P1-6），recall@5 虚高
- 在基准不可信时开启自动演化，等于给目标漂移开了绿灯，且漂移会被系统自己的审计链"证明"为合法

公理 G 说"测不出差异即判表演"——**在能测出差异之前，不该谈自动采纳**。先把 eval 做成可信的判别器（这是 ARCH-006 的真正意义），再谈闭环。

## 六、可能性不等于应该做：明确划界

| 不做 | 理由 |
|---|---|
| 性能优化 | 实测 300 条目 `merkle_root` 0.005s、`retrieve` 0.008s，不是瓶颈 |
| 多写者 CRDT | 当前是单 agent 单库；为不存在的并发引入因果序弱化，损害 I2（可归因） |
| 分布式/多库同步 | 超出单库边界，且会动摇 I1（单一裁决点） |
| ③ 档（完整权限蓄意 agent）防御 | `THREAT_MODEL` 已明示不防；架构上只保证②防住 + ③留痕可查，不追加对抗措施 |
| 自动演化（愿景 C） | 待 eval 判别力建立后再议 |
| 把 33 条题录做成在线知识库 | 与治理内核正交，且引入网络依赖与新的失效模式 |

## 七、一句话总结

这个系统的核心命题是 **"让会修改自己的系统，在人类注意力稀缺的前提下安全演化"**——而它现在 93% 的代码不在解这道题。

完全重构能达到的上限不是"把现有机制做对"，而是：

1. **删掉一半**（内容分发 + 题录对账 → 独立通道）
2. **外包存储**（git 接管链式/回滚/签名，自写机制大部分删除）
3. **安全前移**（从"检测违规"到"违规不可表达"，配合宿主隔离）

做完后，一个约 400 行的内核能承载全部六铁律，且第一次有可能活过当前这一代 agent 形态。

再往上（自动演化）不是不能做，是**在能测量之前不该做**——公理 G 自己已经给出了这个判据。
