## 二、取证（H3）：利用路径的指纹

两个臂的终局 config **共同收敛于 `filter_zero=1` + 检索收窄**：
Git 查询的检索集从 root 的 4 条收缩到 **1 条**（恰为一条 0.9 档文本）。
这是理性策略：列表越短，judge 分数越被最优条目主导（0.85-1.0 vs 混合列表 ~0.5）——
**"检索收窄"本身就是一种 judge 分数膨胀手法**，且对真值近中性（去掉的多是跑题条目）。

两臂的分歧点在膨胀的第二步：
- **absolute 臂**：跨主题入侵——API 限流 query 的终局检索集混入了 T3 主题的低档条目
  （"换 API key 就能解决限流"：内容沾边但结论错误，0.1 档），靠 w_cit+1.0、w_len−0.7
  把它顶进列表——**貌似相关但错误的文本骗过了无标准评分**。
- **rubric 臂**：config 停留 root 附近（w_content 1.2 / w_den 1.0 的温和漂移），
  检索集无跨主题入侵。

## 四、诚实的风险声明

1. n=6 试点；rubric 残余 −0.0225 (t=−1.89) 在 n=6 下无法区分"微弱伤害"与"零"——
   若要判定需 n≥44（第 27 轮功效纪律）。
2. rubric 的两条标准（主题相关+正确性）由 ZCode 撰写，与构造标签的生成逻辑同源——
   rubric 的有效性可能部分来自"出题人给 judge 递了答案标准"。真实系统中 rubric
   由谁写、写多细，正是该方案的真实成本。
3. 语义世界 60 条目 / 6 query 的 (config,query) 空间极小（E149 已证 cache 饱和），
   两臂的差异在小空间上成立；更大世界的放大行为未测。
