# 自演化 · E150：演化活跃度指标落地

> 任务：E149 证明 mutate_dead **静态 +0.0000 / drift 下 −0.1625**，
> 说明**增益不是健康的充分指标**——静止的系统增益恒为 0，永远不会变负。
>
> 本轮把"演化活跃度"做成内核硬指标。
> **验收 43 → 53 项，全过。**
>
> 实验：`proto/kernel.py` + `proto/verify_kernel.py`（T21–T24）

---

## 一、内核改动

```
KernelConfig：
  activity            = True    # 开关
  activity_win        = 4       # 滑动窗口代数
  activity_min        = 1       # 窗口内至少需要的有效变化
  activity_after_drift = 2      # drift 后几代内必须适应

Kernel：
  _activity_hist      每代"核心维度变化"数
  inactive_streak     连续停滞代数
  activity_alerts     累计告警
  _record_activity()  滑动窗口判定
```

告警分两级：
1. **演化停滞**：近 4 代核心维度变化 < 1
2. **drift 后无法适应**：检出于第 N 代，此后 2 代核心维度零变化

---

## 二、⭐ 关键设计：只看【核心维度】

第一版统计 `child != parent`（任意维度变化），**测不出来**。

```python
CORE_DIMS = ("w_kw", "w_content", "w_imp", "w_age", "filter_zero", "deep")
# 表象维度 w_len/w_fmt/w_den/w_cit 不计入
```

原因（T24 构造）：核心维度冻结、表象维度乱变时——

| 指标 | 表现 |
|---|---|
| 采纳数 | **3**（停摆监控**不会**触发） |
| 任意维度变化 | 64（第一版认为"很活跃"） |
| **核心维度变化** | **0** ✅ |

> **这是在"看起来正常运转"的情况下彻底失效**。
> 表象维度乱变甚至会让 judge 分上升 → 被"采纳" → 所有基于增益的监控都认为正常。

这与 E81 的自我美化、E85 的膨胀 349 倍是同一类问题：
**系统可以在被监控的维度上表现良好，同时在真正重要的维度上完全不动。**

---

## 三、与停摆监控的分工

| | 看什么 | 捕获什么 |
|---|---|---|
| 停摆监控（E44） | **零采纳** | 门槛过高、搜索失败 |
| **活跃度（E150）** | **零变化（核心维度）** | mutate_dead、核心维度冻结 |

**实测互补性（T24）**：核心冻结 + 表象乱变时
采纳 = 3（停摆未触发），但活跃度告警 = 13。

> 这是第 5 个"配对机制"的实例：
> **两个监控看不同的东西，任何一个单独都不够。**

## 五、识别到的一个自己的错误

第一版实现完，我写了 T21/T22/T23 就准备收工。
但诊断脚本显示：`mutate_dead` 下 **采纳数也是 0**——
**停摆监控本来就能抓住它**，那活跃度就是重复的。

我没有接受这个结果，而是构造了 T24（核心冻结 + 表象乱变），
才发现**真正需要活跃度的场景不是"完全不动"，而是"在错的维度上动"**。

> 如果当时接受了"停摆已覆盖"的结论，就会交付一个冗余指标。
