# bootstrap_v3.py 架构优化建议 · 深度篇

> 本篇聚焦**公理与实现之间的落差**，不重复前两份文档中已覆盖的工程结构层问题（异常化/分层/UoW/检索层）。
> 所有结论均经实测验证，验证代码与输出附在各条目下。

---

## 核心论断

这个系统宣告了六条公理（A 单一事实源 / D 双平面 / E 根锚定 / G 可证伪…），但**架构上真正承载它们的执行机制只有两个**：哈希链（append-only）与 Merkle 快照。

其余部分靠三样东西支撑：字符串常量（`LAWS`、`THREAT_MODEL`）、168 条 `assert`、以及 `doctor` 的事后对账。

**公理宣告的强度 > 实现承载的强度**——这个落差是全部 P0/P1 的共同根源。下面的建议按"能消掉多少落差"排序。

---

## 一、根本问题：公理 D（双平面）在物理上不成立

### 现状

公理 D 写明：`lifelog = 审计面（真相源）`；`记忆条目 = 投影（必带 source_event_id）`。

即：**memory/ 应该能从 audit/ 重建出来**。

### 实测

```
审计链中关于条目 e0 的全部信息:
  - 2026-09-07 19:20 | prev:fd6737a6… | h:df1822424f56b8f8…  | entry:e0 → intermediate
memory 中 e0: 10 个字段，content = "条目正文0的关键内容"
→ audit 是否含条目内容: False
```

审计链只记 `entry:{id} → {tier}`——**一个指针，不含 payload**。

### 这意味着什么

真相的载体（条目内容）**只存在于 memory/ 里**。audit 不是真相源，它是一本指针日志。

于是系统实际是**四条独立写入流**：`audit/`（事件指针）、`ledger/`（变更流水）、`memory/`（内容正本）、`state.json`（派生量快照）。`doctor` 的四方对账不是"投影 vs 真相"的校验，而是**四个平行真相的交叉核对**。

这解释了一组看似无关的问题为什么扎堆出现：

| 现象 | 根因 |
|---|---|
| P0-4 并发丢更新 92% | `state.json` 是独立真相，必须 read-modify-write |
| P1-8 三处漏刷根 | 根是手抄的派生量，抄漏了就失真 |
| P1-7 同 id 跨层共存 | 唯一性没有单一裁决点 |
| doctor 需要四种差异检测 | 四个真相需要两两对齐 |

### 建议：转向事件溯源

```
audit/  = 唯一 append-only 事件流（每条事件携带完整 payload）
memory/ = fold(events) 的物化视图
state   = fold(events) 的物化视图
ledger/ = 事件的读优化索引（或并入 audit）
```

**收益（一次性消灭）**：lost update（视图是 fold 结果，无 read-modify-write）、漏刷根（根是 fold 产物，不可能漏）、id 冲突（fold 时唯一性天然保证）、doctor 四态对账（退化为"重建 vs 现有"的单一校验）。篡改检测也从"Merkle 事后比对"升级为"重建结果不一致"——语义更强。

**代价**：审计链需要携带 payload（体积增大）；需要视图版本化与 replay；存量库需要迁移（把现有 memory 固化为 genesis 事件）。

**建议分两步走**：

1. **第一步（改动小、收益最大）**：只把 `state.json` 改为 fold 产物——`importance_accum`、`emotion`、`merkle_root` 全部从 `ledger/changes.jsonl` + `audit/` 重算。这一步直接消掉 P0-4，且不需要动 memory 的物理格式。
2. **第二步**：审计事件带 payload，memory 成为可重建视图。存量库通过 `migrate` 把现有条目固化为 `genesis` 事件。

## 二、安全硬伤：截断攻击无法被检出

这是本次验证中**最值得立刻修**的一条，严重性高于 guard 绕过（BUG-005）——因为它打击的是审计面本身。

### 实测

```
构造：append 5 条 → 删掉 audit 尾部 2 行 → 重算 Merkle 根并更新 state.json
doctor 输出: memory 5 / audit 3 / ledger 5 / 审计链 连续 / state 根一致
→ 是否检出截断: False
```

**完全没检出。**

### 原因

Merkle 根锚定的是**内容集合**，不锚定**序列长度**。截断后剩余各行仍然自洽——每行的 `prev` 指向前一行，逐行重算全部通过。只要攻击者同步更新 `state.json` 里的根（或用官方 `wrapup` 自然产生一个新根），截断就永久隐形。

`state.json` 里没有任何字段记录"链应该有多长"或"链尾是什么"：

```
→ state 中是否存在链尾哈希字段 chain_tip: False
```

### 建议：双重锚定

`state.json` 增加 `chain_tip`（审计链最后一行的哈希），与 `merkle_root`、`package_sha256` 一起构成**三元组锚点**纳入人侧保管：

| 锚点 | 防护对象 |
|---|---|
| `chain_tip` | 事件序列的长度与顺序（防截断、防回滚、防重放截断） |
| `merkle_root` | 内容集合（防改文件、防加文件、防删文件） |
| `package_sha256` | 安装器自身（防包被替换） |

`doctor` 增加一项校验：`chain_tip` 与当前链尾是否一致。

**诚实边界**：这仍防不住"重放整个库并同步更新全部三个锚点"——但那属于威胁模型已声明不防的 ③ 档（完整权限蓄意 agent）。② 档（SOP 约束下的粗心/意外）必须防住，而当前状态是**声明防 ②、实际防不住 ②**。

## 三、可观测性：单一健康信号过载，正在导致告警脱敏

### 现状

`merkle_root` 一个信号同时承担三个职责：

1. 内容完整性（有人改了文件）
2. 写入纪律（某条写路径漏刷了根）
3. 篡改检测（有人恶意修改）

而 P1-8 已证明：**正常操作就会触发它**（`eval` / `reflect` / `guard --snapshot` 之后 doctor 必然报"根不一致"）。

### 后果

只用官方命令、不做任何篡改，doctor 就说"根不一致 / 差异等用户裁决"。用户很快会对这个信号脱敏——**真正的篡改被淹没在噪声里**。这是可观测性设计的经典反模式：一个既报故障又报正常的信号，等于没有信号。

### 建议：拆成独立信号矩阵

| 信号 | 含义 | 数据来源 |
|---|---|---|
| `chain_integrity` | 链连续 + tip 匹配 | 逐行重算 + `chain_tip` |
| `content_drift` | manifest 在册文件被改 | 64→256bit manifest 比对 |
| `unregistered` | 新文件未在册（注明 `memory/` 是盲区） | 目录扫描 |
| `view_freshness` | 物化视图落后于事件流 | 事件数 vs 视图版本 |
| `anchor_match` | 与人侧三元组锚点比对 | 人侧输入 |

每条独立报告、独立决定是否阻塞。doctor 输出从"五态全一致"这种二元结论，改为**信号矩阵 + 每条信号的可信度**。

关键原则：**正常路径必须产生全绿**。任何"正常操作也会报警"的信号都要么修复、要么拆出去。

## 四、档位是一等生命周期，而非出厂设置

### 现状

`level` 在 install 时写死进 `state.json`，之后没有任何变更路径。`--redeliver`（L799-830）只修漂移文件，不改档位。

想从 L2 升到 L5 → 只能重装 → 撞上 P0-3（脏目录 + 无条件覆盖用户文件）。

而 `LEVELS` 的定义（L123-134）本身就是累积式的（`L5.adds ⊇ L3.adds`），说明作者心里档位是可叠加的——但没给叠加的操作入口。

### 建议

`engine upgrade --to L5` 作为一等公民操作：

```
resolve(目标档位) → 与当前档位求差集 → 只交付新增部分 → 入账本 + 入审计链 → 更新 state.level
```

- 旧档位内容**不删除**（铁律 1），只是新档位内容叠加
- 反向 `downgrade` 只做标记（`state.level` 变更 + 账本记录），不移除任何文件
- 升档涉及 L8/L9 时，慢车道门禁同样生效（现有 N-004 逻辑可复用）

## 五、特色包的价值主张尚未落地

### 现状

`PACKAGES`（L165-178）为 12 个包各定义了 `libs` 与 `ledger`，例如：

```
"x-writing": {"libs": [...], "ledger": "伏笔账本(planted/recovered)"}
"x-life":    {"libs": [...], "ledger": "承诺账(made/kept/broken)+决策日志"}
```

但代码里**没有任何状态机实现**。包 = 一个目录 + 一个 README 模板（`render_pkg_template` L381-389）。

也就是说：特色包最差异化的部分（账本状态机）恰恰是完全没实现的部分。12 个包目前退化成了 12 个文件夹 + 12 句描述。

### 建议

把 `ledger` 从字符串升级为**声明式状态机定义**：

```python
"x-writing": {
  "libs": [...],
  "ledger": {
    "states": ["planted", "recovered", "abandoned"],
    "transitions": {"planted": ["recovered", "abandoned"], "recovered": []},
    "required_fields": ["planted_at", "chapter"]
  }
}
```

提供通用命令 `engine ledger --pkg x-writing --id F-001 --to recovered`，做转移合法性校验 + 入账本 + 入审计链。

这样"特色包"才从目录模板升级为**可执行契约**，也符合公理 A（单一事实源）——状态机定义同样由 SOURCES 渲染进文档。

## 六、人类令牌模型的强度与声明不匹配

### 现状

慢车道的实现是命令行 `--yes`（L764-767、L856-858）：

```python
if level in ("L8", "L9") and not yes and (is_first or redeliver):
    sys.exit(f"[慢车道] {level} 需人类令牌。先展示并确认：\n{gate}\n确认后加 --yes")
```

### 问题

`THREAT_MODEL` 声明："防②防SOP约束下粗心；防③（完整权限蓄意agent）不防"。

但 `--yes` 只是一个命令行 flag——**任何能调用命令的 agent 都能加上它**。而 ② 档的"粗心"恰恰表现为随手加 `--yes` 让流程走下去。

结论：**声明防 ②，实际防不住 ②**。这与 guard 的情况（ARCH-008）是同一类病灶——措辞与能力不匹配。

### 建议

按强度递增，选一档落地：

1. **弱（低成本）**：`--yes` 时强制回显——打印宪章全文并要求命令中带上宪章里随机指定的一个片段（如 `--yes --echo "objective hacking"`），确保"读过"而非"跳过"
2. **中**：人侧生成一次性 token 文件（人侧持有），命令读取并**核销**（用后删除），token 与 level + 包 sha256 绑定
3. **强**：人侧私钥签名，包内置公钥验签

至少做到第 1 档，让 ② 档违规需要多一个非命令行动作。同时把 `THREAT_MODEL` 的措辞校准为"② 档提供阻力与留痕，不提供强制拦截"。

## 七、基础设施层：两个被忽略的缺口

### 7.1 时钟未注入

`time.strftime("%Y-%m")`（L234）、`time.time()`（L893、L1083）直接调用。

后果：**跨月逻辑与 TTL 逻辑无法在测试中模拟**。现有 `t_cross_month_real`（L2232）只能依赖真实跨月，实际上永远测不到真正的跨月分支——这个用例在一年里只有极少数时候能覆盖到目标路径。

建议：抽 `Clock` 接口（`now()` / `stamp()`），测试注入 fake clock。这不是为了优雅，是为了让跨月链接续接（公理中明确要求的能力）真正可测。

### 7.2 文本落盘没有唯一出口

L742 与 L748 的注释自曝了这个问题：

```python
rs.write_bytes(REFLECT_SYNTHESIS.encode("utf-8"))  # v3.7 修复：write_text 在 Windows 写 CRLF，与 LF 哈希记账天生不符
```

但只有两处修了，`cmd_install` L845-853 与 `cmd_build` L639-641 仍在用 `write_text`。

后果：**同一个库在 Windows 与 Linux 上产生的 Merkle 根不同**，人侧锚点对账会误报。

建议：`_write_text_deterministic(path, content)` 作为唯一出口——统一处理 LF 换行、UTF-8 编码、原子替换。全项目不得出现裸 `write_text` / `write_bytes`。

## 八、测试架构：先解耦，再分层

### 现状

68 个测试与实现同文件，且大量**直接调用内部函数**（`chain_append`、`validate_entry`、`merkle_root`、`render_*`）。

### 被忽略的后果

这不只是"文件太大"的问题。真正的代价是：**测试锁死了内部实现**。

一旦做 ARCH-002（分层拆包），每个内部函数改名/移动都要同步改测试——重构会在半途卡住，最后大概率放弃分层、退回单文件。

### 建议

测试只通过**公共契约**驱动（`cmd_*` 与 `engine` 的命令行语义），内部函数用契约测试间接覆盖。

**执行顺序上，测试解耦应该排在分层之前**——它是让 ARCH-002 真正可执行的前提。上一条工单集里我把 ARCH-001（异常化）排在最前，这里修正：**测试解耦与异常化并列为最先**，两者都完成后再动分层。

## 九、一个诚实的修正：性能目前不是瓶颈

上一份报告的 P2-15 提到"每次 append 全树 O(n) 重算"。实测数据出来后，我需要修正这个判断：

```
300 条目库：单次 merkle_root 0.005s；单次 retrieve 全库扫描 0.008s
```

**当前规模下性能完全不是问题**。即便外推到万级条目，单次也在 0.1s 量级。

结论：**现在不要为性能做优化**。正确性问题的优先级远高于此。

不过有一个附带收益值得指出：`TUNABLES` 里登记的 `index_hot_budget` 与 `merkle_refresh_trigger` 是未雨绸缪的死配置——而它们会在**事件溯源（建议一）落地后自然获得增量能力**，因为 fold 本身就是可增量的（只需 replay 新增事件）。所以这两个参数不必单独实现，等溯源架构落地后顺势接入即可。

## 架构演进路线（修正版）

```
阶段 0  解锁重构
  ├─ 测试解耦（建议八）：测试只依赖公共契约
  └─ 异常化（ARCH-001）：干掉 24 处 sys.exit

阶段 1  消除安全硬伤与信任缺口（最高性价比）
  ├─ chain_tip 双重锚定（建议二）
  ├─ state 改为 fold 产物（建议一·第一步 → 消掉 P0-4）
  └─ 健康信号解耦（建议三）

阶段 2  结构重构
  ├─ 分层拆包（ARCH-002）
  └─ UoW + 锁（ARCH-004）

阶段 3  语义升级
  ├─ 完整事件溯源：audit 带 payload，memory 可重建（建议一·第二步）
  ├─ 不变式校验器（ARCH-003）
  └─ 检索层可插拔（ARCH-006）

阶段 4  价值兑现
  ├─ 档位迁移 upgrade/downgrade（建议四）
  ├─ 特色包状态机（建议五）
  ├─ 令牌模型加固（建议六）
  └─ 时钟注入 + 写入唯一出口（建议七）
```

**相比上一份工单集的顺序修正**：把"chain_tip + state fold"提到了分层之前。理由是这两项改动**不需要动文件结构**，改动量小（约 1.5 天），却同时消掉了 P0-4（并发丢更新）和一个此前未被发现的安全硬伤——性价比高于任何一项结构性重构。
