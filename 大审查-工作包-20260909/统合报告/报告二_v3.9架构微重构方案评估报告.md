## 二、分歧点裁决

| 分歧 | 各家 | 裁决 | 理由 |
|------|------|------|------|
| **索引** | 豆包 SQLite FTS5｜Qwen stdlib 倒排+双跑 parity｜混元「事件溯源后 fold 天然增量，不单独做」 | **Qwen+混元**：单库 44 条目、触发器 100 未到、纯标准库约束；SQLite 列 v4 触发器。但采纳豆包的「索引↔全量扫描双跑 parity 断言」作验收形态 |
| **并发** | 豆包 WAL+补偿事务｜混元 单写者 flock+seq，不做乐观并发｜GLM 读侧容忍脏读 | **混元**：单写者假设（M-4 前置）下 flock+seq 足够；`importance_accum` 改账本重算是根治（混元原型实测 60/60）——比纯加锁更彻底，**并入收敛点 1** |
| **架构分层** | GLM ARC-001 LibraryCtx 配置对象化｜豆包 DDD 四层｜混元 ARCH-002 分层+zipapp｜Qwen H-02 Context 对象 | **混元/Qwen 折中**：分层+zipapp 保单文件分发（豆包 monorepo+pydantic 列 v4/v5）。配置对象化采纳（灭 set_data_dir 全局改写与测试污染整类 bug） |
| **令牌强化** | GLM ARC-008 挑战-响应（口令+challenge）｜混元 V4-07 三档（回显/token 核销/签名）｜Qwen H3 双钥（列 v4-SEC 慢车道） | **分阶段**：v3.9 采混元「中」档（一次性 token 文件+核销+level 绑定）；双钥签名列 v4.0-SEC（Qwen H3 慢车道） |
| **golden 闭环** | GLM ARC-010 absorb-md --gen-golden 从轨迹生成+版本化｜混元「golden 不可信需重建」（P1-6 实证）｜豆包 CI 门 | **GLM+混元合流**：生成候选→人工裁决→版本化（golden_version 入 eval 比较）→劣化门只在同版本间比较。附混元警告：golden 判别力已被 P1-6 证明有问题，重建后基线会变（可能大降——判别力恢复） |

## 四、明确不做（各家共识 + 混元实测背书）

性能优化（300 条目 merkle 0.005s 实测，非瓶颈）/ 增量 Merkle 单独实现（fold/触发器接管）/ ③档防御（THREAT_MODEL 明示）/ 多写者乐观并发（单写者锁+seq）/ 分布式 / daemon / 向量入核（Ranker 插件接口留位）/ SQLite 主存储（派生索引触发器）。

## 五、统合路线（v3.9，约 8~10 人日）

```
v3.8.3（报告一 P0 批次）
   ↓
AR-03 异常层级（最先，0.5d）──→ AR-01/LibraryTx 唯一写入口（1d）
   │                                ├─ chain_tip 三元组（0.5d，混元 V4-03）
   │                                └─ guard/reflect/shadow/eval 迁入
   ▼
AR-02 INVARIANTS 不变式注册表（1.5d）── doctor 复用
   ├─ 并行：AR-04 复合锚点（慢车道裁决）／AR-05 操作注册／令牌中档
   ▼
AR-06 倒排索引（双跑 parity）→ AR-07 增量 Merkle+口径统一 → golden 闭环（GLM ARC-010）
   ↓
发布门：run-tests 全绿（含攻击用例集）+ doctor 信号矩阵全绿 + verify 退出码 + 锚点重抄录
```

**适用条件**：单文件+纯标准库+单写者三约束不变；AR-04 触公理 E 走慢车道；排序变更过 L-004 劣化门。
**与 v4 的关系**：AR-01/02/03 及攻击用例集是 v4 行为等价验证的基准（Qwen 判断正确）——先做这三条稳赚不赔。

## 六、可信度声明

- 本报告的「收敛度」按四家独立提出计数——独立收敛是多源审查中最强的可信度信号。
- 四家方案无一被整体否决：GLM 结构诊断+Qwen 轻量执行+豆包覆盖面+混元数据模型，各取所长。
- 唯一被整体降权的是豆包的企业级处方（WAL/DDD/SPI）——非错误，而是与单文件约束的体量错配（豆包自警「过度设计风险」成立），全部条目转入 v4 选项库。
