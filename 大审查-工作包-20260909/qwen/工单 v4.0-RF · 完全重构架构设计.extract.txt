# 工单 v4.0-RF · 完全重构架构设计（探讨）

| 字段 | 内容 |
|---|---|
| **工单编号** | `v4.0-RF` |
| **性质** | **探讨/提案类工单**——本次审批对象是「探讨与提案 + POC」，**不是重构执行本身**；执行需另立工单并走慢车道 |
| **标的** | 以 `bootstrap_v3.py` 为原型的下一代知识库引导系统 |
| **设计约束** | 公理 A–G 与六铁律全部结构性保留；审计链不分叉；人侧锚点可解释迁移 |
| **交付物** | 架构提案（本文件）+ 行为等价验证框架 + 核心域 POC |
| **状态** | 待人类令牌裁决是否进入探讨执行 |

## 1. 为什么要完全重构（而不是继续优化）

v3 的根本矛盾不在某个函数，而在**三个结构性错位**：

1. **话语与结构错位**：公理 D 明确说「lifelog=真相源，记忆条目=投影」，但实现里 memory 是直接写入的权威，投影**不可重建**，doctor 只能报告不一致、无法修复——事件溯源说了，没做。
2. **交付形态与开发架构错位**：单文件是**分发格式**，却被当成了**开发架构**。数据、策略、渲染、业务、CLI、测试挤在一文件里，任何一层变动都牵扯包锚。
3. **纪律与机制错位**：铁律、账本、根、链的协同靠每个操作自觉（v3.9-1 审计出的 P1 全部源于此），优化能补洞，但补不出「不可能出洞」的结构。

优化的上限是「洞少一点」；重构的目标是「洞在结构上不存在」。

## 2. 设计原则

1. **事件溯源做实**：账本+审计链=事件日志；memory 与索引=可重建投影（公理 D 的完全体）。
2. **唯一写路径**：一切变更经事务提交，顺序与刷根由结构保证，不由自觉。
3. **不变式即代码**：每条铁律一个可执行谓词，提交边界统一执法。
4. **数据与代码分锚**：常变的数据与少变的代码各有哈希，复合成锚。
5. **分发形态不变**：开发模块化，交付仍为自包含单文件（构建步骤打包）——不破坏既有使用方式。
6. **重构本身遵守公理 G**：v4 先 shadow、先证明行为等价，再谈切换。

## 3. 目标架构

### 3.1 分层

```
┌────────────────────────────────────────────────┐
│ CLI 薄壳：参数解析 + 异常→退出码映射（唯一 exit 点） │
├────────────────────────────────────────────────┤
│ 应用层 use cases：install / append / retrieve /   │
│   eval / doctor / guard / migrate …              │
│   每个 use case = 一份事务计划，无直接 I/O          │
├────────────────────────────────────────────────┤
│ 领域层（纯函数，无 I/O，可全量单测）：              │
│   Entry(SchemaV4) · AuditChain · ChainVerifier   │
│   MerkleTree(增量) · Invariants · Registry       │
├────────────────────────────────────────────────┤
│ 端口与适配器：                                    │
│   Store(规范文件+派生索引) · ArxivGateway         │
│   Renderer(纯渲染) · FsLayout(库布局)             │
└────────────────────────────────────────────────┘
```

### 3.2 开发模块树（开发形态 ≠ 分发形态）

```
bootstrap_v4/
  core/            # 领域层：chain.py / entry.py / merkle.py / invariants.py / errors.py
  usecases/        # 一个用例一个文件，声明读写面
  adapters/        # store.py / arxiv.py / render.py / layout.py
  sources/         # 单一事实源，数据化、独立哈希：
                   #   registry.json / tunables.json / laws.json / levels.json / packages.json
  cli.py           # 薄壳
  build.py         # 模块树 → 单文件分发产物（自解压式，兼容 v3 交付形态）
```

### 3.3 库数据布局（对 v3 兼容扩展）

```
mylib/
  audit/lifelog-*.md      # 事件日志·链（规范，只追加，真相源）
  ledger/changes.jsonl    # 事件日志·结构化（事件携带完整负载，见 D1）
  memory/…                # 条目投影（规范文件；语义上=可由事件日志重建）
  store.db                # 索引投影（派生，可随时删除重建）
  state.json              # 复合根 + schema_version
  spec.md / AGENTS.md / … # 渲染产物（带 rendered_by 戳）
```

### 3.4 核心机制设计

**① 事件溯源做实（公理 D 完全体）**
`append` 事件携带**完整条目负载**写入账本；memory 文件是该事件的物化。新增授权命令（人类令牌）：
```
rebuild-projection --lib .    # 重放账本 → 再生 memory 投影
                              # 旧投影先整体移 attic（铁律1：重建不销毁）
```
→ doctor 从「只报告」进化为「报告 + 授权修复」，不一致第一次变得可解。

**② 事务（唯一写路径）**
```python
with Tx(lib) as tx:
    tx.put_entry(e)          # 仅暂存
# commit 固定顺序：
# pre-不变式 → 落盘 → chain_append → ledger(带负载) → 增量根 → 原子写 state → post-不变式
```
任何操作都无法「忘刷根」或乱序——结构使然。

**③ 不变式注册表**：六铁律逐条谓词，提交边界执法，doctor 复用同一谓词。「一致」的定义全系统唯一。

**④ 存储：规范文件 + 派生索引**：规范数据仍是人类可读文件（可 grep、可入 Merkle）；`sqlite3`（stdlib）承载索引与查询面，doctor 校验索引↔规范一致，`store.db` 可随时重建。

**⑤ 链校验单点定义**：
```python
class ChainVerifier:
    def fully_linked(self, audit_dir) -&gt; list[Defect]
    # 自哈希 + 同文件相邻链接 + 跨月衔接，一处定义，四处复用（doctor/提交后校验/migrate/guard）
```

**⑥ 复合锚点**：
```
package_anchor = H( code_digest, registry_digest, tunables_digest, laws_digest )
```
人侧锚定表记录各层 digest → 可表述「哪层变了」；数据日常迭代不再触发全局重锚。

**⑦ 渲染管线**：`render(sources)` 纯函数；产物头部嵌 `rendered_by=v4.x, sources_digest=…`。校验判定：digest 不同→「版本漂移，走 build-docs」；digest 相同而内容不同→「手改违例」。公理 B 精确执法。

**⑧ 操作注册**：`@engine_op(name, writes=bool)` 声明读写面；读操作结构上不可能触碰 state。

### 3.5 关键决策表（ADR 摘要）

| 决策 | 内容 | 代价 |
|---|---|---|
| D1 | 账本事件携带完整负载，memory 降为可重建投影 | 账本体积增大（磁盘换一致性） |
| D2 | 规范数据保持文件形态；SQLite 仅做派生索引 | 双面对账成本（doctor 承接） |
| D3 | attic 维持物理移入（尊重铁律1 字面），索引中以状态位表达 | 无 |
| D4 | 分发仍单文件，由 `build.py` 打包 | 构建步骤进锚点管理 |
| D5 | schema 版本化 + 迁移注册表 | 每条目多一字段 |

## 4. 公理与铁律的传承映射

| 现行 | v4 落地 |
|---|---|
| A 单一事实源 | `sources/` 数据化，各源独立哈希、独立治理 |
| B 文档即产物 | 纯函数渲染 + `rendered_by` 戳，漂移/篡改二分 |
| C 统一账本 | 账本升格为携带负载的事件日志（唯一真相源） |
| D 双平面 | 事件溯源做实：投影可重建（D1） |
| E 根锚定 | 复合锚点 + 人侧锚定表分层记录 |
| F 慢车道 | `GateError` + 人类令牌；回退=移 attic 原样保留 |
| G 可证伪 | 重构过程本身先 shadow、先行为等价证明 |

## 5. 迁移与兼容（链不分叉是硬约束）

1. **`migrate-v3`**：v3 库 → v4 布局；审计链续接——v4 首行 `prev = v3 链尾哈希`（沿用 M-002 形态）；条目经 schema 迁移；投影与索引重建。
2. **根变动即锚事件**：Merkle 根重算须人侧重抄录，走慢车道留痕——不允许静默换根。
3. **行为等价 harness**：同一 golden 集分别跑 v3/v4，比对 `recall@5/MRR`、doctor 判定、链哈希。等价性证明是切换的前置条件（公理 G 用于重构自身）。
4. **shadow 双跑期**：过渡期 v4 只读校验 v3 库，差异只报告；连续 N 天零差异后才可提议切换。
